Every architecture is a set of trade-offs. When I designed officeParser, I made three on purpose:

  • I chose an npm package with no office suite behind it over wrapping a desktop application.
  • I chose structure and meaning over reproducing how a page looks in print.
  • I chose running in both Node.js and the browser over features that would need a native rendering engine.

Those choices make officeParser a good fit for document ingestion, format conversion, and client-side processing. They also mean there are jobs it cannot do, and it is better that you hear that from me than discover it in production.

If your project needs any of the following, use something else.

1. You Need a PDF That Matches Word Exactly

Suppose the requirement is: "I have a contract in Word. I need a PDF with the same line breaks and the same page breaks that Word would produce."

officeParser cannot do this.

Where Word breaks a line or a page is not written in the file. It is computed by Word's layout engine from font metrics, kerning, and its own rules. officeParser models what a document says: headings, paragraphs, tables, lists, formatting. Its PDF output lays that structure out again, through a browser engine or its own simpler one. The content will be right. The page breaks will not be Word's.

What to use instead
  • Word itself, or Microsoft's own conversion through the Graph API. Only Word's engine reproduces Word.
  • LibreOffice in headless mode: soffice --headless --convert-to pdf document.docx. Close to Word, though not identical, and it needs the document's fonts installed.
  • Gotenberg: a Docker service that wraps LibreOffice and Chromium behind an HTTP API.

2. You Need a Spreadsheet That Recalculates

Suppose the requirement is: "Load a workbook, change cell B4, and have every formula that depends on it update."

officeParser is not a calculation engine.

When it reads an .xlsx file, it reads the values: for a formula cell, the result Excel computed and saved the last time the file was written. It does not read the formula text, it does not evaluate anything, and it cannot write an .xlsx back out (see section 4).

What to use instead
  • HyperFormula: a headless spreadsheet engine in TypeScript, from the Handsontable team, with a dependency graph and several hundred built-in functions.
  • ExcelJS: reads and writes workbooks, including formulas and styling. It does not calculate either.
  • Apache POI (Java): workbook manipulation with a formula evaluator.

3. You Have Legacy Binary Files (.doc, .xls, .ppt)

The pre-2007 Office formats are a different family: binary records inside a compound file, not XML in a ZIP. officeParser reads the modern formats (.docx, .xlsx, .pptx), OpenDocument, PDF, RTF, and the text formats. It does not read .doc, .xls, or .ppt.

If you have an archive of old files, convert them first. LibreOffice does this well: soffice --headless --convert-to docx old-file.doc. Then parse the result.

4. You Need to Write Spreadsheets or Slides

officeParser reads fourteen formats but writes fewer. It generates DOCX, ODT, PDF, HTML, Markdown, LaTeX, RTF, EPUB, CSV, plain text, and chunks for retrieval. It does not generate .xlsx, .pptx, .ods, or .odp.

A spreadsheet can go out as CSV, and a deck can go out as a document, but if the deliverable has to open in Excel or PowerPoint as a native file, use a library built for writing them, such as ExcelJS or PptxGenJS.

5. You Need to Run Macros

Macro-enabled files carry VBA code. officeParser has no VBA runtime. It never executes macro code, and it does not read it or carry it into anything it generates. If your workflow depends on a macro running, you need Office itself.

6. You Need a TeX Engine

officeParser reads LaTeX and writes LaTeX, but it interprets LaTeX. It does not compile it.

Reading a .tex file, it follows the structure the way a converter does: sections, lists, tables, math, footnotes, citations, and the macros you define yourself (\newcommand, \def), which it expands within fixed limits. It does not load packages, so a command from a package it does not know keeps its text. Drawings (TikZ, pgfplots, picture) are left out. And it never typesets, so there are no line breaks, page numbers, or floats placed on a page.

Going the other way, ast.to('tex') gives you source that compiles with pdfLaTeX, XeLaTeX, or LuaLaTeX. To turn that source into a camera-ready PDF, you still run a real TeX distribution.

Smaller Limits Worth Knowing

  • Slide reading order. Shapes on a slide are read in the order the file lists them, not sorted by position. The PPTX article explains why that is hard.
  • Untagged PDFs. Without a tag tree, tables and headings are recovered from geometry, which is best-effort. The PDF article has the details.
  • Runtime. The npm package needs Node.js 22.13 or newer.

When officeParser is the Right Tool

Reach for it when the job is:

  • Getting documents into a search index, a retrieval pipeline, or an LLM prompt with their structure intact.
  • Converting between Office formats, Markdown, HTML, LaTeX, and PDF from one typed tree.
  • Processing documents in the browser, so a confidential file never leaves the user's machine.
  • Running in a plain Node.js service where you would rather not install and supervise an office suite.

That is the job it was built for. For everything above the line, use the tool built for that job. Knowing where the boundary sits is part of using any library well.
