officeParser 8.7.0 fills OpenDocument text templates, .odt and .ott, with the same tags and data as Word templates, through the same OfficeTemplate.render, tags() and check().

The tag language was never the hard part. The engine that pairs blocks and walks the data does not care which format it is in, so I moved everything Word-specific out of it into a dialect, and wrote OpenDocument's. This post is about what that dialect had to know: where an ODT keeps its text, how a tag gets split, why a 22-byte element is read as 16 spaces, and why every copy a loop makes needs new names.

A Small Template

I built a template by hand, as an .ott: a greeting whose tag LibreOffice would have split across a span, a reference after a long run of spaces, a loop over list items, a loop over table rows below a heading row, and a loop over a paragraph holding a bookmark, a footnote and a comment. The header holds {{ company }} statement. Then: 

const data = {
    company: 'Acme',
    name: 'Ada',
    ref: 'INV-7',
    tasks: ['Sign', 'Return'],
    lines: [{ item: 'Bolts', qty: 2 }, { item: 'Nuts', qty: 5 }],
    people: [{ name: 'Ann' }, { name: 'Bob' }, { name: 'Cy' }],
};
const out = await OfficeTemplate.render(templatePath, { data });

Read back with parseOffice and written as text, the long run of spaces shortened to its count:

Dear Ada,
Reference[256 spaces]INV-7
To do: Sign
To do: Return

| Item  | Qty | 
| Bolts | 2   | 
| Nuts  | 5   | 

Ann
Bob
Cy
Checked.


--- Notes ---
About Ann
About Bob
About Cy

I then opened the result in LibreOffice 7.3, headless, and printed it to PDF. It opened, the header read "Acme statement", and LibreOffice numbered the three copied footnotes 1, 2 and 3.

What an ODT Keeps Where

An ODT is a zip, like a DOCX, but flatter. There are no relationship files: parts are found by name.

PartWhat it holdsWhat a render does to it
mimetypeThe package's media type, as plain textWrites it first and stored, not compressed; switches a template's type to a document's
META-INF/manifest.xmlEvery part and its media type, the package's own under the path /Switches the root's media type for an .ott; drops encryption data for a template that was decrypted
content.xmlThe body, with the notes, comments and text boxes inside the paragraphs that hold themFills tags
styles.xmlStyles, and the master pages, which hold the headers and footersFills tags
meta.xml, pictures, the restTitle, author and the like; mediaCopied as they are

Word keeps each header in a part of its own (word/header1.xml); OpenDocument keeps them all with the page styles, so tags() gives the sample's header tag, {{ company }}, the part styles.xml. The mimetype entry must come first and stored, so the type can be read at a fixed place near the start of the file without unzipping. The sample's entries come out as mimetype, META-INF/manifest.xml, content.xml, styles.xml, mimetype at compression method 0.

A Tag Split Across Spans

In what is actually inside a DOCX I described Word's runs: text sits in a <w:t> inside a <w:r>, and a new run starts at every change of formatting, so a typed {{name}} can arrive in three. OpenDocument splits the same way with less markup. Text sits straight in the paragraph, and only a stretch with formatting of its own is wrapped, in a <text:span>. Type {{name}}, make two letters italic, and the paragraph is: 

<text:p>Dear {{<text:span text:style-name="T1">na</text:span>me}},</text:p>

The engine reads a paragraph as a list of runs. In a DOCX a run is the text of one <w:t>; in an ODT it is each stretch of character data directly inside a paragraph (text:p, text:h) or inside a span, a link (text:a) or a text:meta in it. The runs of one paragraph are joined, the tags are found in the joined text, and each run a tag touched gets a marker: the first stands for the tag, the others for nothing. So the value goes where the tag began, and takes that place's formatting. Here the tag began outside the span, so Ada is not italic, and the span is left behind, empty: 

<text:p>Dear Ada<text:span text:style-name="T1"></text:span>,</text:p>

A note, a comment or a text box sits inside the paragraph that holds it, but its paragraphs are its own: a tag never runs from the paragraph into its footnote. Some text is never read for tags at all: the text of a field such as text:date, a note's citation, a comment's author and date, and deleted text kept for tracked changes.

Spaces That Are Elements

OpenDocument folds white space as HTML does: two spaces in a row read as one. A second space is kept as an element, <text:s/>, and a run of them as one element with a count, <text:s text:c="5"/>. A tag typed with spaces carries them in that form, and may be split across a span besides: 

template: <text:p>Hello {{<text:s/>who<text:span text:style-name="T1"><text:s text:c="2"/></text:span>}}!</text:p>
rendered: <text:p>Hello Ann<text:span text:style-name="T1"></text:span>!</text:p>

A value is written back the same way, so it reads as typed. Here is one with a tab, three spaces and a new line, in [{{ v }}]: 

value:    'Qty:\t2   pcs\nboxed'
rendered: [Qty:<text:tab/>2 <text:s text:c="2"/>pcs<text:line-break/>boxed]

The count is where my first version went wrong, on the 8.7.0 branch before the release, so no published version did this. It read <text:s text:c="256"/> as the 256 spaces it stands for. That element is 22 bytes. Every limit on a template is a limit on its XML: the parts' sizes, the number of elements. A paragraph's text had never been longer than its XML, so those limits also bounded the text, and with it every pass the engine makes over the text. A run of spaces broke that: 22 bytes became 256 characters, 11.6 times, and a large part of such runs could pass the longest string V8 will make.

So the engine now reads a long run short and writes it back whole. A <text:s/> is read as at most 16 spaces, and the run keeps the count it stood for. <text:s/> is 9 characters and reads as 1; any element with a count is at least 20 characters. The text is never longer than its XML again, and a tag needs no more: the only spaces it looks at are its own and its delimiters'. Where the caller's delimiters hold more than 7 spaces in a row, the limit rises to twice that run plus one, so a run read short still holds the end of one tag and the start of the next. The spaces not read are written back where no tag is: in the run's text outside tags, or between the tag ending in it and the tag starting in it. Here is a run of 999,999 spaces, 25 bytes of XML, between two tags: 

template: <text:p>{{ a }}<text:s text:c="999999"/>{{ b }}</text:p>
rendered: <text:p>left<text:s text:c="999999"/>right</text:p> (1 ms)

The element goes out as it came in, 25 bytes standing for the same million spaces. (The time is the whole render, as the script measured it on my M1 Pro under Node 24.)

What a Block Can Cover

Where a block's tags sit decides what it covers, as in Word: both tags in one paragraph, the text between them; in paragraphs side by side, the paragraphs between them, a paragraph holding nothing but a tag removed with it; in different cells of one table, whole rows. OpenDocument adds two places.

  • List items. Tags in items of one list cover the items between them, and an item holding nothing but a tag goes with it. In the sample, three items ({{ for t in tasks }}, To do: {{ t }}, {{ endfor }}) became two: "To do: Sign" and "To do: Return".
  • Heading rows. A table's heading rows, the ones repeated on every page, sit in a table:table-header-rows of their own. A loop inside them repeats there: one over Q1 and Q2 left two heading rows. A block that starts in the heading rows and ends in the body is refused, rather than writing a table whose heading rows are torn open: 
TEMPLATE_SYNTAX: [OfficeParser]: Template tag '{{ for h in heads }}' in content.xml and the other tags of its block do not
enclose content together: one is in a table's heading rows and another is not.

Afterwards the part is repaired where loops and branches left it invalid: a table or group of rows with no row is removed, and a cell, header, footer, note, text box or comment with no paragraph gets an empty one (a style:header left empty would also hide the left-page header in LibreOffice). A bookmark whose end went with a branch is closed after its start.

Copies Need Fresh Names

A loop copies content, and content carries names that must be unique: an xml:id any element may have, a note's text:id, the names of bookmarks, reference marks, comments, frames, tables and sections, a drawing's draw:id. Each first write keeps its name. Each later copy gets the name with a number, person_2, counted past every name the template already holds, and a range's end follows its start.

To see what is at stake, I wrote the sample's loop paragraph three times by hand with its names unchanged, as a copy that ignored them would, and let LibreOffice 7.3 open and save it. Then I did the same with the render's output:

In each copyNames kept, after LibreOfficeRendered, after LibreOffice
Paragraph xml:idperson; the other two droppedperson, person_2, person_6
Bookmarkwho, who1, who2, renamed by LibreOfficewho, who_3, who_7
FootnoteAll threeAll three
Comment, its range ending after the loop"Check Ann" only"Check Ann", "Check Bob", "Check Cy"

Nothing was refused. LibreOffice opened every file and dropped or renamed what clashed, silently. The notes survived either way. The comments are worth a closer look. A comment can cover a range: office:annotation where it starts, holding its text, and office:annotation-end with the same name where it ends. In the sample the comment starts inside the loop and ends after it, in "Checked.". Written three times under one name, with one end, LibreOffice kept the first comment and lost the other two and their text. (Without the end, it kept all three.)

A range across a loop's edge has one start and one end, so the render writes it once. Most of what a range is made of is then left out of the later copies. A comment cannot, since it holds its text, so each later copy is written as a comment of its own, on a point, under a fresh name: 

<office:annotation office:name="c1">...Check Ann...</office:annotation>
<office:annotation office:name="c1_5">...Check Bob...</office:annotation>
<office:annotation office:name="c1_9">...Check Cy...</office:annotation>
<text:p>Checked.<office:annotation-end office:name="c1"/></text:p>

One more place needed a name. A block may cut through a span, a link or a text:meta: the element is closed before the cut and opened again after it. The half after the cut is a second element, so when the element has an xml:id, that half gets one of its own.

A Template Becomes a Document

An .ott is an .odt with another media type: application/vnd.oasis.opendocument.text-template in mimetype and on the manifest's root entry. Filling one gives a document, not another template, so the render switches both to application/vnd.oasis.opendocument.text, as the sample's output shows. Nothing else in the manifest, or in meta.xml, changes. A password-protected template is decrypted with password or onPassword, and the document is written plain, its manifest without the encryption data.

What It Does Not Do Yet

  • Presentations and spreadsheets are not templates yet. A .pptx, .odp, .xlsx or .ods passed to OfficeTemplate.render rejects with TEMPLATE_UNSUPPORTED_FORMAT. Of the two, slides are the easier; in spreadsheets, moving the rows below a loop, with the formulas, merged cells and print areas that point at them, is the real work.
  • A <text:tab/> or <text:line-break/> typed inside a tag is read as nothing, and a quoted string in a tag holding more than 16 spaces in a row reads as 16, the bound on <text:s/>.
