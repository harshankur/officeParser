A Word template says "Dear {{first name}},". The data has a first name column, because the data came from a spreadsheet and that is what the column is called. Render it with officeParser 8.6.0 and every letter says "Dear {{first name}}," with nothing filled in and nothing said. The tag was never a tag: a field's name has no spaces, so the engine read it as prose between braces, and prose is written as typed.

This post is about what 8.7.0 does with text that only looks like a tag, how it tells that apart from braces that are just prose, code or JSON, and the other places where data written for people meets a template written for machines: numbers with a decimal comma, numbers stored as text, and block keywords spelt the way another template language spells them.

Four Ways to Almost Write a Tag

Here is a template with four near misses and one real tag, made from Markdown with officeParser's own converter, then listed with OfficeTemplate.tags() and rendered: 

Dear {{first name}},
Your order {{ order } ships on {{ date }}.
Total: {{ total | fromat "0.00" }}
Nom : ｛｛nom｝｝

What tags() lists, kind, tag and reason:

text "{{first name}}" space-in-name
text "{{ order }" missing-delimiter
field "{{ date }}"
text "{{ total | fromat \"0.00\" }}" unknown-filter
text "｛｛nom｝｝" full-width

And what render() gives with data holding every one of those values, a first name, an order, a total and a nom: 

warning: TEMPLATE_NOT_A_TAG {"texts":[{"text":"{{first name}}","part":"word/document.xml","reason":"space-in-name"}, ... ],"found":4}
Dear {{first name}},
Your order {{ order } ships on 9 November.
Total: {{ total | fromat "0.00" }}
Nom : ｛｛nom｝｝

The document is what 8.6.0 would write. What changed is that it is no longer silent. tags() lists each near miss as kind: 'text' with a reason, and render() and check() raise one TEMPLATE_NOT_A_TAG warning per call with each text, its part and its reason. The four reasons are exactly these:

ReasonExampleWhat it is
space-in-name{{first name}}A name with white space in it: letters, digits, _ . - and spaces, starting with a letter or _, at most 64 characters
unknown-filter{{ total | fromat "0.00" }}A field through a word after | that is no filter, built in or in formatters
missing-delimiter{{ name }, { name }}A name between delimiters one of which is a character short
full-width｛｛nom｝｝Delimiters typed with full-width characters, as a Japanese or Chinese keyboard types them

It is a warning, not an error, because 8.6.0 rendered every one of these templates and some such text is meant. Refusing them would break templates that work.

Braces That Are Just Braces

The first two reasons are easy, because they sit between whole delimiters, where the engine already looks for tags. The hard one is missing-delimiter. A template can hold code, JSON, set notation and sentences with braces in them, and none of that may be reported. Each line below is a template of its own, with what tags() lists as text: 

Use {x} or { x } in a set.                      -> nothing
Send `{"name": {"first": "Ana"}}` as the body.  -> nothing
const o = {a: {b}};                             -> nothing
A pair of sets: {{x}, {y}}.                     -> nothing
An empty {{}} stays.                            -> nothing
Dear {{ name }, welcome.                        -> {{ name } (missing-delimiter)
Dear { name }}, welcome.                        -> { name }} (missing-delimiter)
Dear {{ name }, see {x}.                        -> {{ name } (missing-delimiter)
Dear {{ name }, see {x}}.                       -> nothing

Look at {{x}, {y}}. Read alone, {{x} is a start delimiter, a name and an end one character short, and {y}} is the same the other way round. Together they are a set of two sets. The difference is balance: the brace {{x} leaves open, a later one closes.

So officeParser counts braces, typed as stored, as a stack. The start's character opens one. The end's character closes one when any is open, so the count never goes below zero. A near miss opens its own start characters and then closes its own end characters, the same way. Then:

  • A short start ({ name }}) is not reported inside braces still open, or right after the start's own character.
  • A short end ({{ name }) that leaves some of its braces open is pending: it is code if a later brace closes everything it left open, and reported if anything is still open at the end of the paragraph. That is why the last two lines above differ by one brace.
  • A short end that leaves nothing open is reported at once. Nothing later can make it balance.

This is only done for delimiters of one character typed twice or more each side, such as the default {{ and }}, where "one character short" means something. With delimiters of one character for both ends, such as $$ and $$, a character both opens and closes, so it balances nothing, and braces are not counted: 

Total $5. Dear $ name $$   [$$ $$]   -> $ name $$ (missing-delimiter)

One Pass, and the Version That Was Wrong

A template is input a caller may not control, so the scan has to be linear. It walks the paragraph's text once and stops only at a character a delimiter can start with, its full-width form, or, when braces are counted, a closing brace. Each stop looks ahead at most a delimiter, a name of up to 64 characters and another delimiter, and builds nothing but that short name. Pending short ends sit on a stack whose levels rise strictly, so each is pushed once and popped once. I timed the scan alone, one run each on my M1 Pro under Node 24, on three of the shapes the tests use, at two lengths:

ParagraphSmallerTwice the length
{{a} repeated, every one left open2.0M characters, 43 ms4.0M characters, 66 ms
{{a} repeated, then as many }1.3M characters, 27 ms2.5M characters, 53 ms
{{ a }}} repeated, end delimiter }}}}2.0M characters, 25 ms4.0M characters, 48 ms

It did not start out like this. 8.7.0 went through rounds of review before release, and the scan was rewritten twice. The first version visited every character and allocated at each, five times the cost of reading the text. It charged each near miss against the template's XML element limit, so plain text that 8.6.0 rendered was refused. And it reported both halves of {{x}, {y}}. The fix counted braces.

That counting is what the fourth round found broken. It applied each near miss to the depth as one signed number, the start characters it opens minus the end characters it closes, and it made every short end pending. That holds while the end is no longer than the start. With {{ and }}}, {{ name }} is a short end that opens two and closes two: it leaves nothing open, but it was still made pending at the depth it found, and the next unrelated closing brace closed it as code. Dear {{ name }}, see {x}. reported nothing; 8.7.0 as released reports {{ name }} there. With }}}}, the net was negative and the depth went below zero. Past the 1,000 near misses a template lists, pending ends were kept in a bit set, a bit per depth, and a depth of -1 became word -1 >>> 5, 134,217,727: an array of 512 MB for one paragraph. Listed and unlisted pending ends also followed different rules, so the same text was counted only once the list was full.

That was two representations of one idea, and a signed number only one branch kept above zero. The fix replaced them with one stack and wrote down what must stay true:

  • The depth never falls below zero and never exceeds the start characters read.
  • Only a short end that leaves its own braces open is pending, at the depth before it.
  • Pending levels rise strictly, so when one is closed, every one above it is closed too.
  • Each pending entry is pushed once and closed or reported once, so the count is exact.

The scan is now tested against a reference written as plainly as possible: braces are objects on an explicit stack, each near miss owns the braces it opens, and a pending one is reported if one of its braces is still on the stack at the end. It is quadratic, which is fine for short random texts. The suite runs 20,000 texts in its fast mode and 200,000 in full, each with room for 0, 1, 2, 3 and 1,000 listings. Here, 20,000 texts, 10,645 of them with near misses, gave no differences in 564 ms on the same machine.

A Thousand, Then a Count

Each listing takes a few hundred bytes for a few characters of text, so a template lists at most 1,000 and counts the rest. A template of 1,500 paragraphs, Row 0: {{ value 0 }} to Row 1499: {{ value 1499 }}: 

tags() listed 1000 texts
warning: TEMPLATE_NOT_A_TAG found 1500 listed 1000
  1500 texts that look like template tags are not tags and are written as typed (only the first 1000 are listed): ...

tags() lists, and raises the warning only when its list was cut. The 1,000 are for the whole template. Notes that only loops refer to are compiled on their own, and earlier on the 8.7.0 branch they took a second room of 1,000; one room now serves every part.

Numbers Written for People

Data from a German or Brazilian spreadsheet writes one thousand two hundred and thirty-four and a half as 1.234,50, and French data as 1 234,50. In 8.6.0 that was text, not a number, and a number picture refused it. 8.7.0 reads it with dataNumberSeparators. The template here is Total: {{ total | format "#,##0.00" }}:

DataConfigResult
"1.234,50"noneTEMPLATE_DATA_INVALID (unformattable)
"1.234,50"dataNumberSeparators: { decimal: ',', group: '.' }Total: 1,234.50
"12,50"the sameTotal: 12.50
"1.5", "1.50"the sameunformattable
"0.500"the sameunformattable
"1234.567"the sameunformattable
"1 234,50" (no-break space){ decimal: ',', group: ' ' }Total: 1,234.50

The refusals are the point. With . for groups, 1.5 could be one and a half written the English way, or a typo. Rather than guess, a group separator must be followed by groups of exactly three digits, and the first group is one to three digits. The first group also may not start with 0. That rule came from review before the release: until then, 0.001 was read as 1 and 0.500 as 500, text written with a decimal point read as a grouped integer. A grouped integer never starts with 0, so 0.500 is now refused.

The rule cannot catch everything. With the same setting, "1.500" is fifteen hundred, as German data means it. If the data mixes both ways of writing numbers, no setting can read it right.

numberSeparators, which existed before, says how a picture writes numbers. It stays output only. Data and document often come from different places, and tying the two together would break the common case: 

"1250.5"   { numberSeparators: { decimal: ',', group: '.' } }       -> Total: 1.250,50
"1250.5"   { dataNumberSeparators: { decimal: ',', group: '.' } }   -> TEMPLATE_DATA_INVALID unformattable

Data from a JSON API fills a German document with the first. With one setting for both, it would be refused.

Text That Is a Number

An application filling templates from a table gets every value as text. In 8.6.0, {{ if total > 100 }} with total: '250' was refused as incomparable. In 8.7.0, text that is a number compares with a number as that number, read with dataNumberSeparators when set. Text that is not a number is still refused, because a silent false would pick the wrong branch. With {{ if total > 100 }}Large order{{ else }}Small order{{ endif }}: 

250         -> Large order
"250"       -> Large order
"99.5"      -> Small order
"150 EUR"   -> TEMPLATE_DATA_INVALID incomparable (text with number)
"1.234,50"  -> TEMPLATE_DATA_INVALID incomparable (text with number)
"1.234,50"  -> Large order   (with dataNumberSeparators: { decimal: ',', group: '.' })

A Keyword From Another Language

Template languages spell their branches differently, and a hand used to another one types {{ elseif b }}, {{ elif b }} or {{ end if }}. 8.6.0 already refused these with TEMPLATE_SYNTAX and the remedy in its message. 8.7.0 puts the fix in details.suggestion, the tag as it should be typed, so an editor can offer it: 

{{ elseif b }}   -> TEMPLATE_SYNTAX unreadable, suggestion {{ else if b }}
{{elif  b}}      -> TEMPLATE_SYNTAX unreadable, suggestion {{else if b}}
{{ end if }}     -> TEMPLATE_SYNTAX unreadable, suggestion {{ endif }}

The spaces typed next to the delimiters are kept, so the suggestion matches how the tag was written.

What It Does Not Catch

  • {{ name } } balances, so it is read as code and not reported, though it is likely a typo. A rule that reported it would also report code.
  • A brace stored as a numeric character reference, &#123;, is not counted as a brace.
  • The scan's cost grows with the length of the delimiters, which a caller sets.
  • Across parts, the 1,000 listings fill in the order the parts are compiled, not the order they are shown.
