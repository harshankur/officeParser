A README that wants two columns side by side reaches for an HTML table, and then wants Markdown inside it: bold text, a list, a code span. GitHub's way of writing that is a blank line on each side of the Markdown: 

<table>
<tr>
<td>

**Fast**: reads *every* cell.

</td>
</tr>
</table>

officeParser has read that since 8.1.0. But put one more line in the cell, a <div align="center"> around the text, a heading, or a --- under the table, and the cell came back empty, with a line like op9ta1at81p:0 after the table where the text should have been. 8.8.0 fixes that. This post is about why it happened, which turns out to be one assumption failing several ways, and how 8.8.0 reads such a table instead.

What a Renderer Does With It

CommonMark has no idea of a table cell holding Markdown. It sees an HTML block, which starts at a line beginning with a tag such as <table>, <tr>, <td> or <div> and runs to the next blank line. Then a paragraph of Markdown. Then another HTML block. A renderer passes the HTML blocks through as they are and turns the paragraph into <p>, and the browser, given <table><tr><td><p>…</p></td>…, builds one table. The Markdown ends up in the cell because the browser puts it there.

A library that reads Markdown into a tree has no browser to do that, so it has to stitch the pieces back together itself. That is what the blank lines make hard: the table is cut into pieces, some HTML and some Markdown, and the cell exists only once they are joined.

How officeParser Joined the Pieces

From 8.1.0 to 8.7.1, the reader split the document at blank lines before reading its blocks. When a piece opened a table, the pieces after it were joined to it while the table stayed open, up to 64 pieces. A piece of HTML was joined as written. A piece of Markdown could not be, because the HTML reader would read **Fast** as two asterisks, so it was set aside and a token joined in its place: a private-use character, a random code made once per document, a colon, the piece's number, and another private-use character. The HTML reader then read the whole table, and each token it found in a cell's text was replaced by its piece, read as Markdown.

A private-use character means nothing on its own (a font may draw it as a box, or not at all), so a token that reached the output read as op9ta1at81p:0: the random code and the piece's number. And a token only became its piece when the HTML reader read it. Every reading of a token anywhere else showed the token and never read the piece.

That was the assumption: that a block holding tokens is always read whole, by the HTML reader. The next step of the reader broke it. After the blank-line split, each block's lines were read again for the Markdown block starts that need no blank line before them: a <div> line alone, a heading, a list item, a rule, a setext underline. Each of those cut the joined table, and a part that held a token but did not start with a tag was read as Markdown, with the token as its text.

Before the split, it lifts out fenced code, math, admonitions and comments on lines of their own, and puts a placeholder line with a blank line on each side in their place. Inside a table, that blank line made the comment a piece, the piece became a token, and the <div> line cut it off.

The Other Ways

Cutting was the common way to lose a cell, not the only one. A placeholder could land where text is read as written. A cell holding a <pre> with a fenced block in it: 

<table><tr><td><pre>Run:

```
npm test
```

</pre></td></tr></table>

8.7.1 read its code as Run:, four line breaks, CODE_BLOCK_0 between two private-use characters, and four more line breaks. 8.8.0 reads it as written, the fence's lines and blank lines included. A comment holding an admonition, anywhere in a document, kept a placeholder the same way, and now keeps :::note and its text.

A piece also stood in for its text inside other HTML. A link around a cell's Markdown, <a href="https://example.com/docs">, a blank line, Read the **docs**, a blank line, </a>, came back from 8.7.1 as the text with no link: the token's text node carried the link, and the piece's runs that replaced it did not. In 8.8.0 each run of the piece carries it, and so does a picture in it. And a piece that closed what a tag had opened, the " of an attribute or the --> of a comment, hid that end inside its token. A comment then ran on and took the rest of the table with it; an attribute ran on to the next quote, and the words up to there were lost.

One Block, From the First Table Tag to the Last

8.8.0 states the rule once and makes every step follow it: a table holding Markdown pieces is one HTML block from its first table tag to its last. No line inside that range is read as a Markdown block start, so nothing cuts it, and no underline makes it a heading. Its pieces are read in its cells where they stand in the cells' content, and as the text of whatever they stand in otherwise: an attribute's value, a comment, a <pre>. Every piece is read somewhere, and nothing of a token or a placeholder is shown.

That makes the lines inside the table read as CommonMark reads them, which is what GitHub shows. In the heading sample, # Install is a line of the HTML block that <td> opened, so it is text in the cell, # Install and all, not a heading. That can surprise, but it is what the CommonMark specification says, which GitHub's Markdown follows: the line is part of the HTML block, and a browser shows it as text.

After the last table tag, lines read as they did before. A heading, a list item, a rule or a fence there reads as Markdown, as officeParser read it before (CommonMark would keep such a line in the table's HTML block up to the next blank line, so GitHub shows a --- right under </table> as text). A plain text line right under </table> stays in the table's HTML block up to the next blank line, so *Tested* on Node 18. there is read with its asterisks. That is what CommonMark says, and 8.7.1 read it the same way.

A comment or preformatted text holding a lifted block gets the block back as written. Each lift now remembers the source it replaced, and wherever a placeholder lands in text read as written, the source goes back in its place, blank lines and all. And a piece the HTML reader leaves out, because it stands in an element read as nothing such as <template>, is read after the table, as it would be without the table.

Which Pieces Are Written as Text

One part of this took two tries. A piece inside a tag or a quoted value has to be joined as written, so that a piece holding the " that ends a value ends it where the HTML reader will. My first version decided that while joining: it scanned the HTML so far, and joined a piece as written whenever the scan was not in a cell's content.

The review before the release found where that went wrong. The HTML reader pairs quotes in a tag, and when a quote never closes before the end of its text, it ends the tag at the first > instead. An unquoted value with an apostrophe, such as <td title=it's>, has a quote that never closes. The scan, which could not know what came later, stayed inside that quote and joined every piece after it as written, and the first apostrophe in the prose, It's, closed it: 

<table>
<tr>
<td title=it's>

First *cell*

</td>
<td>

It's the **second**

</td>
</tr>
</table>

8.7.1 read both cells. The first version of the fix read one empty cell. That never went out. What did is safer by construction: every piece is a token while the table is joined, as in 8.7.1, and which pieces go back as written is decided only when the table is read, by a scan of exactly the text the HTML reader is given. A piece is written back only where that scan proves the reader reads it the same way: a piece that holds the end of what it stands in, or one that cannot change how the reader reads on. Anywhere the scan cannot be sure, after a quote that holds a >, inside an SVG, past a DOCTYPE, the piece keeps its token, and a token the reader drops is read after the table. 8.8.0 reads both cells of that table, as 8.7.1 did.

How It Is Checked

The release adds a property check that writes tables the way people write them and some ways they should not: a Markdown piece in a cell beside every kind of block start (each of CommonMark's seven kinds of HTML block, fences, math, admonitions, underlines, rules, headings, list items, quotes, indented code), inside six kinds of opening, followed by one of thirteen endings after </table> (nothing, text, an underline, a rule, a heading, a list item, a quote, a block); then random mixes of up to four of them; then a part of tables holding unpaired quotes, unclosed values and comments beside prose full of apostrophes. Every piece holds marker words, and a document fails if a marker word is missing from what the reader returns, or if a private-use character or a placeholder's name reaches it.

I ran the release's own check against both versions, seed 1, 10,130 distinct documents (4,524 systematic, 2,996 random, 2,610 with quotes):

8.7.12,1023,031
8.8.000

Each new path is one pass over text the reader already holds, and the suite times the shapes that could make it slower, at two lengths, and checks that the time grows with the length.

What It Does Not Do

  • A table with no Markdown piece is read as before. One written with no blank line, with a heading line in a cell (<td>, # Install, </td> on lines of their own), still moves the heading out of the table, in 8.8.0 as in 8.7.1. CommonMark keeps it in the cell. Nothing is lost or shown as a token there, but the text is in the wrong place.
  • Words in markup the HTML reader reads as nothing stay unread: an attribute it does not keep (a title on a cell), the text of a script or a style. That is the HTML reader's reading of such markup in any document, not something the table loses.
  • A table whose cells nest elements 256 levels deep, past what the HTML reader reads, is read as 8.7.1 read it, without its tokens: its pieces come after its cells instead of in them.

The fix is in the changelog under 8.8.0. If you have a README whose tables still read wrong, I would like to see it: open an issue with the file, or the smallest part of it that shows the problem.
