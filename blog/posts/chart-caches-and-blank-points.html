A chart in a Word document, a slide or a workbook carries a copy of the data it draws, so that a program can show it without opening the sheet behind it. That copy is the chart's cache, and it is what officeParser reads into a chart's chartData. A blank cell in the sheet is a gap in the cache, and until 8.8.0 the gap vanished on the way in: the values after it moved to the wrong categories, in the data and in every output.

setthase reported that (#136) and fixed it (#150), then reported four more things a cache holds that officeParser lost: category levels (#139), number formats (#140, fixed in their #151), axes (#143) and the X values and sizes of scatter and bubble charts (#144). Their #132 also makes 8.8.0 read charts in Word documents. This post is about what a cache holds, why pairing its lists by position was wrong, and what 8.8.0 writes for a chart in every output.

What a Cache Holds

Here is the cache from #136, as Excel writes it: one series of four months, with no label for the second month and no value for the third. 

<c:cat><c:strRef><c:strCache><c:ptCount val="4"/>
  <c:pt idx="0"><c:v>Jan</c:v></c:pt>
  <c:pt idx="2"><c:v>Mar</c:v></c:pt>
  <c:pt idx="3"><c:v>Apr</c:v></c:pt>
</c:strCache></c:strRef></c:cat>
<c:val><c:numRef><c:numCache><c:formatCode>General</c:formatCode><c:ptCount val="4"/>
  <c:pt idx="0"><c:v>10</c:v></c:pt>
  <c:pt idx="1"><c:v>20</c:v></c:pt>
  <c:pt idx="3"><c:v>40</c:v></c:pt>
</c:numCache></c:numRef></c:val>

A blank point is not written as an empty entry. It is not written at all. c:ptCount says how many points there are, and each point that is there says which one it is, with idx. The categories and each series are cached apart, each with its own gaps, so the only thing that ties Mar to its value is the number 2.

8.7.1 read every c:v in order and kept the text alone. For this cache it gave: 

labels  ["Jan","Mar","Apr"]
values  ["10","20","40"]

Nothing in that says which value goes with which label, and anyone reading it, officeParser's own writers included, paired them by position. March got 20, which belongs to the second point, the one with no label. That is the chart's table as 8.7.1's HTML output wrote it: 

        Sales
Jan     10
Mar     20
Apr     40

Pairing by Point Index

PR #150 keeps the indexes. Each list gets a list of the same length beside it holding each entry's point index, and the categories say how many points there are: 

labels        ["Jan","Mar","Apr"]    labelIndexes  [0,2,3]
values        ["10","20","40"]       valueIndexes  [0,1,3]
pointCount    4

The lists are not padded with blanks up to pointCount. A file states its own point count, and a small file can state a very large one: padding would make the output as large as the file says, not as large as what it holds. Lists that existed keep their entries and their order, so code that read them before reads the same. An index list is kept only when every entry has one and they ascend; a list without one holds its points in order. Point labels (pointLabels, a data label's text) get pointLabelIndexes the same way.

Every writer that lays a chart out by point now pairs through the indexes: one row (or one group of bars) for each point index that holds a label or a value, in order, and each list's entry for that index in it. OpenDocument charts had the same fault in another shape. Their data is a small table, a row per point, and 8.7.1 dropped a blank category's label but kept its values, which then paired with the next row's category; a blank value was read as the text NaN that LibreOffice writes for it. 8.8.0 reads each row as its point, with the same index lists.

Quarters Under Years

A chart can group its categories: quarters under years, regions under countries. Excel caches each level apart, innermost first, and an outer label stands only on the first point of its group (#139): 

<c:multiLvlStrCache><c:ptCount val="4"/>
  <c:lvl> Q1 (idx 0)  Q2 (idx 1)  Q1 (idx 2)  Q2 (idx 3) </c:lvl>
  <c:lvl> 2025 (idx 0)  2026 (idx 2) </c:lvl>
</c:multiLvlStrCache>

8.7.1 ran the levels into one list, so four values met six labels: 

labels  ["Q1","Q2","Q1","Q2","2025","2026"]
values  ["1","2","3","4"]

8.8.0 keeps labels to the innermost level, as for a chart of one level, and puts every level in labelLevels, each with its indexes. An outer label covers the points from its index to the next label's: 

labels       ["Q1","Q2","Q1","Q2"]
labelLevels  [{ labels: ["Q1","Q2","Q1","Q2"], labelIndexes: [0,1,2,3] },
              { labels: ["2025","2026"], labelIndexes: [0,2] }]

That is a change to labels for such charts, and a fix: a list of six labels for four points was never right. A chart's table gets a column for each outer level, before the label column, with an outer label on its first point's row, as the sheet behind the chart holds it. 8.8.0's Markdown output: 

|  |  | Sales |
| --- | --- | --- |
| 2025 | Q1 | 1 |
|  | Q2 | 2 |
| 2026 | Q1 | 3 |
|  | Q2 | 4 |

The Text a Chart Shows

A cache holds raw values: a date is a day count, a share is a fraction. The format the chart shows them in is beside them (c:formatCode), and PR #151 reads it. Each series keeps its formatCode and shownValues, the categories labelFormatCode and shownLabels, and the raw values stay as they were: 

labels       ["45658","45689"]           shownLabels  ["Jan-25","Feb-25"]
Revenue      ["1250000","1500000"]       shownValues  ["£1,250,000","£1,500,000"]
Margin       ["0.12","0.15"]             shownValues  ["12%","15%"]

The shown text lines up with the raw list, so it shares its indexes. A chart's table writes the shown text: 

|  | Revenue | Margin |
| --- | --- | --- |
| Jan-25 | £1,250,000 | 12% |
| Feb-25 | £1,500,000 | 15% |

Every Axis

That chart has bars on a date axis and a value axis on the left, and a line of margins on a second value axis on the right. 8.7.1 read the first category axis and the first value axis, by kind. A date axis is not a category axis, so the X title was lost, and the right-hand axis's title with it: 

8.7.1  yAxisTitle "Revenue (£)"                        (no xAxisTitle, no "Margin %")
8.8.0  xAxisTitle "Month", yAxisTitle "Revenue (£)"
       axes: Month (date, bottom), Revenue (£) (value, left), Margin % (value, right),
             a hidden date axis (bottom)
       Revenue: chartType "bar", axisIds ["11","12"]
       Margin:  chartType "line", axisIds ["13","14"]

8.8.0 keeps every axis in axes (its id, kind, side, title, and whether it is hidden) and gives each series the kind of chart it is drawn as and the axes it is drawn on. xAxisTitle and yAxisTitle keep their meaning, now taken from the chart's primary axes: the axes it lists first, whichever plot group comes first in the file. In a scatter chart both axes are value axes, so 8.7.1's "first value axis" was the horizontal one: its title came back as yAxisTitle. In 8.8.0 it is xAxisTitle. HTML and native PDF output draw a series on a right-hand value axis on a second axis there; the native PDF engine does so in every chart but a scatter or bubble chart.

X Values and Bubble Sizes

In a scatter chart each series has its own X values (c:xVal), and a bubble series has sizes too (c:bubbleSize). 8.7.1 kept the first series' X values as the chart's labels and dropped the rest. A chart of two servers, one measured at 1 and 2 users and the other at 100 and 200, read as if both were measured at 1 and 2 (#144). 8.8.0 keeps xValues per series and bubbleSizes, each with its indexes, and leaves labels as it was. The table gives each series its own columns, under a header row that spans them, which a pipe table cannot write, so Markdown output writes this one as an HTML table. Its cells: 

Server A        Server B
Users   ms      Users   ms
1       10      100     30
2       20      200     40

HTML and native PDF output draw scatter and bubble charts as points, a bubble's radius from its size.

Every Output Writes a Chart

Markdown and RTF output wrote nothing for a chart, with no warning. Written alone, a chart of two series came out of 8.7.1 as 107 bytes of RTF with no table in it, and as Markdown holding the workbook's properties and no chart. 8.8.0 writes the chart's data as a table under its title, as DOCX output does. Its RTF, read back by officeParser and written as Markdown: 

**Sales**

|  | North | South |
| --- | --- | --- |
| Jan | 12 | 8 |
| Feb | 15 |  |
| Mar | 9 | 11 |
| Apr | 14 | 13 |

So every writer writes a chart's data now. DOCX, ODT, LaTeX, Markdown, RTF, PPTX, ODP, XLSX and ODS write it as a table. HTML writes a Chart.js chart, or the table when htmlConfig.chartJsSrc is empty. The native PDF engine draws it: bars, or points for a scatter or bubble chart, with category levels and, except in a scatter or bubble chart, a right-hand axis. Plain text and chunks write the chart's text, its labels and then each series' name and values, as before: that is text to search, not a table, and it is not paired.

What It Does Not Do

  • Category levels, X values and bubble sizes are read from OpenXML charts (DOCX, PPTX, XLSX) only. An OpenDocument chart's axes are read, but not which side each stands on, so its series share one axis in HTML and PDF output.
  • A point that is blank in every list has no row: writers write a row for each point index that holds a label or a value, and never pad to pointCount.
  • The native PDF engine draws a chart of at most 12 series, and at most 120 groups of bars or 2,000 points of a scatter or bubble chart; a larger chart is written as its data's text.

If you read chartData yourself, pair a label with a value through their indexes when they have them, and by position only when they do not. The fields are listed in the README's Charts section, and the changes in the changelog under 8.8.0.
