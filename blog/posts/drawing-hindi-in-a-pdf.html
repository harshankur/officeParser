officeParser has a PDF writer of its own, the native engine, which draws a document with pdf-lib instead of a headless browser. Give it a font with pdfConfig.fallbackFonts and it will draw Greek, Arabic, Chinese or Hindi.

Hindi is where it went wrong, in three different ways at once. A word could come apart on the page. Copied out of the PDF, a word read with its letters out of order. And with some fonts every glyph was the wrong one. Each failure has its own cause, and none of them is in the code that lays out lines. This post is about those causes and what I changed for 8.3.0.

A Word is Not Written in the Order It is Drawn

Take the word हिंदी ("Hindi"). In Unicode it is five code points, in the order you type and say them: 

ह  U+0939  HA
ि  U+093F  VOWEL SIGN I
ं  U+0902  ANUSVARA
द  U+0926  DA
ी  U+0940  VOWEL SIGN II

The vowel sign ि comes after ह in the text but is drawn before it, to its left. The anusvara ं is a dot that sits above the letter before it and takes no room of its own. Other words go further: in क्ष, a letter, a virama and another letter become one glyph, a conjunct the font draws as a single shape.

Turning code points into glyphs and their places is shaping. A shaper reads the font's own tables (OpenType's GSUB and GPOS, or Apple's morx) and returns the glyphs in the order they are drawn, each with an advance and an offset. pdf-lib uses fontkit for this. For the word above, with Devanagari Sangam MN, fontkit returns the glyph for ि first, then ह, then the anusvara with no advance, then द and ी.

Failure One: the Positions Were Thrown Away

pdf-lib asks fontkit for that layout, but keeps only the glyph ids. The string it writes into the page is the glyphs one after another, and a PDF viewer moves each glyph along by the width the font file gives it, not by the advance the shaper worked out. Where the two agree, nothing shows. Where they do not (a mark the shaper sets at no advance, or a mark it moves sideways onto its letter), the marks stand in the wrong place and the word drifts apart.

The native engine now asks fontkit for the layout itself and writes it out whole: one string of glyphs (TJ), each moved from where the last one's width leaves off to where the shaper put it, with a rise (Ts) for a mark set above or below the line. Here is the word as it is written into the page now: 

/Span << /ActualText <FEFF0939093F090209260940> >> BDC
1 0 0 1 48 765.89 Tm
[ <0001> <0002> <0003> <0004> <0005> ] TJ
EMC

One string has another advantage over placing each glyph on its own: a program reading the PDF back measures the word as it is drawn. Placed glyph by glyph, a mark that the font gives a width but the shaper gives none made the word look as long as that, and the space after it disappeared when the text was read back.

Failure Two: Copying Gave the Glyphs, Not the Word

When you copy text from a PDF, the viewer does not have the text you typed. It has glyphs, and a table (ToUnicode) mapping each glyph back to characters. Map the glyphs of हिंदी in the order they are drawn and you get िहंदी: the vowel sign before its letter. That is what copying from the native engine's PDFs gave, and what any search over them found.

PDF has an answer for this, the same one browsers and LibreOffice use: wrap the glyphs in a marked-content span that carries the text they stand for, /ActualText. That is the BDC and EMC around the string above. The hex string is the word in UTF-16, in the order it is written. Poppler's pdftotext now reads the line as हिंदी हिन्दी नमस्ते क्षत्रिय श्री कृष्ण, exactly as typed.

Where the span goes matters

My first version closed the span after the text object (ET), and Poppler then read every word as standing at the origin of nothing: the words came out bottom-up, one a line. The span now opens and closes inside the text object, where a text position is current.

I did not mark right-to-left text the same way. Hebrew and Arabic glyphs are drawn in the order they are seen, each already mapped to its letter, and readers put them back in reading order themselves. Given an /ActualText for a Hebrew word, Poppler reversed it a second time. So Hebrew and Arabic are still drawn as pdf-lib draws them, and the shaped path is for the scripts of South and Southeast Asia and for letters with combining marks.

Failure Three: Some Fonts Drew the Wrong Glyphs

Fonts come with two kinds of outlines: TrueType (glyf) and CFF, the PostScript kind, in files that start with OTTO. The native engine subsets a font by default (pdfConfig.subsetFonts), embedding only the glyphs a document uses. For a TrueType font that works. For a CFF font, the subset fontkit writes is not one viewers can read: macOS Preview drew every glyph as another one, and Poppler reported the embedded font as invalid. This was not about Hindi at all. A Latin .otf came out as punctuation.

A CFF font is now embedded whole, labelled as the OpenType file it is. That uncovered a second bug: pdf-lib decides whether a font is CFF by asking fontkit for a cff property that the version it uses does not have, so a whole CFF font was declared as TrueType. And a font embedded whole had widths written only for the glyphs a character maps to directly. A conjunct, a ligature or the left-hand form of ि maps to no single character, so each of those took the PDF's default width of 1000 units. The engine now writes the widths, and the text mapping, for the glyphs it actually draws.

The cost is size. A whole font is the whole file, and a CFF font for Chinese or Japanese is large. If size matters, a TrueType font of the same family keeps the subsetting.

The Bug Found Along the Way: a Shaper That Never Returned

Reviewing the change, I tried a Devanagari word longer than a line. The engine breaks such a word between characters, and the process ran out of memory. The cause was not my code: given a vowel sign with no letter of its script before it, fontkit's shaper for Apple's morx tables never finishes. fontkit prefers morx to OpenType when a font has both, as some of the fonts that come with macOS do. A stray vowel sign is not exotic either: it is what you get when a word changes from bold to plain halfway through and each part is shaped on its own.

For such fonts the engine now lays out a vowel sign or virama with no letter of its script before it unshaped, as the glyph the font gives it, and shapes the text around it as usual. A word too long for a line is now cut between the characters a reader sees (grapheme clusters), never inside a syllable.

Reading It Back

officeParser reads PDFs too, with pdf.js, and the new PDFs found a gap there. pdf.js treats a glyph whose text holds a combining mark as a diacritic of no width. A conjunct's text holds a virama, so pdf.js measures क्ष as zero wide and puts the space before the word after the conjunct, inside the word's /ActualText span, where officeParser's reader dropped it along with the span's own text. A blank inside a span that lies before the span's glyphs is now read as the space before the word. The reader also composes an ActualText's marks with their letters when pdfParserConfig.normalizeText is on, as pdf.js does for the glyphs' text.

Using It

import { readFileSync, writeFileSync } from 'node:fs';
import { parseOffice } from 'officeparser';

const ast = await parseOffice('report.docx');
const pdf = await ast.to('pdf', {
    pdfConfig: {
        engine: 'native',
        fallbackFonts: [readFileSync('NotoSansDevanagari-Regular.ttf')],
    },
});
writeFileSync('report.pdf', pdf.value);

Each character is drawn in the first font that has it, so one Latin font in pdfConfig.fonts and a font for each other script in fallbackFonts covers a document that mixes them. The fonts need the optional peer dependency @pdf-lib/fontkit.

What is Still Not Right

  • Viewers built on pdf.js build their text from the glyphs, not from /ActualText, so copying there can still put ि before its letter.
  • officeParser's own reader can still lose the space after a conjunct when a Latin word follows it: क्ष end reads back as क्षend. pdf.js gives the conjunct no width, so there is no gap left to find.
  • Arabic and Hebrew marks are drawn where pdf-lib draws them: right for the fonts I tested, but not placed by the font's positioning table.

None of this was in the line breaking, the justification or the page layout. It was in the three places where text stops being text: when it becomes glyphs, when a viewer turns glyphs back into text, and when a font file is cut down to fit.
