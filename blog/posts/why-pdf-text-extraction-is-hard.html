Every engineer who sets out to pull text from a PDF starts with optimism: "How hard can it be? It's just text and images on a page."

Two weeks later they are deep in transformation matrices, font encoding tables, kerning adjustments, and scrambled multi-column layouts.

Adobe introduced PDF in 1993 with one goal: a page should look the same on every screen and every printer. It was not designed to be reflowed, searched, or read by a machine. Here is what is actually going on inside a PDF content stream.

1. PDF Has No Words, Lines, or Paragraphs

In HTML, Word, or Markdown, text sits in containers that say what it is: 

<p>The quick brown fox jumps over the lazy dog.</p>

In PDF, none of these concepts exist. A content stream is a list of drawing commands, in a notation that comes from PostScript: 

BT                  % Begin a text object
/F1 12 Tf           % Select font F1 at 12pt
1 0 0 1 72 710 Tm   % Text matrix: position at x=72, y=710
(The) Tj            % Show the glyphs "The"
30 0 Td             % Move 30 units to the right
(quick) Tj          % Show the glyphs "quick"
ET                  % End the text object

Notice what is missing:

  • Nothing says (The) and (quick) are in the same paragraph.
  • Nothing says they are on the same line.
  • Nothing says what order they should be read in.

2. The Missing Spaces

In a text file, words are separated by space characters. In a PDF, the space is often not stored at all.

Typesetting software positions glyphs precisely with the TJ operator, which mixes strings with numeric adjustments: 

[(T) 12 (h) -5 (i) 2 (s) -250 (i) 4 (s) -250 (P) 10 (D) -3 (F)] TJ

The numbers are in thousandths of the font size, and a positive number moves the next glyph back. So -250 means "move forward by a quarter of the font size before the next letter".

To a human, that gap is a space between words. To a naive extractor there is no space character anywhere, and the result is ThisisPDF.

A threshold, not a fact

Every PDF extractor has to guess where the spaces are. The usual rule is a threshold: if the gap between two fragments is wider than some fraction of the font size, insert a space. Set it too high and words run together. Set it too low and kerning splits single words apart. In officeParser that fraction is pdfParserConfig.spaceToleranceFactor, and it defaults to 0.25.

3. Font Encodings: Why Copied Text Comes Out as Gibberish

Have you ever copied text out of a PDF and pasted nonsense?

A PDF does not have to store Unicode. To save space, PDF producers subset fonts: they embed only the glyphs the document uses, and they are free to number those glyphs however they like:

  • Code 0x01 → the glyph for "E"
  • Code 0x02 → the glyph for "T"
  • Code 0x03 → the glyph for "O"

On screen the page shows "ETO". The bytes in the file are 1, 2, and 3.

The ToUnicode CMap

For such a font to be searchable, the producer embeds a ToUnicode CMap that maps each code back to Unicode: 

/CIDInit /ProcSet findresource begin
12 dict begin
begincmap
1 begincodespacerange
<0000> <FFFF>
endcodespacerange
1 beginbfrange
<0001> <0001> <0045>   % Code 0x0001 is U+0045 ("E")
endbfrange
endcmap

A font that uses a standard encoding can still be decoded without one. But when a subset font has neither a usable encoding nor a ToUnicode map, or the map is wrong, the text layer cannot be recovered. The only way to get the words back is to render the page and run OCR on it.

4. Ligatures: When Two Letters Become One Glyph

Good typography joins certain letter pairs into one shape: "ff", "fi", "fl", "ffi", and "ffl".

In a PDF a ligature is drawn as a single glyph. Unicode has code points for these five (U+FB00 to U+FB04, in the Alphabetic Presentation Forms block), and a PDF may map the glyph to one of them. So the word "financial" can arrive as ﬁnancial, with the single character U+FB01 at the front.

Unless the extractor expands those back to plain letters, a search for "financial" will not match the document.

5. The 2D Layout Problem: The Multi-Column Trap

Take an ordinary two-column page: 

+------------------+------------------+
| (1) The quarter's| (3) Next year's  |
| (2) revenue grew.| (4) plans hold.  |
+------------------+------------------+

A parser that sorts text by vertical position reads straight across the gutter:

  1. y = 700: (1) The quarter's (left column)
  2. y = 700: (3) Next year's (right column)
  3. y = 680: (2) revenue grew. (left column)
  4. y = 680: (4) plans hold. (right column)

The result reads: "The quarter's Next year's revenue grew. plans hold."

The Fix: Recursive XY-Cut

The classic way to recover reading order is the XY-cut:

  1. Project every text box onto the horizontal axis.
  2. Look for a vertical band where no text falls (a gutter).
  3. If there is a clear one, cut the page into a left part and a right part.
  4. Do the same on the vertical axis to cut each part into horizontal bands.
  5. Repeat inside every piece until nothing more can be cut. Then read the pieces in order.

The hard part is deciding what counts as a gutter. Cut too eagerly and a wide gap between two words reorders a sentence. In officeParser a vertical cut needs a gap that runs the full height of the block.

What officeParser Does with a PDF

officeParser does not decode PDFs from scratch. It uses Mozilla's pdf.js to read content streams, fonts, and CMaps, and builds the layout reconstruction on top:

  • Lines and spaces. Fragments are grouped into lines and spaces are inserted from the gaps between them (lineToleranceFactor, spaceToleranceFactor).
  • Reading order. Multi-column pages are read with a recursive XY-cut (detectColumns, on by default).
  • Words. Words hyphenated across a line break are joined (mergeHyphenatedWords), and ligatures are expanded (normalizeText).
  • Structure. When a PDF is tagged, headings, tables, lists, and footnotes come from its tag tree (useTags). When it is not, they are recovered from geometry.
  • OCR. Scanned pages have no text layer. OCR (Tesseract) is opt-in, and runs over the images extracted from the pages.
import { parseOffice } from 'officeparser';

const ast = await parseOffice('research-paper.pdf', {
    pdfParserConfig: {
        detectColumns: true,         // recursive XY-cut (default)
        mergeHyphenatedWords: true,  // default
        spaceToleranceFactor: 0.25,  // default
    },
    // For scanned documents, OCR the page images:
    extractAttachments: true,
    ocr: true,
    onWarning: issue => console.warn(issue.code, issue.message),
});

const { value: markdown } = await ast.to('markdown');
Where it is best-effort

Structure recovered from geometry is a guess. In an untagged PDF, a table, or text floated beside a figure, may not separate perfectly. Underline and strikethrough are not extracted, because a PDF draws them as separate lines.

The parser tells you when it suspects trouble: PDF_NO_TEXT_EXTRACTED when a document yields almost no text and OCR is off, and PDF_TEXT_ENCODING_SUSPECT when a fifth or more of the characters it read (out of at least 50) could not be mapped to Unicode.
