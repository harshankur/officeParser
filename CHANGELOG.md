# Changelog

All notable changes to `officeParser` are documented in this file.
The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [8.1.0] - 2026-09-29

This release adds LaTeX, in both directions: LaTeX documents and Overleaf projects parse into the AST, and any parsed document generates LaTeX. It also keeps HTML comments (`<!-- ... -->`) as hidden notes through Markdown, HTML and LaTeX round trips instead of turning them into visible text; reads Markdown as CommonMark and HTML as a browser does, so round trips keep what was written; reads DOCX text boxes, content controls, SmartArt and alternative-format chunks, RTF headers and comments, and PPTX comments that were lost; and bounds what a crafted document can cost (time, memory, output), with limits that grow with the document so a large one is not cut short. Behaviour a caller can observe changed where listed under Changed.

### Added
- **LaTeX parsing (`.tex`, `.latex`, `.ltx`; `fileType: 'tex'`).** A new parser reads LaTeX into the same AST as every other format, so a paper converts to DOCX, ODT, HTML, Markdown, EPUB, chunks and the rest. It interprets sectioning (with `\label`s as heading ids), paragraphs and alignment, run formatting (bold, italic, underline, strikeout, monospace, super/subscript, xcolor colours including `\definecolor`/`\colorlet`, highlights, size switches and grouped declarations), accents, ligatures and text symbols; nested `itemize`/`enumerate` (with `\setcounter` starts), `description` and task items; `tabular`/`tabularx`/`longtable` with `\multicolumn`/`\multirow` merges, column alignment, `\cellcolor` and booktabs rules; `figure`/`table` floats with captions; `\includegraphics` (and `\IfFileExists`, read as the file being there), where a PDF that is only a picture, drawn upright, is taken as that JPEG or PNG; `filecontents` files, written as compiling writes them, for `\input` and `\includegraphics` to read; inline and display math (`equation`, `align`, `gather`, ...) as LaTeX with the document's macros and `\DeclareMathOperator`/`\DeclarePairedDelimiter` declarations expanded and its `%` comments left out; `\footnote` and `\endnote`; `\href`/`\url` (a `%` in a URL is a character, as TeX reads it) and cross-references (`\ref`, `\eqref`, `\nameref`, `\hyperref`, and `\autoref`/`\cref`/`\Cref` with the name of what they refer to) resolved to section, table, figure and equation numbers; `\cite`, `thebibliography`, and `\bibliography`/`\printbibliography` from the project's `.bib` (or its `.bbl`), with `\nocite`, the cited keys listed when no `.bib` is there; `verbatim`/`lstlisting`/`minted` code with its language; quotes; `fancyhdr` headers and footers (into `ast.auxiliary`); `\maketitle` (and beamer's `\titlepage`) as a title block where it stands, a heading styled `Title` followed by `Author` and `Date` lines (`Subtitle` in beamer) with `\thanks` as footnotes, so a converted paper keeps its visible title; `\title`/`\author`/`\date`, beamer's `\institute`, and `\hypersetup` PDF metadata (into `ast.metadata`, where an explicit `pdftitle`/`pdfauthor` wins over `\title`/`\author`); `\today`, as the date of the parse in the document's language (as LaTeX prints the date of the compile) or the text `texParserConfig.today` sets; `beamer` presentations, one `slide` per frame with subtitles, overlays and `\note` speaker notes; theorems (`\newtheorem` with shared counters, numbering within sections and `\theoremstyle`, thmtools `\declaretheorem`, the theorem environments Springer's classes such as llncs provide, a theorem defined in a package out of sight headed but unnumbered, and amsthm proofs ending in □), headed "**Theorem 2.1** (Note)**.**" with a `plain`-style body in italic, and titled blocks in beamer; babel and polyglossia language switches (`\foreignlanguage`, `\text<language>`, `otherlanguage` and language environments), keeping their text, with the main language filling `metadata.language` unless `pdflang` states it; class front matter (`\keywords` and the `keywords`/`IEEEkeywords` environments into `metadata.keywords`, amsart `\address`/`\email`/`\urladdr`/`\subjclass` into `nativeProperties`, IEEEtran author blocks with the authors' names in `metadata.author`, `\IEEEPARstart`, KOMA-Script `\minisec` and `\dictum`, `\epigraph`); and LaTeX 2.09's `\documentstyle` and `\bf`/`\it`/`\tt`-style font switches. References to theorems and to `enumerate` items read their numbers too ("2a" for a nested item), with or without `ignoreInternalLinks`. User macros and environments (`\newcommand`, `\renewcommand`, `\providecommand`, `\def`, `\newenvironment`, and `\NewDocumentCommand`/`\NewDocumentEnvironment` with their `m o O s t d D r R v b` arguments, `\IfBooleanTF` and `\IfNoValueTF`) are expanded, and `expl3` code blocks are skipped. The document is read as pdfLaTeX would compile it: engine tests (`\ifXeTeX`, `\ifPDFTeX`, ...), `\newif` switches, `\ifdefined`, `\@ifpackageloaded`, `ifthen` booleans and etoolbox toggles are decided, and only the branch taken is read (a test that cannot be decided, such as `\ifnum` on a counter, has both branches read and is reported). A file in a legacy encoding declared with `inputenc` (`latin1`, `latin9`, `cp1252`, `koi8-r`, ...) or a `% !TEX encoding` line is decoded in it, and an undeclared file that is not UTF-8 as Windows-1252, included files too. Plain TeX's `\bye`, `\beginsection` and glue are understood, and a ConTeXt document has its sections, lists, code and text read, reported as not being LaTeX. A `% Comment (Author, date): text` line, the form the LaTeX generator writes, becomes a review comment, so comments survive a round trip, and LaTeX the generator writes parses back to the same structure. The usual options apply: `ignoreNotes`, `ignoreComments`, `ignoreHeadersAndFooters`, `ignoreInternalLinks`, `includeBreakNodes`, `extractAttachments` and `ocr`. Adds no dependencies.
- **LaTeX project zips.** A zip holding a LaTeX project, such as Overleaf's "Download source" or the LaTeX generator's own bundle, parses as LaTeX: the main file is the shallowest `main.tex`, else a `.tex` with a `\documentclass` that no other file includes and that is not a `subfiles` or `standalone` part, and `\input`/`\include`/`\subfile` files and images (honouring `\graphicspath`) are read from the archive (an `\input` mid-sentence keeps its paragraph, and the sectioning of included files, a thesis's `\chapter`s, sets the heading levels). A file named `.zip` is routed by what the archive holds, and an unnamed buffer is recognized by its contents. Nothing is read from the filesystem, and no path can leave the project.
- **LaTeX input is bounded like a program.** Macro expansions, expanded text (included files count toward it), include depth, nesting depth and table nesting all have hard limits, include cycles are cut, and nothing is executed, so an expansion bomb or a self-including file costs a bounded, small amount of work, and parsing time grows linearly with the document. Zip reading obeys `decompressionLimits`. An `abortSignal` is honoured before parsing starts, while a project zip is read and while OCR runs; the parse itself runs synchronously, so a timer cannot interrupt it, and its cost is bounded instead.
- **`LATEX_CONSTRUCT_NOT_INTERPRETED`**, **`LATEX_EXPANSION_LIMIT_REACHED`** and **`LATEX_FILE_NOT_FOUND`** warning codes: the input used commands or environments the parser does not interpret (their text is kept; drawings such as TikZ pictures are omitted) or left a group, environment or math open at its end, a macro, include or nesting bound was reached, or included files and images could not be read (a `.tex` holds only the files it carries in `filecontents` blocks; images are kept as path references).
- **LaTeX generation (`to('tex')`, alias `'latex'`).** A new generator turns any parsed document into LaTeX source that compiles unmodified with pdfLaTeX, XeLaTeX, LuaLaTeX, upLaTeX, pLaTeX and `latex` (the last three through `dvipdfmx`), TeX Live 2021 and later: the preamble tells the engines apart with `iftex`, selects fonts per engine (`fontspec` under XeTeX and LuaTeX, `fontenc`/`inputenc` under pdfTeX and the pTeX family), gives every package the `dvipdfmx` driver in DVI mode so images, links and colours work there, and loads only the packages the document uses, among them those its formulas need (mathtools, bm, cancel, esint, siunitx, mhchem and others); KaTeX and MathJax macros (`\R`, `\lang`) are written as the LaTeX they stand for, and a command no loaded package defines prints its own name (reported with `CONTENT_NOT_REPRESENTABLE`), so the output compiles. Headings become sectioning commands (unnumbered by default) with `\label`s for heading ids and linked bookmarks; flat list items are rebuilt into nested `itemize`/`enumerate` (continued numbering kept, task items as check boxes, definition lists as `description`); tables become page-breaking `longtable`s (or `tabular` where a `longtable` cannot go) with a ruled grid, `\multicolumn`/`\multirow` merges, each column aligned as most of its cells are and a cell aligned otherwise by its own, cell colours and a repeated header row, and a table wider than 16 columns continues below itself in bands; footnotes and endnotes become `\footnote` (deferred to `\footnotetext` inside a `tabular`) and `\endnote`; review comments become LaTeX `%` comments; a bibliography becomes `thebibliography`; code blocks become `lstlisting` for a language `listings` knows and `verbatim` otherwise; equations are typeset as real math; images are drawn at their natural size with their alternative text (`alt=`), bounded to the line and page, a PNG or JPEG carried inside the `.tex` so the one file compiles with its pictures (a `filecontents*` block holds it as a small all-ASCII PDF, which compiling writes beside the `.tex` for `\includegraphics` to read with every engine, no shell escape or Ghostscript needed; a PNG that must be decoded to be carried, one with transparency or interlacing, is carried up to 16 megapixels, and a document's decoded images up to 256 megapixels in all; an image the source embedded as a `data:` URI is carried like an extracted one), and an image the source referred to only by a plain relative path keeps that path, spaces included and URL escapes decoded (a web image, or a path that is absolute or leaves the document's folder, becomes a link instead, since TeX cannot fetch the one and must not read the other; in a bundle, which cannot contain such a file, the image is guarded by `\IfFileExists` so the zip compiles whether or not the file is added); charts become data tables; running headers/footers use `fancyhdr`; a title block (a heading styled `Title`, such as a Word title, and the `Author`/`Date` lines after it) is typeset with `\maketitle` where it stands (a `\titlepage` frame in beamer), printing only what the document shows; metadata fills the PDF metadata (custom properties included), and `\title`/`\author`/`\date` when there is no title block. Presentations become `beamer` frames (the slide's first heading is the frame title and a lower one under it its `\framesubtitle`, a heading between slides a `\section`, speaker notes become `\note`, and a slide taller than a frame continues on another). Run formatting (bold, italic, underline, strikeout, super/subscript, colour, a word-wrapping highlight, monospace, and sizes that differ from the body size) is carried over. Link targets are written with `\%XX` escapes, which hyperref turns back into `%`, so a link in a heading or footnote compiles. Output is deterministic. Adds no dependencies.
- **`TexGeneratorConfig`** (`texConfig`): `documentClass` (`'auto'` default, picking `beamer` for slides and `article` otherwise; or `article`/`report`/`book`/`beamer`), `standalone` (`false` emits the body only, headed by the packages, and any font setup, it needs), `bundle` (return a zip of `main.tex` plus every image as a file under `images/`, instead of the `.tex` string), `embedImages` (`true` default: a `.tex` carries its PNG and JPEG images inside it; `false` refers to `images/` files), `numberSections`, and the shared page knobs `format`, `landscape` and `margin`. The `TexGeneratorConfig` and `TexDocumentClass` types are exported, and so are `GeneratorFormatAlias` and `CanonicalFormat`, which make `ast.to('latex')`, `'markdown'` and `'txt'` type-check as the formats they name. CLI: `--to=tex`, `--texConfig.bundle`, `--texConfig.embedImages`, `--texConfig.documentClass`, and the other `--texConfig.*` flags.
- **LaTeX output is sanitized like every other sink.** Document text is escaped, link targets go through the same scheme allowlist as the DOCX/ODT generators and are percent-encoded, image paths are reduced to safe file names inside `images/`, and a code block containing its own end marker is not put in a verbatim environment, nor, in a `beamer` document, one containing a line `\end{frame}` (beamer reads a frame holding verbatim material raw up to that line, so the lines after it would run as LaTeX). Math, the one place document content is emitted as live LaTeX, must pass a check that refuses commands able to read or write files, run programs, redefine commands, build a command's name from text or end the document (`\input`, `\write18`, `\openin`, `\catcode`, `\def`, `\csname`, `\UseName`, `\enddocument`, ...), `^^` character escapes, and unbalanced braces or environments; a refused expression is written as literal text.
- **Characters the fonts lack.** A character the default fonts have no glyph for (check marks, arrows, many math symbols, dingbats, unusual spaces) gets a fallback under every engine. Under XeLaTeX and LuaLaTeX, text in a script Latin Modern lacks is set in fonts TeX Live ships: Computer Modern Unicode for Greek and Cyrillic, and Fandol, Harano Aji or UnFonts for Chinese, Japanese and Korean (whichever language the text is mostly in, the others as fallbacks) through `xeCJK` or `luatexja`, which also break lines between CJK characters; each is used only where it is installed, so a smaller installation still compiles. upLaTeX and pLaTeX set CJK text in their own Japanese fonts. A script pdfLaTeX cannot typeset (CJK, Cyrillic, emoji, ...) is shown there as a `[U+XXXX]` marker (Greek as math letters).
- **`MATH_WRITTEN_AS_TEXT`** warning code: a math expression used an unsafe command or was malformed, so LaTeX output shows it as literal text. The message names the refused commands.
- **`IMAGES_NOT_BUNDLED`** warning code: LaTeX output (without `texConfig.bundle`) references image files the `.tex` does not carry (with `texConfig.embedImages: false`, an image other than a readable PNG or JPEG, or one past the decoding limits); the message names each file and where to place it. It also names, in either mode, images the source referred to only by a relative path, whose data the source did not contain.
- **`CITATIONS_NOT_RESOLVED`** warning code: LaTeX output cites keys (`\cite{key}`) that no bibliography it holds has an entry for, so LaTeX prints `[?]` for them; the message names the keys.
- **HTML comments are preserved.** `<!-- ... -->` in Markdown used to parse as literal text, so converting Markdown to HTML showed it on the page and regenerating Markdown wrote it back escaped as `&lt;!-- ... --&gt;`. It now parses as a `comment` node marked `metadata.sourceSyntax: 'html'`, with the raw body in `text`: a block node when it stands on its own lines (it may span several, blank lines included) or an inline node within a run (it may open on one line of a paragraph and close on another). `<!-->` and `<!--->` are complete, empty comments, as in HTML and CommonMark, and a comment on its own line directly after a table row ends the table, as in GFM. It is not part of any node's text, so plain text and chunks never show it. The Markdown generator writes it back byte-for-byte. The HTML generator emits a real comment (inline ones stay in their run), or under `htmlConfig.sourceAttributes` an empty `<span data-html-comment="…">`, since an editor's DOM parser discards real comments; the HTML parser always reads that shape back. The LaTeX generator writes it as `% <!-- ... -->` lines, hidden when typeset, which the LaTeX parser reads back (moving a space that follows an inline comment in front of the `%`, where TeX keeps it). Every other output format (text, CSV, RTF, PDF, DOCX, ODT, EPUB, chunks) omits source comments rather than revealing a note the author hid. Comment text that could close a comment early (`-->`, `--!>`, a leading `>`/`->`) is neutralized on output.
- **Linked images keep their link.** `ImageMetadata` gains `link`, `linkType` and `linkTitle`, so an image that is a link (a badge, a clickable picture) carries its target. The Markdown (`[![alt](src)](target "title")`), HTML (`<a href><img></a>`, EPUB chapters too), Word (a hyperlink around a picture, or a link on the picture itself), PowerPoint (a picture's click link), ODF (`draw:a`), RTF (a picture in a `HYPERLINK` field) and LaTeX (`\href` around `\includegraphics`) parsers read it, and the Markdown, HTML, DOCX, ODT, RTF and LaTeX generators write it as they write a linked run: an internal target points at its anchor and is dropped under `ignoreInternalLinks`, and every target passes the same scheme check. A Markdown badge used to parse as garbled text, and every other linked picture lost its target.
- **Bookmark ids on more nodes.** `AdmonitionMetadata` and `BreakMetadata` gain `anchorIds`, and definition lists, terms and descriptions carry a new `DefinitionMetadata` with `anchorIds`, as paragraphs, headings, cells and code blocks do. A bookmark on an admonition, a rule or a definition list is read from HTML (`<div class="admonition" id>`, `<hr id>`, `<dl id>`, `<dt id>`, `<dd id>`) and Markdown (an `<a id>` line before it), and written back the same way.
- **`htmlParserConfig.preserveComments`** (default `false`) keeps comments found in HTML and EPUB input as the same `comment` nodes instead of dropping them. Conditional comments (`<!--[if …]>`, `<!--<![endif]-->`) are always dropped. The docs visualizer has a matching switch.
- **`TexParserConfig`** (`texParserConfig`): `today` sets what `\today` prints, in place of the date of the parse: a fixed date, so that the same file parses the same way every day, or a placeholder to find and replace later. CLI: `--texParserConfig.today`. The `TexParserConfig` type is exported.
- **`INVALID_CONFIG_VALUE`** warning code: a generator option got a value it does not accept (a `documentClass`, paper `format` or margin in `pdfConfig`/`docxConfig`/`odtConfig`/`texConfig`, `pdfConfig.engine`, `htmlConfig.standalone.styles`, a Markdown dialect preset, or a chunking `strategy`/`splitBy`/`tableSplitStrategy`), or a parser option got one (`texParserConfig.today` that is not a string, a `pdfParserConfig` budget that is negative or not a number), or a parse's `csvDelimiter` or `newlineDelimiter` cannot safely carry over to output (see Changed). The option's default is used, and the message names the option, the value and what it accepts.
- **Unrecognized generator options are reported.** `UNRECOGNIZED_CONFIG_OPTION` now covers generator configs (a typo such as `texConfig.bundel`, or a parser option passed to a generator) and a `convert()` option placed at the top level instead of under `parseConfig` or `generatorConfig`, naming where it belongs. Configuration warnings appear in a generation result's `messages` as well as reaching `onWarning`, and the CLI prints them (and `INVALID_CONTAINER_WIDTH`) without `--verbose`.
- **`FileTypeAlias`** type: the other names the `fileType` option accepts, as the matching file extensions do (`latex` and `ltx` for `tex`, the ODF template names `ott`/`ots`/`otp`/`otg`, and `zip`, parsed as whatever the archive holds), now part of its type.
- **`CommentMetadata.parentId`**: a reply (a PPTX modern comment's reply, or a classic comment threaded on another) names the comment it answers.
- **`CONTENT_PART_NOT_READ`** warning code: a chapter an EPUB's spine lists was not read (its file is missing, of a type that is not a chapter, or encrypted). A book whose chapters are all encrypted (DRM) is refused with `DOCUMENT_DECRYPTION_FAILED`, where its bytes were read as text.
- **Docs visualizer: LaTeX in and out, and an Export panel.** The visualizer accepts `.tex` files and LaTeX project `.zip`s (with a sample `.tex` that carries its image), has a LaTeX window (highlighted source, or a preview of the LaTeX parsed back with its images, with class, standalone, images-inside and numbering options, downloadable as `.tex` or as a zip with its images), and a new Export panel downloads the loaded document in every generated format (DOCX, ODT, LaTeX, EPUB, PDF, HTML, Markdown, RTF, text, CSV, chunks, AST), including the formats that have no preview window.

### Changed
- **pdf.js runs in processes of its own in Node** (`pdfParserConfig.separateProcess`, default on). A PDF of 100 KB can hold a stream that inflates to a string pdf.js turns into gigabytes before any of it reaches the parser, which ended the host with a fatal out-of-memory error no caller can catch (a worker thread's memory limit did not hold either). pdf.js now runs in separate processes, at most one per CPU (further parses wait their turn), each under `pdfParserConfig.processMemoryMb` (default 1,024): such a PDF ends its process instead, and the parse rejects with the new `PDF_PROCESS_FAILED` error. `abortSignal` stops pdf.js mid-request (it ends that parse's process, and never another parse's), and the processes end with the host. A process is kept for the next parse (it costs about a tenth of a second to start). Where no process can start, pdf.js runs in the host with the new `PDF_SEPARATE_PROCESS_UNAVAILABLE` warning, as it does with `separateProcess: false`; `abortSignal` stops it there too. The browser runs pdf.js in a Web Worker as before.
- **PDFs are read within budgets.** A form XObject can draw another many times, and pdf.js reads a form again at each use, so 2.5 KB nesting seven forms that each draw the one below ten times asked for ten million text items and ended the process out of memory (forms of shapes alone did the same through the operator list); and pdf.js drops text it places off the page, so 1.8 KB drawing one 1 MB string a few hundred times kept it busy for minutes. Text is read within `pdfParserConfig.maxTextItems` (default 20,000) plus one item per byte of the file, an item counting once more for each 64 characters it holds; the drawing operators kept (fonts, images and text colour; paths do not count) within `pdfParserConfig.maxOperators` (default 250,000) plus four per byte; and the CPU time the pdf.js process spends on the document within `pdfParserConfig.maxTimeMs` (default 5,000 ms) plus 20 ms per KB, which host load or concurrent parses do not use up (pdf.js in the host has no time limit: bound it with `abortSignal`). Past the text or time budget the page keeps the text read and the rest of the document is not read; past the operator budget, images, text colours and font styles stop and text does not; each with the new `PDF_CONTENT_LIMIT_EXCEEDED` warning, naming the budget. Annotations are held to `pdfParserConfig.maxAnnotations` (default 10,000) plus one per 32 bytes, where 58 KB of pages sharing one list of 3,000 annotations ran the process out of memory; past it the rest of the document's links and highlights are not read (`ANNOTATION_EXTRACTION_FAILED`). A destination's page is looked up once per page (500 KB of bookmarks each naming a page deep in a long tree took two minutes). The budgets take a number or its text; `Infinity` is no limit, and another value is reported with `INVALID_CONFIG_VALUE` and the default used.
- **`decompressionLimits.maxXmlElements`** (default 2,000,000): the XML elements a document's parts may hold in all, EPUB chapters included. Reading XML takes several hundred bytes of memory per element, so 32 KB of zip holding 8 million empty elements filled a 4 GB heap, far below `maxUncompressedBytes`. XLSX sheets and shared strings are read without building elements (a rich run counts one, eight plain strings one). Past the limit the parse rejects with the new `XML_ELEMENT_LIMIT_EXCEEDED` error code. Comments, CDATA sections and processing instructions count as elements (each is a node, and the text between them another), and a DOCX chunk counts its lines, RTF groups and control words, or MHT parts and header lines before it is read. The HTML reader joins text that markup read as nothing (a stray end tag, a comment it does not keep) splits, where each piece was a node of its own.
- **`decompressionLimits.maxTableCells` bounds XLSX too.** An XLSX sheet is read without building XML elements, so neither limit bounded it, and 854 KB of zip holding 16 million cells ran the process out of memory. A workbook now yields at most `maxTableCells` cells (default 1,000,000) plus one per byte of the file, as an ODF document does (whose limit gains the same allowance), with the `TABLE_CELL_LIMIT_EXCEEDED` warning: a large workbook is read whole, since a real one holds under half a cell per byte of its zip.
- **`decompressionLimits.maxRepeatedContent`** (default 16,777,216): the content one document repeats by reference, in all. A document can state something once and use it many times: an ODF cell or row repeated with `table:number-columns-repeated` / `table:number-rows-repeated` (in a sheet or a chart's table), an XLSX shared string shown in many cells, a style's font or colour given to every run using it, a relationship's link target given to every hyperlink naming it, a comment author named by id, a chart's text or a picture's recognized text given to every frame showing it, and in LaTeX a heading's title given to every `\nameref`, a theorem kind's title to every theorem and beamer's title block to every `\maketitle`. The limit grows by 16 characters per byte of the document, so a workbook showing one 200-character note in 150,000 cells keeps it in every cell. The AST shares the value, but every writer writes it at each use: 700 bytes of ODS asking for 100,000 copies of a 2,000-span cell made 200 MB of text (and the parse walked each copy, 6 seconds), 2.7 KB of XLSX showing one 1 MB string in 400 cells made 400 MB of CSV (a rich string of 20,000 runs in 50,000 cells ended the parse out of memory), 1.7 KB of DOCX giving one 64 KB font or link target to 2,000 runs made 131 MB of HTML, and a 1.3 KB chart repeating one 100 KB value 2,500 times made 250 MB of text. Each use after the first is charged what it weighs (characters, plus 16 for each node a repeated cell holds, and the formatting values of a rich string's runs, which cells showing it share: one run of a 64 KB font shown in 7,500 cells made 492 MB of HTML) past 64, so short values repeat freely; `maxTableCells` counts cells, not what they hold. Past the limit, with the new `REPEATED_CONTENT_LIMIT_EXCEEDED` warning, the remaining repeats of a content-bearing ODF cell are not made (later cells keep their row and column numbers), an XLSX cell, chart value, frame or reference shows the start of its text, and a node repeating a long style value or link goes without it. An attachment name longer than 128 characters (a relationship target shown at every picture using it) is shortened, alike on the attachment and on every node naming it; HTML writes a chart's data once, where every chart showing it carried a copy; and a parser finds an attachment through an index, where each node searched them all.
- **`decompressionLimits.maxRawContentLength`** (default 64M characters): the `rawContent` one document's nodes carry in all, with `includeRawContent`. A node's raw content holds the markup of everything nested in it, so nested tables and text boxes repeated each level's markup at every level above it (270 KB of ODT took 5 seconds and 900 MB), and a repeated ODF cell or row serialized its markup again for every copy. Past the limit the remaining nodes carry no `rawContent`, with the new `RAW_CONTENT_LIMIT_EXCEEDED` warning; a repeated cell's markup is serialized once.
- **Tables are written within a grid budget.** Every writer lays out a sheet's (or table's) cells by the row and column each carries, filling the grid between them, so a small spreadsheet with one cell at `XFD1048576`, a few thousand cells along a diagonal, a span of a billion columns, or many sheets each holding a large empty grid made output grow with the grids, not the cells: HTML and EPUB ran out of memory, and CSV and Markdown output grew with the square of the cells. The grids of a document's sheets and tables may fill 1,000,000 empty positions in all, plus 16 per byte of the document parsed (a sparse sheet of 3,000 rows with values in its first and 400th columns is written as it stands); one holding more than remain is laid out closer before any writer fills it (the rows and columns no cell starts or ends in are left out, and if that is not enough, each row's cells follow one another), and a writer pads short rows to their table's width, and fills a sparse sheet's empty rows, within the same budget; each is reported with the new `TABLE_GRID_LIMIT_EXCEEDED` warning. DOCX and ODT output push a cell right past every earlier row's vertical merge still open, so 1.5 KB of rows each spanning a thousand below made a staircase of 500 MB of DOCX (and each column step scanned every open merge); the budget and both writers share one layout. A LaTeX column band after the first holds only the rows with something in its columns, and cells past LaTeX's thousand-column limit are reported (`CONTENT_NOT_REPRESENTABLE`). Plain text lines a column up to at most 256 characters within 16 million spaces per document plus 16 per byte (one 100 KB cell over 2,000 rows made 200 MB), and a PDF page it lays out (`textConfig.preserveLayout`) at most 1,000 columns wide within the same spaces (a 2 KB PDF page 200 million points wide, a run at each edge, made 389 MB of text); past it, cells and runs are set off by one space, reported with `TABLE_GRID_LIMIT_EXCEEDED`. DOCX, ODT and LaTeX build a chart's data table within the grid budget and at most 100,000 cells (`CONTENT_NOT_REPRESENTABLE` past it), where a 9.6 KB PPTX of 3,000 labels by 3,000 series ran them out of memory.
- **Pictures cannot multiply output past what memory holds.** HTML (standalone included), Markdown and RTF write a picture's data at every place showing it, so a small document showing one large picture many times failed after allocating gigabytes; the pictures one document writes inline now stop at 128 MB in all, the rest written as name references (HTML, Markdown) or their alt text (RTF) with an `IMAGE_NOT_INLINED` warning. EPUB packages each picture as one file every `<img>` points at, where it inlined and re-extracted it per reference. RTF encoded a picture a character at a time, and one of 40 MB (a 42 KB DOCX) ran out of memory.
- **A document or AST nested past the stack is the typed error.** Every generator failed with the engine's own `RangeError`, and the Office and ODF parsers failed on XML nested thousands deep (hyperlinks in hyperlinks) with a generic `FILE_CORRUPTED` error; both are now the `MAX_NESTING_DEPTH_EXCEEDED` error. Output past what a string holds is the new `OUTPUT_TOO_LARGE` error, not the engine's `RangeError`, and so is an AST built in code whose nodes, records, lists or long strings are shared along more paths than a writer follows: a node two parents share is written under each, so nodes each holding the next twice doubled a writer's work per level (see Fixed). A parsed document stays inside that bound: the bound grows with what the AST holds, a record many nodes share (a spreadsheet's style, given to every cell) weighs at each later holder only what it weighs past what a node's own record may, and a document's own `config.decompressionLimits.maxRepeatedContent` (a number, up to 1 GiB) widens it.
- **A chunk's heading is not repeated whole.** Every chunk under a heading carried it in `metadata.closestHeading` (and a sheet name in `sheetName`), so one 1 MB heading over a thousand chunks made a gigabyte of chunk metadata; past 256 characters each holds the start and `…`.
- **A network path in a link or picture cannot reach a file share.** HTML, EPUB and Markdown output kept `//host/path` and `\\host\share` targets, which a page opened from disk (an EPUB in its reader, a saved HTML file) resolves to `file://host/...`: on Windows an SMB fetch that sends the user's credentials, for a picture with no click. `//host/path` is now written as `https://host/path`, what it means on the web, and a backslash form is refused, as DOCX, ODT and RTF output already refused both (and LaTeX output does). A preserved `srcset` or `ping` attribute is checked per URL.
- **CSV guards full-width formula characters and quotes more separators.** A cell starting with a full-width `＝`, `＋`, `－` or `＠`, which spreadsheets read as `=`, `+`, `-` and `@`, is guarded like the ASCII ones, and a cell holding `;` or a tab is quoted, so a spreadsheet splitting on either reads the cell whole. A parse's `csvDelimiter` carries over to CSV output (unless `csvConfig.columnDelimiter` is set) when it is at most 16 characters, holds no line break or quote and does not start with `=`, `+`, `-` or `@` (a row starting with an empty cell would start a formula); another is reported with `INVALID_CONFIG_VALUE` and `,` used, and the same holds for a `newlineDelimiter` past 16 characters in text output.
- **XLSX booleans read as shown.** A boolean cell read as `1` or `0`; it reads `TRUE` or `FALSE`, as Excel shows it and as ODS cells read.
- **An EPUB's pictures are named after their files, once each.** Each picture a chapter showed became an attachment named `image_1.jpeg`, `image_2.png`, ... from 1 in every chapter, so two chapters' pictures shared a name, and a picture shown twice was two attachments. A picture is now one attachment, named after its file (numbered when two files share a name), which every `<img>` showing it names, and a chapter's own inline pictures are named apart from the others'. A chapter the spine lists more than once (which EPUB does not allow) is read once.
- **DOCX line breaks and tabs are text.** Without `includeBreakNodes`, a line break the author typed (`w:br`, `w:cr`) was dropped and a tab never read, so words ran together in every output ("Line oneLine two", a table of contents' "Tables2"). A typed line break is now always a `break` node (`textWrapping` or `carriageReturn`), as an HTML `<br>` always was, and a tab a `\t` in the text; ODF's `text:line-break` is the same `break` node (it was a `\n` text node Markdown, HTML, RTF and DOCX output ran together). `includeBreakNodes` still gates page, column and last-rendered-page breaks, which are layout.

### Fixed
- **XLSX cells showing the same rich-text string keep their own style.** Each cell's background, alignment, font and size were written onto the string's shared runs, so every cell showing the string took the style of the last one read.
- **HTML character references decode correctly, in text and attributes.** The HTML parser (which also reads EPUB chapters) decoded only `&amp;`, `&lt;`, `&gt;`, `&quot;`, `&#39;` and `&nbsp;`, so `&rsquo;`, `&copy;`, `&eacute;` or `&#8217;` came through as literal text; it decoded `&amp;` before `&quot;`, so escaped literal text like `&amp;quot;` came back as `"`; and most attribute values were not decoded at all, so a link to `?a=1&amp;b=2` pointed at that literal text (gaining another `&amp;` on each HTML round trip) and alt text and titles kept their escapes. Every numeric reference (one from 0x80 to 0x9F as the Windows-1252 character browsers read it as, so `&#146;` is `’`) and HTML 4's named references now decode, in one pass (the exact inverse of how the generators escape), in text and in every attribute value. Attribute values are decoded before a URL's scheme is checked, so `java&#115;cript:` is refused.
- **Markdown text that looks like an internal placeholder no longer breaks parsing.** A literal `__CODE_BLOCK_0__` (or a similar `__MATH_BLOCK_n__`/`__ADMONITION_n__` line) was taken for a lifted block and crashed the parser with `"undefined" is not valid JSON`. Lifted blocks now use placeholders built from characters the document does not contain, so such text is ordinary Markdown.
- **Markdown keeps text that looks like Markdown.** Text holding Markdown's own characters was written as it was, so it read back as markup: `2*3*4` turned italic, `[1](x)` a link, `$5-$10` math, a paragraph starting `# ` a heading, and literal `&quot;` lost one level of escaping on every save (`&amp;quot;` became `&quot;`, then `"`; inside emphasis or link text, both at once). The generator now escapes each character where it would be markup: `` ` ``, `*`, `[`, `]`, `~`, `$` and a run of `=` get a backslash, as do `_` (except inside a word, so `snake_case` stays as it is) and a backslash that would escape what follows (one ending a bold or italic run too, which escaped its closing delimiter); a heading's `#`, a quote's `>`, a list item's `-`, `+` or `1.`, a line of `-` or `=`, and a leading `:` get one only where they start a line; and the `&` of anything that reads as a character reference is written `&amp;`. Code and math stay as written. Alt text keeps its brackets (they were removed) and, like titles, its backslashes. The parser decodes references and backslash escapes in image alt text, link and image titles, link targets and embed labels, as CommonMark renderers do (it kept them verbatim). A title containing `"` is written with `&quot;`: written as `\"`, it could not be read back and turned the link into a broken URL. A reference named like an object property (`&constructor;`) stays text instead of becoming JavaScript source.
- **Bold italic, underscores and emphasis spacing follow CommonMark.** `***text***` and `___text___` parse as bold and italic; they came out bold with a stray `*`, so every bold-italic run the generator wrote broke on the next read. An underscore inside a word (`snake_case_name`) no longer starts emphasis: `_` and `__` emphasis starts and ends at a word's edge. The generator writes the whitespace at the edge of an emphasized run outside its delimiters (`**Note:** body`, not `**Note: **body`, which a renderer shows with its asterisks), and with `emphasisMarker: 'underscore'` writes emphasis inside a word or next to other emphasis, where `_` cannot mark it, with `*`. A `*`, `**`, `~~` or `==` followed by whitespace opens nothing, so `5 * 3 * 2`, `a ** b` and `if a == b` stay text (they read as emphasis or a highlight, which the generator then wrote as such), and a delimiter escaped just before the closing one (`**Important\***`) is text rather than part of the closer. Emphasis inside emphasis pairs as CommonMark pairs it (`*a **b** c*` is italic with bold inside; it lost its bold, or left `* c*` as text), and delimiters CommonMark leaves unpaired are then paired as earlier versions paired them (they wrote `**Note: **body`, and such files keep their bold); where a run cannot be marked with delimiters, the generator writes `<em>`/`<strong>` under `fallbackToHtml.textFormatting`.
- **Consecutive line breaks stay in their paragraph.** A second hard break in a row was written as a line of two spaces, which is a blank line, so the paragraph split in two when read back (by any CommonMark renderer too). A hard break that starts a line is now written as a backslash.
- **Code spans keep their content.** A code span is read as CommonMark reads it: a backtick run is closed by the next run of the same length (a shorter run inside a longer one no longer opened a span), and the single space padding each end is not part of the code, so `` `x` ``, written as ``` `` `x` `` ```, no longer gains two spaces on each save. A span that begins and ends with a space is padded when written, so its spaces survive.
- **Links, images and tables keep brackets, parentheses and pipes.** Link text may hold brackets, nested up to three deep or escaped (a link used to end at the first `](`, so `see [1] and [2](u)` linked the wrong text), and a link or image title may hold parentheses (`[x](u "Figure 1 (a)")` ended at its first `)`). A `|` in a table cell, in text or code, reads back as a `|` instead of splitting the cell, and a code span in a cell holding `\|` keeps its backslash.
- **Math holding a `$$` line reads back as written.** The generator indents a math line that is exactly `$$`, which would end the block, and the parser now takes that space off again; it kept it, so the line gained a space on every save.
- **A Markdown link cannot turn into `javascript:` in a renderer.** A link target spelling its scheme with a character reference (`javascript&colon;alert(1)`, from HTML or Markdown input) passed the scheme check as a relative path, and a renderer that decodes references in link targets read it as `javascript:`. Such an `&` is now written `&amp;`, so a renderer reads the target exactly as checked.
- **MDX components in code are kept.** Stripping MDX components (`<Callout>`, `<Chart />`) also removed them from fenced code blocks and code spans, so a code sample showing a React component lost it. Code is now left as written.
- **Fenced code blocks are read as CommonMark reads them.** A fence whose info string was not a single word (```` ```c++ ````, ```` ```objective-c ````, ```` ```js title="a.js" ````, ```` ``` js ````), or that was indented, was not recognized, so its code became ordinary text and was reflowed on the next save; a fenced block inside a list item, quote or admonition was flattened the same way, and one indented under a list item by the four spaces editors write was read as indented code, fence lines included. A fence may now be indented up to three spaces past the start of its line, or of the list item's text. These are code blocks with their language: inside an admonition, and after the list item or between the quote's paragraphs (which cannot hold a block).
- **A one-line code block stays a code block.** A code block of one line without a language was written to Markdown as inline code and to HTML inside a `<span>`, so it came back as inline code. It is now a fenced block and a `<pre>` (in a Markdown pipe-table cell, where a fence cannot go, it stays inline code).
- **Markdown keeps no-break and other Unicode spaces.** Only spaces, tabs and line endings are whitespace to Markdown, but the parser and generator also trimmed a no-break space (U+00A0), an em space and the other Unicode spaces from the edges of paragraphs, headings, list items, quotes, table cells and footnotes, and read one as the space after a heading's `#`, a list marker or a quote's `>`. A document's no-break spaces and em-space indents were lost on the first save, and a line starting with a no-break space and `- ` was read as a list item. They are now text.
- **Markdown from any format reads back as the same Markdown.** Saving a document from Word, PowerPoint, Excel, ODF, RTF, PDF, HTML or LaTeX as Markdown, then reading that Markdown and saving it again, gave different Markdown. Spaces and tabs at the edges of a paragraph or heading were written, though a reader drops them (and four at the start of a paragraph made it a code block); a picture followed by a heading on a page or slide shared its line, so the heading came back as text; a paragraph right after a list item on a slide read as part of the item; an endnote standing on a PDF page was written where it stood, after whatever came before it; a table row's missing cell was written as a space; a picture's anchors were put on a line of their own, which inside a paragraph is a line break; and runs differing only in a font, size or colour that Markdown does not write stayed separate spans, so a link whose space was in the link colour became `[ ](url)[text](url)`. Edge spaces are no longer written, blocks in pages, slides and cells are separated as top-level blocks are, a standing endnote is written with the other definitions at the end, a missing cell is empty, a picture's anchors go on its line, and runs Markdown writes the same way are one span. The test documents of every input format now save byte-identical Markdown twice.
- **Plain-text and RTF output, ODF table cells and long PDF paragraphs take linear time.** Plain-text output removed the line breaks at its ends by scanning every run of line breaks inside it, so a document holding a long run (a code block of 200,000 blank lines) took about a minute; RTF output looked up each run's colour by scanning the colour table, so text in many distinct colours took seconds. Reading an ODF table cell tested the end of the cell's text so far after each paragraph, and reading a PDF re-read a paragraph's text at each hyphenated line join and a page's rotated text at each run, so the time grew with the square of a cell's or paragraph's length: a cell of 160,000 paragraphs took 17 seconds. Each now takes time linear in its input (that cell, under a second).
- **Generated Markdown separates blocks with one blank line.** Display math, fenced code, tables, slide, sheet and page rules, embeds, page breaks and slide notes each added a separator of their own, so documents had runs of two or three blank lines (and whitespace-only lines from EPUB); abbreviation definitions were preceded by three. Every run of blank lines outside code and math blocks is now one.
- **Display math written inside a Markdown paragraph is read as math.** `Inline $$a+b$$ end` used to parse as a literal `$`, inline math and another `$`. A `$$...$$` inside a paragraph is now display math, as KaTeX, MathJax, GitLab and Pandoc render it: the paragraph is split around the equation, which becomes a block math node and regenerates as a `$$` block. In a heading, list item, table cell, quote or footnote, or inside emphasis, where a block cannot go, it is inline math. `\$` escapes and single-dollar math are unchanged.
- **HTML whitespace is read as a browser shows it.** The HTML parser (which also reads EPUB chapters) dropped the whitespace between two inline elements, so `<code>a</code> <code>b</code>` became one code span and `<b>A</b> <i>B</i>` read "AB"; it kept the spaces around a `<br>` and at the edges of a paragraph or cell; and it read `&nbsp;` as an ordinary space. Whitespace now collapses as in a browser, across element boundaries too, and a no-break space is kept (a paragraph holding only one is still an empty paragraph).
- **A table written as HTML in Markdown keeps its cells' content.** A table the Markdown generator writes as HTML (one with merged cells, or any table under the `commonmark` preset) dropped its cells' link targets, line breaks, code formatting, math and pictures, and read back with only the plain text of its cells, some of it misread as Markdown (`2*3*4` turned italic) and a nested table garbled. Its cells are now written as the HTML generator writes them, and the Markdown parser reads an HTML table with the HTML parser, as a renderer shows it: formatting, links, line breaks, code, math, pictures, footnote references, nested tables and any text beside the table in its block survive, and the table is stable over saves.
- **Errors reach the `onWarning` of the call that raised them.** Some errors were raised without the caller's config, so they were printed to the console even when `onWarning` was set, and never reached it: HTML nested too deeply, an unsupported output format, an invalid style map (`INVALID_STYLE_MAPPING`, `INVALID_SELECTOR`, `INVALID_OUTPUT_MAPPING`) and `FEATURE_NOT_SUPPORTED_IN_BROWSER`. A PDF generation failure went to the `onWarning` of the parse that made the AST rather than of `to()`/`generate()` (and to the console for an AST built by hand). Each now goes to the `onWarning` given to the call.
- **Markdown blocks are read as CommonMark reads them.** A thematic break may have spaces (`* * *`, `- - -`, `_ _ _`) and may follow a paragraph line (`***`); `* * *` and `- - -` read as list items before. A setext underline in the middle of a block (`text\n---\nmore`) makes a heading, and a rule after a quote is a rule (it made a heading of the quote, and still did when the quote was indented); a `=` or `-` line continuing a quote's paragraph is text (`> quote\n===` made a heading), and a quote marker may be indented up to three spaces on any of its lines; a line of spaces is a blank line; a marker alone (`-`) is an empty list item; a change of marker (`-` to `1.`, or `-` to `*`) starts a new list (the items joined the list before it); a tab after a marker reaches the next tab stop, so a paragraph indented by a tab under the item is the item's; an ordered item not starting at 1 does not interrupt a paragraph; a row of `-` cells after a table's delimiter row is a row (it was dropped); a link reference definition cannot interrupt a paragraph, and its label ends at the first unescaped `]`; four columns of indentation make a code block, of a line starting `#` or `-` too (it read as a heading or list), and the block runs on across blank lines (it split into one code block per paragraph of it) but ends at its last line of code, but a block indented to a list item's content column after the item is the item's content, a paragraph or table after the list as the AST's one-line items hold it (four spaces after `- item` or `1. item` read as a code block, where every renderer shows a paragraph or table); an HTML table that a blank line runs through is one table (what followed the blank line was escaped text), Markdown between blank lines in its cells, the GitHub way (`<td>`, a blank line, `**text**`, a blank line, `</td>`), is read as Markdown into its cell, and `<table>` in a code span or a sentence is text (it was read as a table, and the text around it lost); a `---` starting the document and followed by a blank line is a rule, not front matter (the text to the next rule was lost, as in a document starting with a page, slide or sheet boundary), and a `---` block is front matter only when its lines read as YAML; `>` needs no space after it; `#` alone is an empty heading, and `## {#id}` one with an id. A quote, and a GitHub admonition, hold blocks: a list, heading, table or code block in one was read as a line of its text, which the next save escaped (`> \- a`). A definition list may hold several terms. A footnote may hold paragraphs and a list, continued across blank lines as Pandoc and the generator write them, and may refer to another footnote, whose definition Markdown output dropped; a footnote referring to itself no longer overflows the stack.
- **Markdown inline content is read as CommonMark reads it.** A paragraph's inline content is read as one text across its lines, so a link, emphasis, code span or inline HTML may span a line end (`[official\ndocumentation](url)` and `*a long\nphrase*` read as text, the tags of a README's multi-line `<a href><img></a>` logo stayed visible, and a code span wrapped across two lines read as two backticks of text); a reference definition's target may stand on the next line, and its title reaches the link (it was dropped); a link target may hold parentheses (`https://en.wikipedia.org/wiki/Foo_(bar)` was cut at the first `)`); a link with no text keeps its target; an autolink's character references are decoded in its text and target alike (`<https://e.com/?a=1&amp;b=2>` linked to the literal `&amp;`), and an address in angle brackets (`<me@example.com>`) is a mail link (it was text); a backslash ending a paragraph is text, and a no-break space starting a list item is content.
- **Markdown output keeps structure a reader would lose.** An empty heading was written with an empty `{#}` id that grew on every save; a bookmark on an empty paragraph was dropped, breaking links to it; a rule inside a paragraph was written as text (`a---b`); code and math blocks in a list item, table cell or definition were written as fences joined by `<br>`, read back as one code span holding the tags (each line is now a code span, block math inline math, and a rule there is a line break); a list item or definition term starting with `#`, `-` or `1.` became a heading or list in renderers; a list starting deeper than its first level, or nesting two levels at once, was indented into a code block; a definition term holding a paragraph (HTML's `<dt><p>`) ended the list; a heading or quote in a list item, table cell or definition was written with its marker escaped (`: \# h`, `- a<br>\> q`), which read back as text holding the marker (its text is written now, an admonition's after its bold label, a definition list's as its lines, and an embed there is a link); a line break between blocks or just before a rule wrote a stray `\` or trailing spaces, which changed on the next save, as did a space ending the text before a code block or rule in a paragraph. Front matter is written with `<` as `\u003c`, so a tag in a title is text in a renderer that shows front matter as a paragraph, and quoted values are read with their escapes decoded (`\"`, `\\` stayed as written).
- **A node of a type the AST does not define is written as its content.** An AST holding a node type outside `OfficeContentNodeType` (built by hand, or by a newer version) made the HTML and EPUB generators fail with a `TypeError`, the Markdown and RTF generators write the word `undefined` in its place, and CSV (inside a table) leave the node out. Every generator now writes its children or text, with its link, formatting and notes: as a paragraph among blocks, as a cell in a row, and as a row in a table. Such nodes nested in each other are written in time linear in their content, and one that notes share is written once.
- **Sheets keep their content in HTML and Markdown output.** The Markdown generator wrote a sheet with merged cells, and every sheet under a dialect without pipe tables (`commonmark`), as nothing at all: the HTML table it falls back to was written for tables only. Content among a sheet's rows that is not a row (a CSV comment line, a picture in a spreadsheet) became an empty row, its content gone; it is now a row of one cell where it stands. The HTML generator (and EPUB, which uses it) placed a sheet's cells by the row and column a spreadsheet parser records on each one, so a sheet built by hand, whose cells carry none, was written as an empty grid; such cells now take the next free place in reading order. Reading a sheet this library wrote as HTML no longer takes the row numbers and column letters drawn around it for cells of the table.
- **RTF output keeps code, equations and definition lists.** Code blocks and equations were dropped from RTF output; a code block is now written in a monospace font with its lines kept, and an equation as its LaTeX source (with a `CONTENT_NOT_REPRESENTABLE` warning, as DOCX gives). A definition list's terms and descriptions ran together into the paragraph after them; each is now a paragraph, the term bold and the description indented. A CSV comment line is written as a paragraph (it was dropped); a source comment (`<!-- ... -->`) stays out of RTF as before. A picture RTF cannot carry (one by URL, or whose attachment is missing) was dropped; it is a link on its alt text to where it links or to the picture, as in DOCX, else its alt or recognized text. A picture among the blocks is a paragraph of its own (it ran into the text after it).
- **HTML code blocks keep highlighted code and line breaks.** A `<pre>` block was read from its direct text, or its first `<code>`'s, only, so the tokens a syntax highlighter wraps in `<span>`s were dropped (`<span>let</span> x` read as ` x`), as were a prompt before the `<code>` (`<span>$ </span>`) and a second `<code>`, and a `<br>` in it ran the lines together. The whole block is read, without the line break right after `<pre>`, which HTML does not show.
- **HTML captions, admonitions and footnotes read back as written.** A `<figcaption>` holding a line break or inline math is a paragraph of its own beside its picture (it merged into the picture's line). An admonition takes its type from a class naming one (`class="admonition warning"`) when it has no `data-type`. A footnote read from HTML kept the space before its back-link, one more on every save, and with `preserveXmlWhitespace` the whitespace between two blocks became an empty paragraph, one more on every save.
- **Plain-text output puts definitions and blocks in items on their own lines.** A definition list's terms and descriptions, and an admonition's text, ran into each other and into the paragraph after them, and a block in a list item (a definition list, a table) ran into the item's text (`- itemT`).
- **The native PDF engine draws pictures in paragraphs.** It drew a picture only when it stood among the blocks, so every picture inside a paragraph (where Word, ODF and Markdown put them) was missing from the PDF. A picture in a paragraph is now drawn where it stands, between the lines of text around it; one in a list item, heading or footnote, which the engine lays out as text, is its alt or recognized text, with a `CONTENT_NOT_REPRESENTABLE` warning as for a picture in a table cell. An embed (a video, a framed page) was dropped too; its URL is written, with its label.
- **Embeds keep their URL.** An embed naming no `embedType` (built by hand), or a YouTube one given by its URL alone, was written by the HTML and Markdown generators as an empty YouTube block, its URL lost; it is now read from what it carries (a video id, else a YouTube URL, else any URL is a framed page), and DOCX, ODT, RTF and PDF output link a video given by its id alone.
- **Chunks hold a table of one row.** Under the default `tableSplitStrategy: 'row'`, a table's first row is the header repeated in each chunk of its other rows, so a table of one row made no chunk and its text reached none.
- **HTML with omitted end tags parses as a browser reads it.** HTML allows leaving out `</p>`, `</li>`, `</td>`, `</tr>` and similar end tags, but the HTML parser (which also reads EPUB chapters) nested each such element inside the previous one: unclosed list items became items inside items, text after a block that closed a paragraph was lost, and a page of a few hundred unclosed paragraphs was refused as nested too deeply. An element now ends where its end tag is implied, a cell's or row's within its own table, and the reader builds its tree as a browser does: formatting open at an implied paragraph end carries into the next paragraph, a heading does not nest in a heading, `textarea` and `title` hold text, `noscript` and `template` show nothing, content after `</body>` is kept, a table's caption and content misplaced in it come before it, and a comment among a table's rows or a list's items no longer splits it. Markup that really is nested too deeply is refused with the `MAX_NESTING_DEPTH_EXCEEDED` error before anything can run out of stack on it (it failed with a stack overflow instead).
- **Inline HTML written directly in the body is one paragraph.** Text and inline elements directly in `<body>` (or in an HTML fragment) became a paragraph each: `Hello <b>world</b>!` was three paragraphs, and the space between two inline elements was lost. A run of inline content between blocks is now one paragraph, as a browser shows it, a picture beside text included (it split the text in three); a rule (`<hr>`) stays a block.
- **Nested HTML links and abbreviations read as a browser shows them.** A link started inside a link ends the first, as a browser ends it (the text of both took the outer link); where a link can hold another (across a table cell or an object), text follows the innermost one, as a click does. Text inside nested `<abbr>` elements takes the innermost title, the one a reader sees.
- **HTML output keeps blocks out of paragraphs.** A code block or display equation inside a paragraph (from HTML input, or an ODT display equation), and a rule or page break in one (a Word page break sits in its paragraph), were written as a `<pre>`, `<div>` or `<hr>` inside the `<p>`, which HTML does not allow: a browser splits the paragraph there, and an EPUB fails validation. The paragraph is now written around it (a quoted one keeps its `<blockquote>`, and its ids go before a block it starts with), and a picture in a paragraph is written as an inline `<img>` (its block markup, with the caption holding its file name, split the paragraph the same way). Reading HTML this library wrote no longer turns that file-name caption into a paragraph of text on every save; a `<figcaption>` or any other caption stays a block of its own, and one holding paragraphs keeps them (they were nested in a paragraph). Nothing is written between a picture or inline equation in a paragraph and the text after it: the blank line that was read back as a space before the next word or punctuation.
- **Bookmarks survive HTML and Markdown.** A node with several bookmarks is written to HTML with its first id on the element and the rest as empty `<a id>` anchors before it, which the HTML parser dropped, so each save lost them (the `_Toc` targets of a Word table of contents among them, whose links then went nowhere in Markdown output). An empty anchor is now read as an id of the element it stands before, or of the paragraph, heading, item, cell, note or admonition holding it, or of the picture right after it. The ids of table cells, rules, definition lists, admonitions, quotes and equations were not read either, nor that of an embedded picture or of a `<div>` read through for the blocks it holds (where the generator puts a picture's id, and a sheet's), and a picture has its id written on its `<img>` (on the wrapper of one among the blocks, its ids swapped places on every save). A sheet's own ids are written beside the id its tab links to (the first was dropped, and that id written twice), and a footnote's at its start, in HTML and Markdown. In Markdown an `<a id>` inside a line was escaped into visible text on the next save (the id the generator writes before a picture in a paragraph, and one in a table cell, among them): it is read the same way, and a bookmark before a code block, rule, admonition or definition list stays that block's rather than moving to the next paragraph. The ids of what a list item, table cell or definition holds, and of inline math, are written at the start of its line, where a reader gives them, and the ids in a table the Markdown generator writes as HTML (merged cells, or the `commonmark` preset) are written in it (they were left out). Heading ids are GitHub's in every writer: they keep the letters of every script (`#überblick`, `#введение`), and HTML's, like the others', leave punctuation out rather than making it a hyphen (`version-20` for "Version 2.0", which HTML wrote `version-2-0`, so a link written for the Markdown heading missed it). HTML gave a heading in another script no id, and a Markdown link to one lost its target on saving (`#berblick`). Two headings of the same text get ids numbered as GitHub numbers them (`intro`, `intro-1`). A heading read from HTML was written to HTML with `id=""`, as its generated id came only from text the node itself carried (DOCX and ODT output gave it no bookmark); it comes from the heading's text now, and a heading whose text slugifies to nothing gets no generated id. An id that slugifies to nothing was written to Markdown as `<a id="">`, read back as text, and one a heading carried twice was written twice.
- **A Markdown embed label cannot write markup.** An embed's label (from HTML's `data-embed-label`, a `::youtube[label]` directive or an AST) was written raw into the link text of the `link` and `thumbnail` embed forms and into a directive's label, so a tag or a `]` in it reached the output. It is now escaped as text, and read back decoded, as is `data-embed-label` from the generator's HTML form (which kept its escapes).
- **An ODF picture that is a link is no longer dropped.** A frame inside `draw:a` in a text document (a clickable picture) was skipped, picture and all.
- **A Markdown link within the document is internal.** A link to `#id` was marked external, as no other parser marks it, so `ignoreInternalLinks` kept it, HTML output opened it in a new tab, and regenerated Markdown pointed it at the id as written instead of the id written for its target, a broken link wherever ids are generated.
- **The document language reaches HTML, EPUB and PDF output.** HTML output always declared `lang="en"`, EPUB read the language only from `nativeProperties.language`, and the native PDF engine wrote no `/Lang`. All three now write `metadata.language`, where parsers put it (the EPUB parser now does too), falling back to `nativeProperties.language`.
- **A parse cancelled while OCR runs rejects.** With `ocr: true`, an `abortSignal` (or `ocrConfig.abortSignal`) that fired while an image was being recognized was taken for a failed recognition, so a DOCX, PPTX or ODF parse (and at times others) resolved without the images' text, with an `OCR_FAILED` warning for each. A parse whose signal fires before it finishes now always rejects with an `AbortError`; an OCR timeout is still an `OCR_FAILED` warning.
- **Stopping OCR mid-image no longer crashes Node or hangs.** A cancellation or `terminateOcr()` that landed just as an image was handed to an OCR worker terminated the worker before Tesseract had sent it the job, and the rejection Tesseract then raised had nothing to catch it, which ends a Node process; a worker is now stopped only once it has the job (or, mid re-initialization, once that settles or its load timeout passes, so a language download that never finishes cannot hold `terminateOcr()` indefinitely). `terminateOcr()` during a parse fails the images still being recognized (an `OCR_FAILED` warning carrying the new `OCR_TERMINATED` error code) instead of leaving the parse waiting. A cancelled recognition no longer leaves its 30-second timeout running, which kept the process alive; and a recognition taking longer than `ocrConfig.timeout.autoTerminate` is no longer cut short by the idle timer.
- **A PDF attachment is typed `application/pdf`.** Attachment type detection did not know PDF, so a PDF (a LaTeX project's figure, or a PDF embedded in a document) came out as `application/octet-stream`.
- **`convert()` lists each warning once.** A generation warning was also collected into the AST's warnings, which `convert()` put in front of the generator's own, so every generator warning appeared twice in `messages`.
- **A decompression limit reached while identifying an archive is reported as that limit.** For an input identified by its contents (a buffer, or a file named `.zip`), exceeding `decompressionLimits` while detecting the format made the parse fail as an unsupported format instead of with the limit error.
- **Raw HTML in Markdown is read as a renderer shows it.** HTML written in Markdown was text, its tags escaped into view on the first save, so a README's centred logo (`<p align="center"><img ...></p>`), a `<details>` block or `Press <kbd>Ctrl</kbd>` became visible markup in every renderer. An HTML block (a line starting with a block-level tag such as `<p>`, `<div>`, `<details>`, `<h1>` or `<center>`, or a `<pre>` closed in the block, running to the blank line) is now read with the HTML parser, as HTML tables already were: a centred paragraph or heading, a picture, a code block, the text of `<details>`. An inline element is its formatting (`<b>`/`<strong>`, `<i>`/`<em>`, `<s>`/`<del>`, `<u>`/`<ins>`, `<sub>`, `<sup>`, `<mark>`), its code (`<code>`, `<kbd>`, `<samp>`), a link (`<a href>`), an abbreviation (`<abbr title>`), a quotation (`<q>`) or a picture (`<img>`, with its width and alignment), with the Markdown inside it read too; an element never closed, or one not among these, stays text. A comment in an HTML block or table is kept, as Markdown's are (it was dropped). An HTML picture's `width` attribute (`<img width="200">`) is read too; only `data-width` and a style width were.
- **A note in a note's text is written.** HTML output and the native PDF engine left a note referred to only from another note's text out of the notes.
- **Chunks hold pictures' alt text, and a table cell's pictures and notes.** A picture's alt text reached no chunk; it is `[Image: alt]`, as plain text writes it (with its recognized text as before), unless `includeImages` is `'none'` or `'ocr-text-only'`. A table row's cells lost their pictures and notes, and a cell of several formatted runs was split into words at each run. A note in a table's data row (under the default `row` strategy) was in no chunk, and math in a line of text broke the line before it.
- **Table spans are bounded.** A DOCX `gridSpan`, an ODF cell's spanned columns and rows, and an HTML `colspan` and `rowspan` were read as written, so a span of billions, or a negative one, went to every writer (a negative `gridSpan` moved the cells after it back). Spans are held to what browsers allow, 1000 columns and 65534 rows, and to at least 1.
- **DOCX content in content controls, custom XML and text boxes is read.** A content control (`w:sdt`: a table of contents, a cover page, a form) or `w:customXml` element in the body, and a table row or cell wrapped in one, was dropped with its content; headers and footers read content controls one level deep only. The text of a text box drawn in a run (where Word puts text boxes) was dropped too, as was a table in a text box. All are now read at any depth, a text box's paragraphs, lists and tables as blocks right after the paragraph drawing it. Markup-compatibility content (`mc:AlternateContent`) is read from the branch a reader understands, the first `mc:Choice` whose namespaces it reads, else the `mc:Fallback` (an emoji Word writes as `w16se:symEx` has its character there, and was dropped); a text box in it is read once, and a picture or note reference in a text box is shown once, with the text box's text (the run drawing the text box showed it as well, and with `extractAttachments` a shape in `mc:AlternateContent` became two empty pictures). A drawing with no picture (a text box, SmartArt or chart) no longer makes an empty picture node.
- **ODF fields, list headers, grouped rows and partly formatted cells are read.** Text in an ODF paragraph's fields (a date, a page or sequence number such as the 3 of "Figure 3", a cross-reference, an author's name), `text:meta` and ruby was dropped, as were a list's header paragraph (`text:list-header`) and the rows of `table:table-rows` and `table:table-row-group` (grouped rows). An ODS cell whose paragraph held any formatted span kept only the spans' text ("Total: **5** units" read as "5"), and lost its links and line breaks. All are read now; ruby is written as its base with the reading in parentheses. The text a tracked deletion removed (`text:tracked-changes`) is no longer read as body text, nor is hidden text (`text:hidden-text`) or a script. A cell of several paragraphs keeps each on a line of its own, a covered cell (`table:covered-table-cell`) keeps the columns after it in place and the cell covering it records its span, a note cited again (`text:note-ref`) is that note rather than its number as text, and a chart LibreOffice saved has its data (its namespace was looked for only near the start of the part, and rows in `table:table-rows` were skipped).
- **RTF headers, footers, comments and text boxes are read, and Unicode text no longer doubles.** Headers and footers were skipped, and the left, right and first-page ones (`\headerl`, `\footerf`, ...) were read into the body; all go to `auxiliary.headers` and `auxiliary.footers` now, as DOCX's do (`ignoreHeadersAndFooters` still leaves them out). An annotation (`\annotation`) is a comment with its author, initials and date, and a shape's text box (`\shptxt`) is read after the paragraph anchoring it, without the shape's properties. Each of these (and a footnote) is read apart from the paragraph and table around it: a footnote in a table cell or list item ended the cell's table or the item's list. A character outside the code page is written `\uN` followed by a fallback for older readers (`\ucN` characters, one by default), which was read as text too: Word writes Cyrillic or Chinese as `\u1055\'3f`, so every such character came out followed by a `?`. The fallback is skipped now (at most 16 characters, whatever `\ucN` asks), and kept in `rawContent`.
- **PPTX modern comments are read.** PowerPoint 365 writes comments to `ppt/comments/modernComment_*.xml`, with their authors in `ppt/authors.xml`, and no longer writes the older comment parts, so a current presentation's comments were all lost. They are read now, each reply a comment of its own with its author, initials, date and the comment it answers (`parentId`), a paragraph per paragraph. Classic comments were not read at all (their text is a `p:text` string, which was never read); they are read too.
- **SmartArt text is read.** The text of a SmartArt graphic lives in its own data part, which no parser read, so every SmartArt diagram's text was lost. A PPTX SmartArt frame is now read as a bulleted list, its items nested as the diagram nests them, and a DOCX one as the same list after the paragraph drawing it. A diagram shown by several frames is read once.
- **DOCX tracked moves are read once.** Text a tracked change moved (`w:moveFrom`) was read where it was moved from as well as where it stands (`w:moveTo`), so it came out twice; moved-away and deleted content is left out, as a deletion's text was, and insertions are read.
- **DOCX alternative-format chunks are read.** A `w:altChunk` holds content in another format that Word merges into the document where the chunk stands: HTML, MHT, RTF, plain text or another DOCX. html-docx-js, for one, writes a document's whole body as an MHT chunk, so such a DOCX parsed as empty. Chunks in the body, table cells, headers, footers, notes and comments are now read where they stand, each part's links and pictures resolved through its own relationships (an MHT chunk's pictures become attachments), each part once, and count against `decompressionLimits.maxXmlElements`. A nested DOCX chunk inflates within what the document around it left of `decompressionLimits.maxUncompressedBytes`, and a DOCX inside it is not read. An HTML or plain-text chunk is decoded as its byte-order mark or `<meta>` charset says. Only the parts a chunk names are inflated. A chunk that cannot be read (its part is missing, of another format or corrupt, or a DOCX in a DOCX chunk) raises the new `ALT_CHUNK_NOT_READ` warning naming why, and the rest of the document is read; a chunk past the document's own limits (`maxXmlElements`, `maxUncompressedBytes`) still fails the parse.
- **XLSX inline strings keep every run.** A cell holding an inline string of several rich-text runs kept only the first run; its whole text is read now (without its phonetic reading).
- **PPTX shapes in `mc:AlternateContent` are read.** A shape PowerPoint writes for newer readers with a fallback for older ones (an equation, an SVG picture) was dropped with its text; the branch the reader understands is read in its place (see DOCX content above).
- **Long lists no longer fail.** Appending a list of more than about 120,000 items (a slide group of that many shapes, an EPUB chapter of that many blocks, a text box or paragraph of that many runs) passed every item as an argument, which the engine refuses: the parse failed, and a writer reported it as nesting too deep. Lists are appended item by item.
- **A code block ends its line in plain text.** A code block or display equation ran into the paragraph after it (`code onePara after`).
- **HTML reads Word's and XML's markup as markup.** A namespaced tag (`<o:p>`, `<m:math>`), a markup declaration (`<!DOCTYPE html>` without `<html>`, `<![CDATA[`) or a processing instruction (`<?xml ...?>`) came through as visible text; they are read as a browser reads them, and Word's conditional comments (`<![if !supportLists]>`) drop their markers and keep their content. Whitespace next to any inline element (`<math>`, a custom element) is kept (`word<math>` ran together).
- **Footnotes in GitHub's, Pandoc's, markdown-it's and EPUB 3's HTML are notes.** A footnotes section whose items carry no `data-footnote-id` was dropped whole, and definitions were read only from its direct children, so a rendered README's footnotes lost their text in every output.
- **An HTML page's title, language, encoding and base are read.** `<title>` was neither decoded nor collapsed (`A &amp; B` stayed literal), `<html lang>` was ignored, a declared charset was ignored (a Windows-1252 page from Word's "Save as Web Page" came out garbled, a UTF-16 one as noise), `<base href>` was ignored, and a picture given only by `srcset` lost its image.
- **An EPUB's chapters are all read, or reported.** A spine chapter whose manifest `href` is percent-encoded (`chapter%201.xhtml`) or has an `.xml` extension, or whose file is missing, was dropped without a word, and a `%20` in a picture's path was not resolved; the first two are read and a missing or encrypted chapter raises `CONTENT_PART_NOT_READ`.
- **EPUB output is well-formed XML.** A control character in the text (from Markdown, CSV, or a character reference in HTML) was written into the book, which readers refuse; ids starting with a digit, which XML does not allow, are renamed with their links; an ordered task list opened `<ul>` and closed `</ol>` (in HTML output too).
- **A footnote cited twice has an id per reference.** Markdown `[^1]` cited twice wrote `id="footnote-ref-1"` twice in HTML and EPUB, which epubcheck refuses.
- **Internal links reach every node with a bookmark in DOCX and ODT output.** Bookmarks were written only for paragraphs and headings, so a link to a table, picture, equation, cell or list item went nowhere.
- **RTF output keeps headers, footers and review comments, and opens everywhere.** Headers, footers and comments were left out; they are written as `{\header}`, `{\footer}` and Word's annotations. A named or three-digit colour wrote `\redNaN`, and readers refused the whole file; a table nested in a table corrupted the outer one (it is written as Word writes it, with `\itap` and `\nestcell`); a tab or line break was written as the raw character. DOCX, ODT and LaTeX output keep named colours too (they dropped them).
- **RTF reads nested and merged tables, East Asian code pages and TextEdit files.** Word's nested tables were flattened, `\clvmrg` dropped the continuation cell without a row span and `\clmrg` was ignored, so later cells shifted; text in code pages 932, 936, 949 and 950, or under a font's `\fcharset`, was decoded as the wrong characters; and a TextEdit file's lines (a backslash ending a line) ran into one paragraph.
- **ODT output writes a cell's runs as one paragraph.** Each formatted run of a cell (a spreadsheet's "Total: **5** units") was a paragraph of its own.
- **Writers do not repeat work per use.** A picture shown many times is decoded once per document by DOCX and ODT output (a 3 MB DOCX showing one 3 MB picture 20,000 times took 105 seconds) and embedded once by the native PDF engine (shown 400 times, it made a 1.2 GB PDF). Names made unique (DOCX and ODT bookmarks, PDF heading anchors) resume their numbering per name, where 60,000 bookmarks of one name in a 7 KB DOCX took two minutes, and a node's `anchorIds` hold each id once. DOCX lists with the same kind at every level share one numbering definition (each list restarts its ordered levels), where every list wrote all nine levels.
- **More Markdown reads as it was written.** HTML written in capitals (`<IMG>`, `<B>`, `<BR/>`) was stripped with its content as if it were an MDX component; a line break in a heading was written onto a line of its own, which read back as a paragraph showing the heading's id (it is written as `<br>`); a loose list numbered `1.` throughout read as 1, 1, 1; several terms of one definition, or a term starting with `:`, turned the list into a paragraph; a front matter list (`tags:` over `- a` lines) was written back as `tags: ""`; a closed heading (`## Title ##`) kept its closing hashes; a link target in angle brackets (`<./my docs/x.md>`) kept them; a picture without alt text was written `![image]` and read back with that alt text; the pandoc dialect's admonitions (`::: {.note}`) did not read back; and a paragraph line shaped like a table's delimiter row made the paragraph a table. Abbreviations are found in time linear in the text however many are defined (10,000 of them over 10,000 lines took 12.5 seconds), match whole words (`e.g.` too) and prefer the longest.
- **CLI generator options take effect.** `--maxInlineImageBytes`, `--metadataOverrides.*` and the other options only generators have were sent to the parser, reported as unrecognized and ignored; and an option whose default is a number takes the value as a number.
- **A document cannot write onto JavaScript's shared prototypes.** An XLSX drawing whose picture referred to `__proto__` (read with `extractAttachments`) set `Object.prototype.altText`, and a DOCX numbering override at level `__proto__` or `constructor` set `Object.prototype.start` (and `Object.start`), so one crafted file changed every later parse and conversion in the process (a picture with no alt text took the attacker's). Every map a parser keys by the document's own names (relationships, styles, numbering, drawings, sheet names, comment authors, attributes) now has no prototype; tables of fixed names (highlight colours, alignments, package and MIME types, admonition colours, code languages) answer only their own names, where `w:highlight="constructor"` put a function into the AST as a colour and a package whose `mimetype` read `constructor` failed with an internal error instead of the unsupported-type one; and a custom or native property named `__proto__` is an ordinary property (it set its object's prototype, and was lost).
- **Crafted documents no longer take time in the square of their size.** An XLSX sheet of unclosed rows, cells or values (160,000 unclosed rows, a 2.6 KB file, took 23 seconds), HTML with many unclosed `<script>` or `<style>` tags (EPUB chapters too), a CSV cell of a long run of digits, a length or equation holding a long run of spaces, a long run of `&` in an XLSX string, PDF text with long runs of whitespace, and a Markdown line of many spaces were read again from each position. Each takes time linear in its size. An unclosed XLSX row or cell now ends where the next one starts, keeping its cells (it was dropped). Lookups that searched a whole list for each item are indexed: an ODS chart's cell references searched every sheet by name (100,000 references beside 400,000 sheets took 216 seconds), HTML output searched all sheets for each sheet's number, and an ODT embedded object searched every part of the package. Runs in DOCX hyperlinks nested in hyperlinks were given their link again at each level (17 seconds), and text boxes nested in text boxes copied their content into each level around them; the outermost link is given once, and a text box's content is added to its paragraph once. XLSX pictures' alt text was looked up through every drawing relationship for each picture (2,000 pictures beside 200,000 relationships took 90 seconds), a PPTX comments part through every part of the package, an EPUB chapter through every file of the book, and an ODT embedded object through a tail at every folder of each part's path; each is a map lookup now. An HTML end tag that closes nothing walked up to the root each time (16 million of them 250 elements deep, 63 KB of EPUB, took 17 seconds), and an RTF field searched the fields nested in it for its link at every level; each is passed over at once now. An HTML tag whose `>` stands only between quotes (`<br ">"`) was scanned for to the end of the document from every tag (2 KB of EPUB took two minutes); a failed scan now tells later ones where they would fail. HTML content under many wrapper elements (divs, lists, quotes, inline elements) was collapsed, trimmed and copied again at every level, and an implied end tag walked up the open elements (2 million paragraphs under 250 divs, 6.7 KB of EPUB, took 55 seconds); each level now handles only where its pieces meet. ODF runs inside spans, links or fields nested in each other were copied up at every level too; they are read into their paragraph once. An XLSX sheet naming one drawing many times placed the drawing's pictures again at each naming (2,000 namings of a drawing of 300 pictures made 600,000 picture nodes); it places them once.
- **A list level out of range cannot hang a parse.** A DOCX `w:ilvl` was taken as written, and the parser stepped through every level between it and the list's for each paragraph: a level of -20,000,000 took 20 million steps per paragraph, and one past 2^53 never finished. A DOCX `w:ilvl` and a PPTX `lvl` are now clamped to the nine levels a list has (0 to 8).
- **A note, comment or string referred to many times cannot exhaust memory.** Each reference to a DOCX footnote, endnote or comment, and to a footnote in HTML (EPUB chapters too), built its own copy of the note and its text, and each cell showing an XLSX rich-text string joined its text anew, so a file of a few kilobytes referring to one large note thousands of times ended the process with a heap out-of-memory error (which no caller can catch). An XLSX comments part was read again for each relationship naming it (one 1 MB comment named 2,000 times, 3.7 KB of XLSX, ended the process out of memory). A note or comment is now one node every reference shares, a comments part is read and attached once, and a string's text is joined once. Writers write a shared note once too: plain text, RTF and chunks copied it at every reference (a 20 KB document made 20 MB of output, and a slightly larger one failed with `Invalid string length`), as did ODT output; a later reference is now a mark with the note's number (a DOCX `NOTEREF` field, as Word writes a note referred to again, or an ODT `text:note-ref`, which the DOCX and ODT readers read back as the same note), each reference in HTML has an id of its own, and a chunk holds the note's text at its first reference. A comment is written once too (DOCX and ODT output wrote it at every reference). Notes or comments referring to each other twice each, a shared graph rather than a tree, made DOCX and ODT output double per level; each shared node is now read and written once.
- **A small PDF cannot tie up the CPU for minutes per page.** Finding a page's column gutters checked every line again at each gap, so a PDF of 2 KB holding one line of 32,000 spaced words took over two minutes, and pages sharing one content stream multiplied that at no cost in size. Each text item looked through the whole stack of marked content enclosing it (thousands deep in a crafted file), and was matched against every link and highlight area on the page (one highlight of 20,000 quads, or one link listed 20,000 times), each link testing every character. Each now takes time linear in the page: the gutter needs no second check, each stack level carries what a text item reads, repeated annotations are read once and a page's first 1,000 links and 1,000 highlight areas are read (the rest with an `ANNOTATION_EXTRACTION_FAILED` warning), and a link's characters are found by range.
- **A small RTF cannot take gigabytes to read.** Recording a picture's raw content serialized the whole picture again for each group inside it, so a 16 KB picture of 8,000 empty groups took 2 GB and 2.6 seconds with `extractAttachments` (a picture's `rawContent` now holds it once, where it held repeated copies), and each footnote or table in a paragraph copied the paragraph read so far.
- **A small ODF, PPTX or chart cannot exhaust memory or CPU.** An ODF chart's table repeated a cell as many times as it asked (`table:number-columns-repeated="100000000"` in a 1.3 KB ODT ended the process out of memory); a chart's category labels were written again for every series (2.6 KB of PPTX, 2 GB); an embedded ODF object was read again for every frame naming it (10 KB, a minute); a PPTX comments part was read again for every relationship naming it (19 KB, out of memory); every ODT list scanned all the document's list styles (4.6 KB, two minutes); each ODS chart series scanned the whole sheet and copied its range (1.8 KB, 3 GB); and runs of spaces (`text:s`) had no bound in all (3.8 KB, 500 million characters). A chart's table now makes at most 10,000 series and 1,000,000 values, and its text holds the labels once (ahead of each series' name and values, where they were repeated before each); an object and a comments part are read once and shared, a comments part on the first slide naming it; list styles are indexed by name; a chart's ranges are resolved through each sheet's rows, within a document-wide budget (past it, a range stays its `[range]` text); and a document's runs of spaces make 16 million spaces in all, past which a run is one space.
- **Content nested in its own kind is read once.** The XML readers looked up nested content through every level below (notes in a note's body, text boxes in a text box, tables in a table's cells, shared-string runs in runs, PPTX table rows and paragraphs, a frame's image or text box, DOCX footnotes, endnotes, comments, drawings and `mc:AlternateContent` in their own kind, XLSX and PPTX comments in comments, XLSX fonts, fills and cell formats, ODF style properties and comment authors, OOXML chart series, PPTX math), then reached the nested content again through the outer one, so the work grew with the square of the depth, or doubled per level: 528 bytes of ODT with footnotes nested 24 deep ended the process out of memory, 1.3 KB of DOCX with nested text boxes took half a minute, 586 bytes of ODS with nested tables took 7 seconds, 1.9 KB of XLSX with nested shared strings 20, XLSX fonts nested 2,000 deep 20, a PPTX chart of nested series over 30, and an XLSX or PPTX comment nested in comments copied its text at every level (400 MB). Each level is now read from its own children (or its outermost matches), and finding the first element of a kind stops at it. A DOCX numbering definition is shared by the lists naming it, where each list copied all its levels (20,000 lists naming one of 4,000 levels took 11 seconds). A table nested in an ODS cell is part of its cell, no longer a sheet of its own, and a DOCX paragraph around a text box is no longer taken for a list item by the text box's numbering.
- **Plain text lays out a nested table once.** Its cells were rendered, then rendered again to lay them out, so each table nested in a table doubled the work: 26 levels took minutes.
- **A DOCX template with unclosed paragraphs renders in linear time.** Splitting a part at its paragraph tags read the rest of the part from every `<w:p` without a `>`, so 570 bytes of zipped `<w:p ` took 24 seconds. A paragraph holding a placeholder is rebuilt from slices of its text, where it was rebuilt a character at a time (one of 300 million characters, 293 KB of template, ended the process out of memory). Each value is made once per document, and each use of a value after its first counts what it outgrows its placeholder by against `decompressionLimits.maxRepeatedContent`: 1,000,000 placeholders of one 100-character value (9.6 KB of template) wrote 450 MB of XML in 8 seconds, and a longer value failed with the engine's `RangeError`. Past the limit the render rejects with `OUTPUT_TOO_LARGE`.
- **Raw source (`includeRawContent` with `serializeRawContent: false`) is found in linear time.** The source was split into lines again for every node (32,000 paragraphs in a 4.2 KB DOCX took 49 seconds), and an element with no closing tag of its own name searched the rest of the part. A nested element of the same name (a table in a table) now ends at its own closing tag, where it ended at the first one; it is found in one pass (an element holding 160,000 of its own name, 3 KB of DOCX, took two minutes), reading no further than the `maxRawContentLength` budget has left.
- **A Markdown reference definition repeats within a budget.** A link's or picture's target, or an abbreviation's title, is written at every use, so a long one used many times made output growing with the square of the input (100 KB used 200 times, 20 MB). Uses after the first may repeat 16 MB of such text in all; past that, a reference stays its text, as an unknown one does.
- **An EPUB cannot multiply its pictures in memory.** Each `<img>` was written into its chapter as the picture's data, a copy per reference, so a 1 KB book showing one large picture a few thousand times took gigabytes; a picture is now read once however often it is shown.
- **A value of the wrong type in an AST is written as its type.** An AST (built by hand, or from JSON) holding an array where a string goes (a picture's alt text, a link, a style), a string where a number goes (a heading level `"1><script>"`) or an object where either goes reached writers that escape one kind of value and wrote another raw: an array's text went into an HTML attribute unescaped. Every generator now reads the values coerced to the types the AST defines, or without them. Heading levels, list indentation and item numbers are held to the range their format allows (`<h7>` is `<h6>`), and a video id is used only when it is one. Formatting keeps only the fields the AST defines (a wrapper's 16,000 other fields, given to each of its 16,000 runs, filled the heap from 597 KB of JSON), and metadata of more fields than any node holds keeps the defined ones. A list where a string goes is joined one level deep, into at most 64K characters (lists holding lists ten times each, eight levels down, made a hundred million values), and a chart's labels, series and values are plain strings. A record or list many nodes share is read once. An AST's own CSV delimiter is taken only as one character that neither ends a row nor starts a formula (`\n=` wrote a formula line no cell held).
- **An RTF link cannot break out of its field.** A `"` in a link target ended the `HYPERLINK` field's instruction, and what followed was read as RTF; it is percent-encoded.
- **A Markdown code block's language cannot open a tag.** A code node's `language` was written into the fence's info string with only line breaks and backticks removed, so a renderer writing the info string into its HTML unescaped could be handed `"><img onerror=...>`; `<` and `>`, which no language name holds, are removed too.
- **A style value holds no character references.** An inline style's value keeps no `&`: a browser decodes a reference such as `&#59;` into the `;` the sanitizer removes, ending the declaration.
- **The XML reader writes nothing to the console.** `@xmldom/xmldom` printed each recoverable problem in a document part (an entity it cannot resolve) with `console.error`, so a document could fill a host's logs at will. It now reports nothing, and keeps such an entity as written; a fatal problem still fails the parse.
- **Documentation: `abortSignal` does not interrupt a parse already running.** The README, the security policy and the config reference said it stops heavy loops; reading a document's markup is synchronous, so a timer cannot fire during it. To bound the time an untrusted document can take, parse it in a worker you can end. (A PDF is the exception in Node: pdf.js runs in a separate process that the signal ends.)
- **Docs visualizer: Markdown, HTML and CSV uploads parse without choosing a file type.** The visualizer handed the parser the file's bytes without their name, so a text format (which has no magic bytes) failed auto-detection unless its type was picked by hand. A file whose extension names a format is now passed with its name, so the extension decides; any other name is still detected from its content.
- **Docs visualizer: the RTF preview shows the document's pictures.** It parsed the generated RTF back without its images, so they appeared as broken links.
- **Docs visualizer: EPUB input offers the HTML parser options that apply to it.** "Preserve HTML Attributes" and "Preserve Iframes" affect EPUB chapters too, but were shown only for HTML and Markdown.
- **Docs visualizer: a chunk's heading can no longer inject markup.** The RAG-chunks window wrote each chunk's closest heading into the page as HTML, so a heading in an uploaded document could run script there. The chips are now plain text.
- **Docs visualizer: "Open result in Visualizer" loads the document completely.** The Template Studio hand-off set the parsed document but kept the previous file's name and Reparse state, so downloads were named after the old file and Reparse re-parsed it. It now loads the rendered document exactly as an upload.
- **Docs visualizer: Reparse is enabled only when a setting changed.** The button compared differently shaped configurations and so was always enabled after a parse.
- **Docs visualizer: accessible download menus and narrow screens.** The Download menus announce themselves to assistive technology, take focus when opened, move with the arrow keys and close with Escape or Tab, returning focus to their button; window headers wrap on phone-width screens instead of overflowing.
- **Docs visualizer: every warning is shown.** The warning banner showed only the most recent warning, so one from an output window could hide the parser's own explanation. It now lists every warning, grouped by where it came from (parsing, each output window, each download); regenerating an output replaces its warnings.

## [8.0.0] - 2026-09-16

This release is a ground-up rewrite of PDF text extraction, adds native DOCX and ODT generators plus ODG parsing, and drops one deprecated API.

### Breaking
- **`ast.toText()` was removed.** Use `(await ast.to('text')).value`, which produces the same content at its defaults and is configurable (layout, notes, image placeholders). The CLI's `--toText` flag was removed too and now errors with `--toText was removed in v8. Use --to=text instead.`
- **Long-deprecated config options were removed.** A major version is the moment to drop surface deprecated across the v7.x line: `outputErrorToConsole` (use `onWarning`; parse warnings no longer reach the console on their own, they are delivered to `onWarning` and collected in `ast.warnings`), `ocrLanguage` (use `ocrConfig.language`), `ocrConfig.autoTerminateTimeout` (use `ocrConfig.timeout.autoTerminate`), and `putNotesAtLast` (already a no-op; notes are attached via `node.notes`). Each of them now raises `UNRECOGNIZED_CONFIG_OPTION` naming its replacement rather than being ignored in silence. Their CLI flags (`--outputErrorToConsole`, `--ocrLanguage`, `--putNotesAtLast`) are gone too, and the CLI now **exits with status 1** and prints the replacement instead of accepting them: use `--verbose`, `--ocrConfig.language`, and `node.notes` respectively. The internal `ensureDomMatrix` alias was dropped in favor of `ensureEnvPolyfills`. The Markdown-dialect deprecations introduced in 7.7/7.8 are **kept** for one more cycle.
- **PDF output changed shape and content by default.** The PDF parser now recovers real structure: tagged PDFs yield `heading` (with correct levels), `table`/`row`/`cell`, `list`, and `note` nodes, and one `paragraph` per paragraph rather than one per visual line. Consumers that relied on the old page-of-flat-paragraphs shape, or on the exact old text, will see different output. Word spacing, column reading order, hyphenation and super/subscripts are all fixed, so the plain text differs as well.
- **Per-node page geometry is on by default.** PDF text runs, paragraphs, headings, tables, cells and images carry a `bounds` box, and page nodes carry `pageWidth`/`pageHeight`/`rotation`. This enlarges the JSON AST. Set `ignorePageGeometry: true` to omit it and restore the smaller shape.
- **`.to('text')` for PDFs is now layout-faithful by default.** With `textConfig.preserveLayout` (default true) and geometry present, each page renders as a spatial monospace grid so columns and tables line up like the source page. Set `preserveLayout: false` for flowing text.
- **Node.js `>=22.13` is now required** (was `>=18`). This matches the bundled `pdfjs-dist`, whose own floor is `>=22.13`, so the previous claim was already unmet on the PDF path.
- **OCR text now preserves 2-D page layout by default** (`ocrConfig.preserveLayout: true`). A 7.x consumer that OCRs images now gets column-aligned, space-padded text instead of the old flat reading-order string, which changes `node.text`/`ocrText` content (and therefore RAG chunk content and embeddings). Set `ocrConfig.preserveLayout: false` to restore the flat output.
- **PDF image attachments were renamed and re-typed.** Extracted PDF images are now `pdf_image_p<page>_<n>.png` with `mimeType: 'image/png'`; v7 emitted `pdf_image_p<page>_<n>.bmp` with `image/bmp`. Any consumer that filters, routes or stores attachments by a `.bmp` suffix or the `image/bmp` type must be updated. The bytes are roughly an order of magnitude smaller and remain valid for OCR and embedding.
- **`includeImages` now defaults to the explicit `'image-only'` mode, which no longer carries image OCR text.** In v7 an image node's recognized text leaked into the Markdown fallback and the HTML `alt` attribute; at the v8 default it does not. Anyone feeding scanned or OCR'd documents into RAG through Markdown or HTML **loses that text unless they opt in**: set `includeImages: 'image+ocr-text'` (image plus its recognized text) or `'ocr-text-only'` (text alone). `true`/`false` still map to `'image-only'`/`'none'`.
- **Markdown and fragment HTML no longer inline an image over `maxInlineImageBytes` (1500000 by default).** An over-cap image renders its recognized/OCR text when it has any (multi-line OCR as a fenced block in Markdown), otherwise a compact reference to the attachment name, and `IMAGE_NOT_INLINED` is raised. Output that previously carried a self-contained multi-megabyte `data:` URI now references a file the caller must ship alongside it; raise `maxInlineImageBytes` (or set `Infinity`) to restore v7 behavior. **Standalone HTML is unaffected and always inlines**, since a self-contained document has nowhere else to resolve the image from.
- **ODF comments and (Writer) master-page headers/footers are parsed by default.** Every `.odt`/`.ods`/`.odp`/`.odg` parse now exposes `office:annotation` comments (on a node's `.comments`): text-paragraph comments in any ODF type, spreadsheet cell notes on the `.ods` cell, and slide/page comments on the `.odp`/`.odg` page. An `.odt` parse also exposes its master-page `style:header`/`style:footer` content (in `ast.auxiliary`); v7 dropped both entirely. They therefore appear in every generated destination too. Set `ignoreComments` / `ignoreHeadersAndFooters` to restore the old output.
- **PDF running headers and footers route to `ast.auxiliary` by default.** Text a PDF marks as an `/Artifact` in the top or bottom band of a page is no longer part of `ast.content`; it is collected in `ast.auxiliary` (and dropped entirely under `ignoreHeadersAndFooters`), so `.to('text')` and chunked output no longer repeat the running header on every page.
- **PDF `formatting.size` now carries its unit and `metadata.description` its proper source.** A PDF run's `size` is `"12pt"` where v7 emitted the bare `"12"`, matching the DOCX/ODF/RTF parsers and the CSS the HTML generator writes. `metadata.description` now comes from the PDF `/Subject` field (v7 mistakenly read `/Keywords`), and `metadata.keywords` is newly populated from `/Keywords`.
- **NEW optional peer dependency `puppeteer: ">=22"`.** The default `to('pdf')` engine needs `page.pdf({ tagged, outline })`, which puppeteer added in 22. The range is declared (v7 listed puppeteer only in `peerDependenciesMeta`), and npm 7+ validates optional peers, so a consumer pinned to puppeteer 21.x or older gets an `ERESOLVE` on install until they upgrade. Projects that never generate PDFs are unaffected: the dependency stays optional and is only loaded on demand.

### Added
- **Template rendering / mail-merge (`OfficeTemplate.render`, alias `renderTemplate`).** Fill a DOCX template's `{{placeholder}}` tags from a data object and get back a new `.docx` with all of the template's formatting, layout and structure intact; pass an *array* of data objects to get one document per entry (a batch mail-merge). It is not parsing or conversion: the template is copied and only its placeholders are substituted. The substitution is run-aware, so a placeholder Word split across several runs (e.g. `{{`, `na`, `me}}`) is still filled, and a value adopts the formatting of the run its placeholder sat in (a bold `{{amount}}` renders bold). Placeholders are matched in the body, headers, footers, footnotes/endnotes and comments; values may contain newlines (rendered as line breaks). Config (`TemplateConfig`): `data` (object or array), `delimiters` (default `{{ }}`), `onMissing` (`'keep'` default / `'empty'` / `'error'`), and `password` / `onPassword` (an encrypted template is decrypted first, with the same lazy-callback retry semantics as parsing). New error codes: `TEMPLATE_UNSUPPORTED_FORMAT` (a non-DOCX template) and `TEMPLATE_FIELD_MISSING` (a placeholder with no data under `onMissing: 'error'`). Output is deterministic. Zero dependencies (built on the bundled `fflate`). Other formats (XLSX/PPTX/ODF) will follow.
- **Password-protected documents (all encryptable formats).** Encrypted OOXML (`.docx`/`.xlsx`/`.pptx`; ECMA-376 both *agile* AES-CBC and *standard* AES-ECB, unwrapped from their CFB/OLE container) and encrypted ODF (`.odt`/`.ods`/`.odp`/`.odg`; per-entry AES-256/192/128-CBC with PBKDF2) now decrypt and parse, and PDF decryption is exposed through the same options (pdf.js handles the PDF cipher). One unified, top-level config drives every format: **`password`** and the lazy/interactive **`onPassword`** callback, with unified error codes **`PASSWORD_REQUIRED`** (encrypted, none supplied), **`PASSWORD_INCORRECT`** (wrong), and **`DOCUMENT_DECRYPTION_FAILED`** (a structural or unsupported-scheme failure). Decryption happens before type detection, in a new zero-dependency `crypto` module (Node's `crypto` plus native WebCrypto PBKDF2, polyfilled in the prebuilt browser bundle) with a minimal CFB reader; the unsupported schemes raise a clear error rather than a wrong-password one: OOXML's legacy RC4/CryptoAPI and ODF's legacy Blowfish, and ODF's newer AES-256-GCM with Argon2id key derivation (the default since LibreOffice 24.8); re-save with the classic AES-CBC/PBKDF2 scheme to parse it. Untrusted input is bounded: the ODF second-layer decompression and per-entry PBKDF2 work accumulate against a document-wide budget, and the OOXML agile key-stretch (`spinCount`) is capped so a hostile descriptor cannot make the synchronous hash loop block the event loop. Fixtures are generated independently of the decryptor by `scripts/generate-crypto-fixtures.mjs`.
- **ODT generation (`to('odt')`).** A new generator writes a real OpenDocument Text package (a `.odt` zip: `mimetype` first and STORED, `content.xml`, `styles.xml`, `meta.xml`, `META-INF/manifest.xml`, and `Pictures/`) from any parsed source, returning a `Uint8Array`. It is the round-trip partner of the ODF parser: headings, styled runs, ODF whitespace encoding (`text:s`/`text:tab`/`text:line-break`), nested lists rebuilt from the flat AST with continuation numbering, tables with merged cells (`table:covered-table-cell`) and header rows, images (`draw:frame`, deduped by attachment, SVG rendered natively by Writer), external and internal links, bookmarks, inline footnotes/endnotes with citations, `office:annotation` comments, code, admonitions and `meta.xml` metadata (custom properties round-trip) all re-parse. Unlike DOCX, ODF carries formatting in named automatic styles, so a per-file style registry interns each distinct formatting bundle to one `<style:style>` (minted in render order for byte-stable output), and there is no per-part relationship layer. Adds no dependencies (built on the bundled `fflate`) and is reproducible. Configurable via **`OdtGeneratorConfig`** (`odtConfig`): `format` (a shared `PaperFormat`), `landscape`, `margin`. Same sanitization inventory as DOCX (URL allowlist with graceful text degrade, entity escaping with control-char stripping, safe style/frame/table/bookmark names, hex-validated colors). Shares the reproducible-zip and image helpers with the DOCX/EPUB generators via a new `officeGenUtils` module.
- **ODF comment and header/footer parsing.** `OpenOfficeParser` now reads `office:annotation` comments (into a node's `.comments`, with `dc:creator`/`dc:date`) for every ODF type at its natural placement (text-paragraph comments, `.ods` cell notes, `.odp`/`.odg` page comments), and, for `.odt`, the Writer master-page `style:header`/`style:footer` (into `ast.auxiliary`), both behind the existing `ignoreComments` / `ignoreHeadersAndFooters` flags. These were previously dropped from every ODF parse. This makes the ODT generator's round-trip honest and also surfaces the content for `odt`→`docx`/`html`/`md`. This is a default-output change: see the matching entry under **Breaking**.
- **DOCX generation (`to('docx')`).** A new generator writes a real WordprocessingML package (a `.docx` ZIP: `[Content_Types].xml`, `word/document.xml`, `styles.xml`, `numbering.xml`, footnotes/endnotes/comments, headers/footers, media, and `docProps`) from any parsed source, returning a `Uint8Array`. It reproduces headings, styled runs (bold/italic/underline/strike/color/size/font/sub-superscript/highlight), paragraphs, tables with merged cells (`gridSpan`/`vMerge`), bulleted and numbered nested lists, images (with EMU sizing sniffed from PNG/JPEG/GIF), external and internal hyperlinks, bookmarks, footnotes, endnotes and comments, code blocks, admonitions, and document metadata. Like the EPUB generator it adds no dependencies (built on the bundled `fflate`) and runs identically in Node and the browser, and its output is reproducible (pinned zip mtimes and deterministic ids, honoring `metadataOverrides.modified`). Configurable via **`DocxGeneratorConfig`** (`docxConfig`): `format` (a shared `PaperFormat`, the same names `pdfConfig.format` accepts), `landscape`, and `margin` (points or a unit string). Every value written into the XML is sanitized: hyperlink targets go through a UNC/scheme allowlist (rejected links degrade to plain text rather than being dropped), text and attributes are entity-escaped with invalid XML control chars stripped, bookmark/anchor names are reduced to a safe character set, and colors are hex-validated. Round-trips cleanly back through the Word parser.
- **`CONTENT_NOT_REPRESENTABLE`** warning code: raised when a content feature has no faithful representation in the destination format (e.g. math or an embedded object written to DOCX) and is downgraded to a plain-text fallback rather than silently dropped.
- **`UNRECOGNIZED_CONFIG_OPTION`** warning code: raised (once per parse) when a parser-config key is not recognized, so a typo or a key renamed across the v8 upgrade (e.g. the old `ocrLanguage`, now `ocrConfig.language`) is surfaced instead of being silently ignored. The message names the offending keys and, for a known rename, the replacement.
- **Parse support for ODG (OpenDocument Graphics / LibreOffice Draw).** `.odg` (and the `.otg` template) join the ODF family handled by the existing OpenOffice parser: each `draw:page` becomes a `page` node, and shape text (text boxes, custom shapes, grouped shapes), embedded tables, and embedded images are extracted per page. Parse-only, in line with the other ODF types; vector geometry, shape coordinates, and ODG generation are out of scope. The HTML generator's PDF-detection now keys off the source format instead of the presence of `page` nodes, so ODG is not styled as a PDF.
- **Tagged-PDF structure recovery.** When a PDF declares a structure tree and it passes reliability checks, headings, tables, lists and footnotes/endnotes come from the tags. Untagged PDFs fall back to geometric heuristics.
- **Reading-order recovery** for multi-column and float-beside-text pages, via a recursive XY-cut, so columns and floating tables no longer interleave.
- **Hybrid grid recovery on the tagged path.** A grid that a producer tagged as a run of loose paragraphs rather than as a Table (a calendar tagged one paragraph per day is the canonical case) is now additionally recovered as a `table`/`row`/`cell` subtree, bringing the tagged path to parity with the geometric one (which already recovers such grids via `detectTables`). It runs over the assembled tag-derived paragraph siblings on the parser's internal authored geometry, so it applies under `ignorePageGeometry` too, and it is conservative by construction: only contiguous short paragraph siblings that are not already inside a table are candidates, columns are clustered by horizontal centre and must each appear in several rows, and the same guards the geometric detector uses (at least three columns and three rows, short cells, a stable column set, vertical-pitch adjacency) must hold, so ordinary prose, multi-column articles and a grid's own title line are never folded in. Tagged tables, lists, headings and notes are untouched.
- **`pdfParserConfig`** (mirrors `htmlParserConfig`): `useTags`, `detectColumns`, `mergeHyphenatedWords`, `lineToleranceFactor`, `spaceToleranceFactor`, `headingDetection` (`auto`/`font-size`/`off`), `pageRange` (e.g. `'1-3,7'`), and `normalizeText`. (`password`/`onPassword` are top-level, shared across formats: see the password entry above.)
- **`maxInlineImageBytes`** generator config (default 1500000): caps the decoded size, in bytes, of an image inlined as a `data:` URI in HTML/Markdown (the base64 URI itself is ~1/3 larger). Under the default `'image-only'` mode an image over the cap renders its recognized/OCR text when it has any (multi-line OCR as a fenced block in Markdown), otherwise a compact name reference; plain text follows the same rule. Standalone HTML always inlines regardless of the cap. See **Breaking** for the default-output change.
- **`IMAGE_NOT_INLINED`** warning code: raised (naming the image, its byte size and the cap) when an image over `maxInlineImageBytes` is emitted as its recognized/OCR text, or as a name reference when it has none, instead of an inline `data:` URI, so the downgrade is surfaced rather than silent. Markdown raises it even when OCR text is rendered in the image's place, since the image itself is still missing from the output. Standalone HTML, which must be self-contained with no external files, still inlines regardless of the cap and does not raise it.
- **`includeImages` widened from `boolean` to an image mode** (`ImageMode`): `'image-only'` (the `true` default), `'image+ocr-text'` (image then its OCR/recognized text), `'ocr-text-only'`, or `'none'` (the `false` case). This makes OCR text in the output explicit and consistent across HTML/Markdown/text/RTF instead of the previous ad hoc behavior (OCR text leaking into Markdown fallbacks and the HTML `alt`). `boolean` values keep working. The default drops that leaked text: see **Breaking**.
- **`ignorePageGeometry`** flat config flag to omit page geometry from the AST; reading order, table structure and `colSpan`/`rowSpan` inference are unaffected (they run on the parser's internal geometry regardless of the flag), so the result is the geometry-on AST minus the `bounds` boxes.
- **`textConfig.pageSeparator`** to control the string between rendered PDF pages (default `'\n'`; set `'\f'` for pdftotext-style form feeds).
- **`OfficeMetadata.language`**, populated from a PDF's `/Lang`; and `metadata.nativeProperties.tagged` plus the raw `markInfo`.
- **`NodeBounds`** type and error/warning codes `PASSWORD_REQUIRED`, `PASSWORD_INCORRECT`, `PDF_STRUCT_TREE_UNRELIABLE`, **`PDF_NO_TEXT_EXTRACTED`** (a warning that a PDF yielded essentially no text, so it is likely scanned; enable `ocr` with `extractAttachments`), and **`PDF_OUTLINE_TRUNCATED`** (a warning that a PDF's bookmark outline was cut short by the depth/size cap that bounds hostile files, or could not be read, so `ast.auxiliary.outline` is partial or absent).
- **`scripts/generate-pdf-fixtures.js`** producing the committed multi-column, rotated and encrypted PDF test fixtures.
- **`pdfjs-dist` upgraded to 6.2.108 and pinned to an exact version.** 6.3.x is deliberately held back: its `getMarkInfo()` returns `{}` for a marked PDF, which collapses tagged-PDF heading/table/note extraction to the geometry fallback (see `scripts/sync-pdfjs-versions.js` for the pin rationale and pre-bump checklist). Browser users self-hosting the worker must point `pdfWorkerSrc` at `pdfjs-dist@6.2.108`. Accordingly, `engines.node` is now `>=22.13.0` (pdf.js 6.x's floor).
- **Document outline / bookmarks** are extracted into `ast.auxiliary.outline` as a tree of `list` nodes carrying section-anchor destination links (see the internal-link resolution below; honors `ignoreInternalLinks`).
- **Page labels** (`PageMetadata.pageLabel`, e.g. roman-numeral front matter), **document permissions**, **optional-content layer names**, and **AcroForm field values** are surfaced (the latter three under `metadata.nativeProperties`).
- **Accessible PDF generation**: `PdfGeneratorConfig.tagged` (default true) emits a tagged PDF, and `outline` emits a heading-derived bookmark tree.
- **`PDF_GENERATION_FAILED`** error and **`PDF_TEXT_ENCODING_SUSPECT`** warning codes. The latter fires when a page's text is dominated by unmappable glyphs (broken/missing ToUnicode), so "empty" is distinguishable from "undecodable".
- **Print/PDF page-break fidelity.** The generated HTML's print stylesheet turns a page-break node (`<hr class="page-break">`) into a real page break rather than the on-screen dashed marker, repeats a table's `thead`/`tfoot` on every page the table spans, and keeps figures, blockquotes and code blocks from being split across pages. This applies to `to('pdf')` and to "Print to PDF" from the generated HTML.
- **Native PDF generation engine.** `pdfConfig.engine: 'native'` renders a PDF by laying the AST out directly with `pdf-lib` (a new optional peer dependency) instead of the default HTML-through-a-headless-browser route (`'html'`). It needs no browser, so it runs the same in Node (no Puppeteer/Chrome to install) and in the browser - where, unlike the print-based path, it can produce real PDF bytes client-side - and is much lighter. The engine handles headings, inline bold/italic/size/color text, bulleted and numbered nested lists, grid tables with borders, embedded images (honoring an explicit width), page breaks, horizontal rules, footnotes/endnotes (drawn at document end), master-page headers/footers, and document metadata, with word wrapping and pagination. Trade-off: it draws in the Standard-14 Helvetica and Courier faces (not the document's own) and performs a clean reflow rather than pixel-matching the HTML renderer, and `tagged`/`outline` do not apply to it. pdf-lib is stubbed out of the prebuilt browser bundle (kept lean); install it and self-bundle to use the native engine in the browser.
- **Geometric table recovery for untagged PDFs.** The geometric path now reconstructs grid tables from the layout, running before block/column segmentation (which would otherwise carve a table's columns into separate reading blocks). A run of three or more rows whose short cells align into three or more stable columns becomes a `table`/`row`/`cell`. Guards - at least three columns, and a hard per-line length cap so a long prose line can never be a cell - keep a multi-column article of wrapped lines from being misread as a table (verified: zero tables on the column-article fixtures). Column-alignment fidelity is best-effort and below the tagged path; scanned/OCR content whose glyphs are split may produce rough cells.
- **Geometric list recovery for untagged PDFs.** On the geometric path (untagged PDFs, or `useTags: false`), bullet and numbered list items are recovered from the layout - both a marker that prefixes its text (`• item`, `1. item`) and a marker drawn as its own atom in the hanging indent with the item text beside it (the usual multi-level / roman-numeral case a PDF producer emits). Nesting level comes from the marker's indent, ordered items are numbered from the rendered marker (so an interrupted list resumes), and detection is deliberately conservative - an ambiguous `-`/`*` or a lone numbered prefix only counts inside a run of compatible markers - so prose and multi-column articles are not turned into lists.
- **OCR text preserves 2-D page layout.** `ocrConfig.preserveLayout` (default true) rebuilds the recognized text's spatial layout from Tesseract's per-word bounding boxes, so a scanned table, form or multi-column page keeps its columns (right-hand text stays on the right, labels and values line up) instead of collapsing to a flat reading-order string - the OCR analogue of `textConfig.preserveLayout` for born-digital PDFs. The block is left-normalized so there is no giant leading indent, and wide vertical gaps become blank lines. Set it `false` for the previous flat text. The HTML generator renders image OCR text in a `<pre class="ocr-text">`, and the Markdown generator emits multi-line OCR text in a fenced code block, so the recovered layout stays visible in both.
- **PDF text color and highlight extraction.** `pdfParserConfig.extractTextColor` (default true) recovers each run's fill color into `formatting.color`. pdf.js exposes no color on its text content, so it is reconstructed from the operator list by tracking the text matrix and matching each show to a text run by position. Color is document content like bold or font, so it is extracted by default (v7 never reported it, so this only adds a field); set `extractTextColor: false` to skip it on a throughput-focused text/RAG path. Cost: the operator list, otherwise fetched only for the first page(s) that introduce a font, is now fetched for every page, about 1.6x parse time on a text-heavy PDF and near-free when `extractAttachments` or `ocr` already fetch it. Pure black is left unset, so only genuinely colored text carries a `color` (matching the DOCX/RTF parsers). Highlight annotations populate `formatting.backgroundColor` unconditionally - they come from the annotation list already read for hyperlinks, so they cost nothing extra.
- **PDF table `colSpan`/`rowSpan` recovery.** A tagged PDF encodes a merged cell as a wide/tall cell plus empty placeholder cells filling the columns/rows it covers (pdf.js exposes neither `/ColSpan` nor `/RowSpan`). Those placeholders are now absorbed: a non-empty cell whose box extends past an adjacent empty column takes it over and reports `colSpan`, and one whose box reaches well into the row band below (where the cell directly beneath is an empty placeholder) reports `rowSpan`. Conservative by construction (only empty placeholders a cell's own geometry provably covers are merged), so regular grids - including sparse matrices with legitimately empty cells - are untouched. Span inference runs on the parser's internal page geometry, so it works under `ignorePageGeometry` too (that flag only strips the emitted `bounds`). The HTML generator now renders any table containing a rowSpan with a grid-occupancy model, so a spanning cell reserves its column in the rows below instead of shifting them (this also fixes DOCX/ODT/ODP vertical merges, which previously mis-aligned).
- **Client-side native PDF in the browser (`officeparser/browser-native-pdf`).** The native PDF engine (`pdfConfig.engine: 'native'`) needs `pdf-lib`, which the default prebuilt browser bundle stubs to stay self-contained. A new dedicated entry leaves `pdf-lib` external, so a consumer that installs `pdf-lib` and bundles officeParser for the browser (Vite/webpack/etc.) gets a real PDF produced entirely client-side, with no headless browser. Same API as the main entry; Standard-14 fonts only.
- **`HtmlGeneratorConfig.omitDefaultTextColor`** (default `false`): omit an inline run `color` equal to the document default (near-black or near-white) so imported text follows the reader's light/dark theme instead of being pinned to black or white. Deliberately-coloured runs are emitted unchanged (Word's `w:val="auto"` already carries no colour); default output is byte-identical.

### Fixed
- **Attachment lookups are now O(1).** Every generator resolved an image/chart to its bytes with a linear `attachments.find` per node (O(nodes x attachments)); a per-generation `name -> attachment` index makes it O(1), which matters for a media-heavy document such as a fully inlined self-contained export. Output is unchanged (first-match-wins preserved).
- **A new AST node type can no longer be silently dropped by a generator.** The HTML, RTF and text generators classify every `OfficeContentNodeType` explicitly (no `default:` arms; `TextGenerator` uses a full `Record` instead of an allowlist) and `tsconfig.json` now sets `noImplicitReturns`, so adding a node type fails the build until each generator says how it renders it, instead of degrading to its children unnoticed. No output changes.
- **Internal PDF links resolve to the target section, not just the page.** A cross-reference or bookmark destination is matched to the nearest heading on its target page, which is given a stable anchor id (`heading.metadata.anchorIds`), and the link points at that anchor - so a reference jumps to the exact section in the generated HTML/PDF instead of the top of the page. When no heading is near the destination (a whole-page jump, a rotated page, or a target far from any heading) it falls back to the page anchor `#page=N`, which page nodes still carry as `id="page=N"`.
- **Rotated text (90/180/270 degrees) is no longer silently dropped**; it is recovered as trailing paragraphs (precise visual ordering of rotated text remains a limitation).
- **A super/subscript run now attaches to the preceding text without a stray space** (`super`+`script` -> `superscript`, `H`+`2` -> `H2`) unless a genuine word gap exists.
- **PDF images are sized from their on-page bounds** (points) in generated HTML/PDF rather than their intrinsic pixel size, so a high-DPI scan no longer prints oversized.
- **PDF generation fails loudly**: a rendering/engine failure throws `PDF_GENERATION_FAILED` instead of returning a silent zero-byte buffer.
- **Broken and glued PDF words.** Spacing is now inferred from the horizontal gap between text fragments, so runs split by a font or size change (like `super`+`script`) join into `superscript`, and genuinely separate words keep their space.
- **Vertically stacked glyphs in a narrow cell read as one token.** A producer that wraps a single token down a narrow cell (a "fancy" calendar drawing `11` as two stacked `1`s, or `Sun` as `Su` over `n`) previously joined the stacked lines with a space (`1 1`, `Su n`). Two consecutive lines that are both 1 to 2 characters and horizontally overlap (a vertical stack, not a real wrap, which normal prose never trips because a wrapped line's predecessor fills the width) now join without a space.
- **A PDF with per-page font subsets no longer sleeps up to half a second per font per page.** The image-dependency wait polled the wrong object pool for font ids (which live in `commonObjs`, not `objs`), so the callback never fired and the 500 ms timeout always elapsed; each dependency is now routed to the pool that holds it. On a multi-font document this removes many seconds of pure idle wait per page under `extractAttachments`.
- **1-bit grayscale (CCITT/JBIG2 fax) scans decode correctly.** The `GRAYSCALE_1BPP` path read one byte per pixel, but the data is bit-packed (8 pixels per byte, rows padded to a byte), so a fax scan came out as noise and OCR found nothing; it is now unpacked properly.
- **`ignoreInternalLinks` is now honored for PDF** (internal-destination links were always emitted before).
- **`ignoreHeadersAndFooters` is now meaningful for PDF**: running headers/footers marked as Artifacts route to `ast.auxiliary` or are dropped (see **Breaking** for the default-output change).
- **`onNode` now fires exactly once per node in HTML output.** `HtmlGenerator` re-processed nodes on several internal passes (a bold-header table asked the hook four times per cell, a rowSpan table three times, everything else twice), which surprised hooks that count or mutate. Each node is now offered to the hook once and the recorded verdict is reused. Output is unchanged apart from the chart element ids on spreadsheet sheets, which no longer skip numbers.
- **Header rows are read from real ODT and DOCX files.** The ODF parser walked only a table's direct `table:table-row` children, so rows inside `table:table-header-rows` (what LibreOffice writes for a repeating header, and what `to('odt')` emits) were dropped entirely, and the Word parser ignored `w:tblHeader`. Both are now read and their cells marked as header cells, so `isHeaderRow` and every generator recognise them and the DOCX/ODT round-trips keep their header rows.
- **A DOCX vertical-merge continuation cell no longer adds an empty paragraph and a stray space to the merged cell on re-parse.** The continuation cell must contain a block child, so a generated document carries an empty `<w:p/>` there; the parser now folds a continuation cell into the merged cell only when it holds real content, which makes the DOCX round-trip byte-stable.
- **A worker/memory leak per PDF parse** (the loading task was never destroyed) is fixed.
- **A scanned PDF could crash downstream Markdown parsers.** PDF images are now encoded as PNG rather than uncompressed BMP (roughly an order of magnitude smaller, and still valid for OCR and embedding), and the HTML/Markdown generators no longer inline images above `maxInlineImageBytes`. A full-page scan previously became a multi-megabyte base64 `data:` URI on a single line, which overflowed the inline lexer in parsers such as `marked`. Over the cap, Markdown and plain text now render the image's recognized/OCR text when it has any (multi-line OCR as a fenced block in Markdown) and a compact name reference otherwise, so scanned documents produce readable text rather than a giant image blob; fragment HTML instead references the image by name (`<img src="name">`), a reference an HTML consumer can resolve. Both the rename/re-type and the non-inlining are breaking for existing consumers: see **Breaking**.
- **`ocr: true` without `extractAttachments: true` no longer silently does nothing, in any format.** OCR runs over extracted images, which need `extractAttachments`, so the combination produced no text; every format now raises the new `OCR_REQUIRES_ATTACHMENTS` warning (previously only PDF did), and the PDF path also skips the wasted per-page image decode. Set both flags to OCR a document's images.
- **A table nested inside a header cell keeps its own body cells as `<td>` in HTML output.** The `<thead>` promotion rewrote every `<td>` in the header row to `<th>`, including a nested table's; it now promotes only the row's own top-level cells (a header row dropped by `onNode` is also no longer wrapped in `<thead>`).

### Security
- **Global prototype pollution closed.** List-numbering counter maps in the Word and OpenDocument parsers were keyed by a raw document id, so a `numId`/`listId` of `__proto__` could write onto `Object.prototype` for the whole process from one crafted `.docx`/`.odf`. The maps are now null-prototype.
- **Memory-exhaustion (OOM) DoS closed.** An ODF `<text:s text:c="…">` space count and a list `ilvl`/indentation reaching `String.prototype.repeat` were uncapped, so a sub-kilobyte file could force a multi-gigabyte allocation; the counts are now clamped.
- **Decompression-bomb (OOM) DoS closed on PDF image extraction.** With `extractAttachments` or `ocr`, PDF images were decoded with no size ceiling, so a crafted PDF embedding a small, highly compressed stream that expands to enormous pixel dimensions could force a multi-gigabyte allocation. `getDocument` now caps decoding at 40 megapixels, and skips image decoding entirely when neither flag is set.

### Added
- **`==text==` highlight round-trips through Markdown.** In a dialect that defines it (Obsidian/extended), a highlighted run now emits as `==text==` and `==text==` parses back to a highlight; other dialects keep the HTML `<mark>`/`<span>` fallback and leave `==` literal on parse. Import is purely additive; export of the default-yellow highlight becomes `==` under the `extended` dialect.

- **Markdown dialect capabilities are typed by the syntax they select.** `mdConfig.dialect` now names each capability's syntax: `admonitions: 'blockquote' | 'fence' | 'fence-attribute' | 'none'`, and `strikethrough`/`definitionLists`/`footnotes`/`citations`/`wikilinks`/`attributeLists` as `'<marker>' | 'none'` (e.g. `strikethrough: 'tilde'`, `wikilinks: 'double-bracket'`). A new `highlight: 'equals' | 'none'` capability is added. `'none'` is the explicit off switch; an omitted field still inherits from `extends`. Naming each capability for its syntax (rather than a product flavour or a bare boolean) lets a shared convention be one value and lets a second syntax be added later without a breaking change.

### Deprecated
- **Boolean values for dialect capability fields, and the admonition flavour names.** `strikethrough: true`/`false` (and the same for `definitionLists`, `footnotes`, `citations`, `wikilinks`, `attributeLists`) and `admonitions: 'github' | 'gitlab' | 'pandoc'` still work - they coerce to the new syntax values (`true` to the marker, `false` to `'none'`; the flavour names to `'blockquote'`/`'fence'`/`'fence-attribute'`) - but are deprecated and will be removed in the next major. Output is byte-identical for existing configs.

### Fixed
- **Nested lists flattened on an HTML round trip.** An HTML list item wrapping its text in a block element (`<li><p>a</p><ul>…`, the shape rich-text editors built on ProseMirror/Tiptap emit) exported to Markdown as `- a\n\n\n    - a1`: the paragraph's trailing blank line split the list into separate blocks and the child's indent was then stripped on reparse, so `a` and `a1` came back as flat siblings in one list. List items are now emitted as a single tight line (via `itemLineBreaks` above), a conservative parser pass re-joins a blank-line-split indented child back into its list, and `HtmlGenerator` places a nested list inside its parent's still-open `<li>` (spec-valid `<li>a<ul>…</ul></li>` instead of the invalid sibling `<li>a</li><ul>…`), which also makes generated EPUB XHTML valid. A bare-text `<li>` (no `<p>`) was never affected. **Behaviour change** to the shape of generated nested-list HTML.
- **GFM table column alignment was lost on import, non-standard on Markdown export, and dropped through HTML.** Import ignored the `:---`/`:---:`/`---:` separator markers; Markdown export emitted `| --- |` with a trailing non-standard table-level `{align=…}` rather than per-column markers; and the HTML generator emitted no cell alignment at all, so a table lost its alignment whenever it passed through HTML (the editor import path `md → HTML → editor`). Alignment now lives on per-column `CellMetadata.align`: the Markdown generator regenerates the standard `:---`/`:---:`/`---:` markers, and the HTML generator emits `style="text-align: …"` on each `<th>`/`<td>` which `HtmlParser` reads back (alongside the existing table-level `<table data-align>`), so alignment survives `md → HTML → md` losslessly. A uniform-alignment table additionally carries `data-align` on the `<table>` for editors that model one alignment per table. Unaligned tables are byte-identical. **Behaviour change** to generated table separators (Markdown) and cell styles (HTML).
- **Inline monospace text was emitted as a styled `<span>` in HTML.** Inline code (a monospace text node) rendered as a `font-family: monospace` `<span>` rather than `<code>`, so it did not round-trip as inline code through HTML. It is now a `<code>` element (with bold/italic wrapping it), which the parser reads back to a monospace run.
- **A single-line code block carrying a language rendered inline in HTML.** `HtmlGenerator` chose `<pre><code>` vs an inline `<span>` purely by whether the code contained a newline, so a one-line code node with a language (`const x = 1;` tagged `js`, or a one-line mermaid diagram) rendered inline and lost its block-ness. A code node carrying a language now always renders as `<pre><code>`.
- **A plain `<blockquote>` was dropped on HTML → Markdown export.** Only the admonition `> [!NOTE]` path emitted a blockquote; a plain `<blockquote>` silently lost its `>` marker. It now round-trips as a `> quoted` blockquote.
- **An HTML `<br>` was read back as a soft wrapping break.** `HtmlParser` mapped `<br>` to a `textWrapping` break, which the Markdown generator emitted as a bare `\n` in a paragraph - reimporting as a space, so `<p>line1<br>line2</p>` collapsed to one line. `<br>` is now a `carriageReturn` hard line break, symmetric with the generator, so it survives the round trip in paragraphs as well as cells.
- **A single-line `$$…$$` imported as inline math with stray `$`.** A `$$\int_a^b$$` on its own line fell through to the inline `$…$` tokenizer, which matched the inner `$\int_a^b$` and leaked the outer pair as two literal `$`. An own-line `$$…$$` is now block math, matching the multi-line `$$` form. (`$$` inside a line of other text is left as-is.)
- **`npm test` failed on a cold run, and a CLI timeout masqueraded as a content mismatch.** The CLI parity test shells out to OCR the sample PDF (~27-30s, more on a cold cache), but the harness capped every CLI call at 30s and coerced `spawnSync`'s SIGTERM kill (`status: null`) to exit `0`. So a cold run clipped the PDF at the limit and then read the killed process as a clean exit with empty output, reporting `0.0% similarity ... Got: 0 words` - a phantom parser regression rather than the timeout it was. The OCR parity call now gets a 120s budget, and a timed-out CLI run is surfaced as a distinct non-zero status with a clear message. Test tooling only; the published package is unchanged. (#111)

### Added
- **Attribute-driven HTML interop for wikilinks, citations, math and mermaid.** `HtmlParser` now accepts the on-the-wire shapes structured editors emit, with no change to default output: `a[data-wikilink]` (page in `data-target`, display text from the anchor body or `data-alias`), a `span.citation` carrying `data-key`, math whose `data-math` holds the raw LaTeX with the mode in the class token (the delimited `data-math="inline|block"` shape is still read exactly as before; any other `data-math` value, previously read as inline math with the attribute ignored, is now taken as the LaTeX source), and `div[data-mermaid]`/`div.mermaid`/`pre.mermaid` mapped to a `mermaid` code node (previously the div flattened to plain text).

The `[^id]` reference marker also stays at its citation point (`Body[^1].`) rather than migrating to the end of the paragraph, aligning the Markdown and HTML generators. **Behaviour change** to the Markdown footnote-section markup. **Migration note:** a `.md` file saved by officeParser &le; 7.5.x carries the old `### Notes` section; on its first re-save that line is parsed as a genuine heading and kept once (a single `### Notes` heading, bounded - it does not accumulate, and settles by the second cycle). The parser deliberately does not swallow it, so a document's own genuine `### Notes` heading is never removed. Documents authored at &ge; 7.6.0 are unaffected.
- **Footnote bodies never reached RAG chunks.** `ChunkingGenerator` collected a node's children but not its `notes`, and emitted a content node's chunk without recursing into them, so a footnote's text was absent from the chunk index although present in `.to('text')`. Note bodies are now folded into the referencing node's chunk text.
- **Quoted frontmatter scalars lost their type on a Markdown round trip.** A quoted YAML scalar (`version: "123"`, `flag: "true"`) was unquoted and then coerced to a number/boolean, which the generator re-emitted unquoted, destroying the string permanently after one save. A quoted scalar now stays a string; only bare, unquoted scalars coerce (matching YAML semantics). **Behaviour change:** a quoted numeric or boolean now retains its declared string type and re-emits quoted, rather than re-emitting unquoted as a number/boolean.
- **Orphan footnote definitions were silently dropped.** A `[^x]: …` definition with no matching `[^x]` reference was discarded on any conversion, so deleting a reference but keeping its definition lost the definition on the next save. Unreferenced definitions are now preserved on both sides - recovered from a `.md` document and from a `section[data-footnotes]` on the HTML side - and emitted in the footnotes section on output (a `[^x]:` line in Markdown, a `div[data-footnote-id]` inside `section[data-footnotes]` in HTML) with no citation marker and no dangling back-link, so an unreferenced definition survives a full md -> HTML -> md round trip. **Behaviour change:** the definition is now kept rather than lost.
- **Thematic breaks (`---` / `<hr>`) were lost on save.** A Markdown `---` and an HTML `<hr>` parsed to a page break, which the Markdown generator emits as a bare newline, so a horizontal rule silently vanished on the first save and re-collapsed on the next. A thematic break is now a distinct `breakType: 'thematic'` (an additive metadata value) that emits `---` in Markdown and `<hr>` in HTML; an office page break (`<hr class="page-break">`) stays a page break. **Behaviour change:** a `---` / `<hr>` now survives a round trip instead of collapsing to whitespace.
- **A footnote referenced in a table cell was defined twice.** The HTML generator re-processes table cells (header-row detection and sparse-column rows) after they were already processed, which pushed a cell's footnote into the collected definitions twice - a duplicated `id`, definition, and back-links. Collected notes now de-duplicate by identity, so a table-cell footnote is defined exactly once.
- **Repeated references to one footnote id were duplicated.** Two `[^1]` references to a single definition renumbered to `[^1]`/`[^2]` on save with the body copied. Repeated references now share one note, so they stay `[^1]` with a single definition; office notes that merely share a numeric id (a footnote and an endnote both numbered `1`) remain distinct.
- **Documentation**: `generate(ast, 'chunks')` returns an `OfficeChunk[]` array, not a JSON string (the code comment and README said otherwise); consumers serialize to JSON/JSONL themselves.

- **`NO_WORKSHEETS_FOUND` and `NO_SLIDES_FOUND` warnings**, so a chartsheet-only workbook or a slide-less presentation says why it is empty instead of returning silently.

- **The browser bundles broke webpack builds.** One dynamic import escaped the build's ignore annotations, because the rule that added them treated an interpolated template literal as a fixed string. Webpack does not skip a specifier it cannot resolve: it builds a context module over the whole directory, so consumers ended up bundling all of `dist/`, Node-only files included, and their build failed on `child_process`. A webpack 5 build of the ESM and slim ESM bundles is now warning-free. (#108)
- **Valid documents were rejected as `zip` files.** Magic-byte detection reports a generic `zip` for archives that place too much data before their format declaration, which streaming ZIP writers and part-heavy decks both do. When detection is inconclusive the archive is now opened and the format read from `[Content_Types].xml` or the `mimetype` entry. - **Corrupt input parsed as an empty document instead of failing.** Since 7.3.0 an unreadable, truncated, or mislabeled archive resolved to an empty AST with no warnings, indistinguishable from a genuinely empty file. Truncation inside an entry could also leave the promise pending forever. (#107)

- **ODF documents could parse as empty or as the wrong content.** An ODS/ODP with no `mimetype` entry was walked as a text document, and a missing root `content.xml` could promote an embedded `Object N/content.xml` to the document body.
- **Errors were reported twice, with a doubled `[OfficeParser]: ` prefix and their code flattened to `FILE_CORRUPTED`.** Archive extraction errors also ignored `outputErrorToConsole` and `onWarning`, always writing to the console.
- **Reusing one config object across calls leaked state between documents.** A sufficiently complete config was used directly rather than copied, so each run wrote to the caller's object: later parses appended their warnings to earlier, already-returned `ast.warnings`, and generation rewrote an invalid `htmlConfig.containerWidth` to `'auto'` on the caller's own config, silencing the warning on every later run. Config resolution now always returns an object it owns, on both the parser and generator side. `abortSignal` and callbacks keep their identity.

### Added

Fractions, sub/superscripts, radicals, delimiters, n-ary operators, functions, accents, matrices and math alphabets (`ℝ` and friends) are all carried through, and a document's own `<annotation encoding="application/x-tex">` is preferred over anything reconstructed from the presentation markup. ODF attaches breaks to the paragraph *style* (`fo:break-before`/`fo:break-after`) rather than writing an inline element, so nothing was ever found to emit; those now produce `break` nodes around the paragraph, and `<text:soft-page-break/>` maps onto the same `lastRenderedPage` type DOCX uses. (#104)

### Fixed
- **Equations were silently corrupted rather than merely missing.** DOCX and HTML/EPUB equations fell through to generic text concatenation, so `<m:num>1</m:num><m:den>2</m:den>` and `<mfrac><mn>1</mn><mn>2</mn></mfrac>` both came out as `12` - a plausible-looking number with no indication anything was lost. PPTX equations were dropped outright. ODF equations survived but in an ad hoc notation (`(1)/(2)`) that no generator could render as maths. (#97)
- Table subtrees were rendered twice by the Markdown generator, making conversion time grow quadratically with nesting depth and duplicating any footnote inside a table cell. (#105)
- Paragraph-level text properties (bold, font size, colour, font family) in ODF documents were parsed into the style table but never applied to the paragraph's text, so they were absent from every generated output. (#104)
- ODF styles that explicitly turn formatting *off* (`fo:font-weight="normal"`, `style:text-underline-style="none"`, and the italic/strikethrough equivalents) were not recorded at all, so a span could not override an inherited paragraph style. LibreOffice writes exactly this whenever part of a bold paragraph is un-bolded. Such styles now appear in `metadata.styleMap` with the flag set to `false`, and a span carrying one clears the inherited value.
- **Formatting a heading or table header row already implies is no longer emitted twice.** A heading whose every run is bold produced `# **Heading**` in Markdown, and in RTF and HTML an inner font size that *overrode* the heading's own and visibly shrank it. Uniform bold/size inside a heading or header row is now dropped in favour of the element's own styling; partial emphasis (`# Normal **Bold** Normal`) is untouched, and colour, font and every other property still come through.
- Text inside PowerPoint grouped shapes (`<p:grpSp>`), including nested groups, was silently dropped. (#106)
- A crafted ODF table row carrying a large `table:number-rows-repeated` with no cells bypassed the per-document cell budget entirely and could exhaust memory.

### Added
- **Markdown output dialect** (`MdGeneratorConfig.dialect`): target a real-world flavor (`'github'`, `'gitlab'`, `'obsidian'`, `'pandoc'`, strict `'commonmark'`, or the default `'extended'`), or pass a `MarkdownDialectConfig` object to control admonitions, footnotes, citations, wikilinks, math, tables, list markers and emphasis per feature. The default is byte-identical to prior output.

Setting `modified` also makes EPUB output byte-stable across runs. Formats with a fixed metadata vocabulary (EPUB, RTF) warn on unrepresentable `custom` keys via `onWarning` rather than dropping them silently.
- **`subject` and `keywords` now reach generated output** (HTML `<meta>`, Markdown frontmatter, EPUB `dc:subject`, RTF `\info`); previously they were parsed but never written.

- **Footnotes degrade gracefully when disabled** (`dialect: { footnotes: false }`, or under `commonmark`): note content is inlined as a parenthetical at the reference point instead of being dropped.
- **`OfficeParserConfig.mdParserConfig`**: per-input-format parser config sub-object mirroring the generator side. Reserved for future use.
- **`AdmonitionMetadata.sourceSyntax`** (`'github' | 'gitlab'`): records which concrete syntax produced an admonition, for round-trip-aware tooling.
- **Expanded CommonMark / Markdown Extra parsing**: backslash escapes, reference-style links/images, underscore emphasis, multi-backtick inline code, setext headings, `<url>` autolinks, HTML entity and numeric-character-reference decoding, hard vs. soft line breaks, `~~~`-fenced and 4-space-indented code blocks, and list-item continuation lines.

### Fixed
- **Several Markdown constructs emitted document text without escaping** (math, wikilinks, citation keys, footnote ids, abbreviation definitions, image attribute lists, admonition types/titles), so a hostile document's markup could survive a parse-then-generate cycle intact. Each now escapes or allowlists its content.
- **A crafted ODF spreadsheet could exhaust memory.** `table:number-columns-repeated` / `table:number-rows-repeated` were expanded into AST nodes with no bound, so a few hundred bytes could materialize millions of cells. A per-document cap (`decompressionLimits.maxTableCells`, default 1000000) now clamps and warns instead of expanding without limit. Relatedly, repeated ODF rows/columns now **share their child and comment nodes by reference** in the AST (rather than deep-copying per repetition), which closes a byte-amplification and is a large memory win; a consumer that mutates a cell's children/comments in place will see the change on every repetition (the nodes are literally shared) - clone before mutating if that matters.
- **`abortSignal` could not interrupt work already in progress.** It was checked once per parser and honoured by only one generator; parsers now consult it through their content loops and all generators check during traversal.
- **`styleMap` class lists and attribute names were emitted unescaped/unvalidated** on the spreadsheet row and sheet paths, allowing attribute injection through a crafted mapping.
- **Config resolution could pollute `Object.prototype`** when a generator config was supplied via `JSON.parse` (a `__proto__` key reached the prototype through the recursive merge). Guarded.
- **`sanitizeCssValue` could be bypassed with CSS backslash escapes** (`u\rl(...)` reassembled into a live `url()` after the safety check); the escape strip now runs before the check.
- **RTF hyperlinks had no scheme allowlist**, so `javascript:`, `file://` and UNC targets were emitted verbatim; they are now restricted to the schemes HTML and Markdown already allow. **Behaviour change:** intranet `file://`/UNC links lose their clickable target (the link text is kept).
- **The HTML parser's nesting-depth guard never fired** (it tripped at 1000, but the stack overflowed around 800). Lowered to 256 so a deeply nested document raises the typed error instead of a `RangeError`.
- **`.to('text')`/`.to('md')` stripped genuine leading/trailing document whitespace** by trimming the whole output; only the generator's own separator artifact is stripped now (issue #102).
- **EPUB generation was not reproducible**: `dcterms:modified` and every zip entry's mtime defaulted to the current time, so the same AST produced different bytes each run. Both now derive from one resolved instant, falling back to the document's own modification date.
- **`.to('text')` dropped chart data series and CSV comments** (nodes carrying content in `text` with no children) and **concatenated adjacent table cells** with no separator (`ITEMNEEDED`). Both fixed.
- **The plain-text `renderMetadata` header could be forged**: a newline in a document's title rendered as extra `Key: value` fields. Line breaks are now folded to spaces.
- **Inline styles were matched by substring**, so `color:` matched inside `background-color:` and `max-width: 100%` was read as an explicit width, while spaceless and vendor-prefixed forms were missed. Replaced with a real declaration parser.
- **`csvSafeCell` tested its formula-injection trigger against the untrimmed value**, so a leading-space formula (`" =1+1"`) slipped through unprefixed.
- **Markdown parser correctness**: nested-list numbering leaking across siblings, an indentation-unit mismatch that doubled nesting depth on re-parse, `> >` blockquotes stripping only one `>` level, `)`-style ordered lists (`1) item`) not recognized, `----- text` misread as a horizontal rule, and short table separator rows (`|-|-|`) rejected.
- **Out-of-range numeric character references crashed the parser**: `&#999999999;` (Markdown `&#N;`/`&#xH;`, and XML entities via `xmlUtils.ts` used by e.g. `ExcelParser`) threw a `RangeError`; such references are now left as literal text.

### Changed
- **`styleMap`'s `output.tag` now takes effect in HTML output.** It was silently ignored (shadowed in every branch), while Markdown and RTF honoured it and the README documented it as working. A hostile tag is now rejected against an element allowlist. This also activates the built-in default style mappings for HTML, so a `Heading N`/`Quote`/`Title`-styled paragraph maps to the corresponding element instead of remaining a `<p>`.
- **Node.js 18/20 caveat.** Some hardening (notably the parser nesting-depth threshold) is calibrated against current Node; on 18/20 exact thresholds may differ, though failure stays graceful. Both remain supported until the next major version.
- **Documentation fix**: `TextGeneratorConfig.preserveLayout` defaults to `true`, not `false` as previously documented.

The boolean conflated three unrelated decisions (document shell, CSS delivery, script/injection emission) into one flag and emitted a *global, unscoped* stylesheet whenever `standalone: false` was combined with a fragment embedded in a host page. The object splits these into independently-controllable fields (`document`, `metaTags`, `styles` (`'full' | 'scoped' | 'none'`), `scripts`, `headInjections`, `bodyInjections`), each defaulting to its "on" (standalone) value when omitted, so `{ document: false }` alone yields a fully-styled fragment with just the `<html>` shell removed. ### Changed
- `HtmlGenerator`'s footnotes section now emits `data-footnotes=""` (an explicit empty value) instead of a bare `data-footnotes` attribute, so the markup is valid XHTML as well as HTML.
- **Behavior change: `standalone: false`**: previously emitted an HTML fragment containing a global, unscoped `<style>` block (leaking onto any host page it was embedded in). It now emits a genuinely bare fragment with no `<style>`/`<script>` at all, matching the new "every envelope part off" semantics. **The old output is not lost: it moved from `false` to `{ document: false }`:** because an object's omitted fields each default to their "on" value, `standalone: { document: false }` keeps the full (global, unscoped) stylesheet and the spreadsheet script while dropping only the document shell, reproducing the previous `standalone: false` output byte-for-byte in the common case (the sole difference being that `injections.bodyStart`/`bodyEnd` now apply to the fragment instead of being silently dropped). ### Fixed
- **Centralized Output Sanitization**: Added `src/utils/sanitize.ts` as the single source of truth for escaping AST-derived (untrusted document) text in every generator's output context, closing several injection gaps: HTML/XHTML text and attributes (`escapeHtml`/`escapeXml`), inline `<style>` CSS values (`sanitizeCssValue`: strips `url()`/`expression()`/`@import`/`javascript:` and CSS-breakout characters), `href`/`src` URLs (`sanitizeUrl`/`sanitizeImageUrl`: reject script-executing schemes, allow only `http(s)`/`mailto`/`tel`/relative/fragment, plus `data:image/*` for images), inline `<script>` JSON payloads (`serializeForInlineScript`: escapes `<`/`>` and U+2028/U+2029 so a document-supplied chart label can't close the script tag early), CSV cells (`csvSafeCell`: guards against formula/DDE injection per CWE-1236), RTF control words (`escapeRtf`), and Markdown text/URLs (`markdownEscapeText`/`sanitizeMarkdownUrl`). `CsvGenerator`, `EpubGenerator`, `HtmlGenerator`, `MarkdownGenerator`, `PdfGenerator`, and `RtfGenerator` all now delegate to these helpers instead of ad hoc per-generator escaping. Covered by a new `test/security/testSanitization.ts` regression suite (`npm run test:security`).
- **Zip Bomb Protection**: `extractFiles` (`src/utils/zipUtils.ts`) now decompresses via `fflate`'s streaming `Unzip`/`UnzipInflate` and caps `decompressionLimits.maxUncompressedBytes` against the *actual* inflated byte count as it streams in, instead of the ZIP header's declared (and attacker-controlled) `originalSize`; a crafted archive can understate that field and still inflate to gigabytes under the old declared-size check.
- **Denial-of-Service Hardening**:
  - `HtmlParser`'s tree builder no longer re-scans/re-lowercases the whole remaining document for every tag or `<script>`/`<style>` close tag (was `O(n²)` on documents with many tags); `parseNode` recursion is now capped at depth 1000, throwing the new `OfficeErrorType.MAX_NESTING_DEPTH_EXCEEDED` instead of overflowing the call stack on a maliciously deep element tree.
  - `MarkdownParser`'s MDX-unwrap fixed-point loop is capped at 100 passes, bounding the cost of a pathologically deep `<A><A>...</A></A>` input.
- **SSRF Hardening (PDF generation)**: `PdfGenerator`'s Puppeteer page now intercepts every network request and aborts anything that isn't an inline `data:`/`blob:` URI or the configured `htmlConfig.chartJsSrc` host. A warning is emitted when a resource is blocked.
- **PDF Parsing Hardening**: `PdfParser` now passes `isEvalSupported: false` to `pdf.js`, preventing its font/CMap fast-path from compiling attacker-controlled PDF content via `new Function`.
- **Markdown Round-Trip**: Standalone bookmark-anchor blocks (`<a id="x"></a>` on their own line, emitted by `MarkdownGenerator` just before a heading/paragraph) and table cells using the `<div style="text-align: X">` alignment fallback are now correctly folded back into `anchorIds` / cell alignment on re-parse, instead of surviving as escaped literal text on a save→reload cycle.
