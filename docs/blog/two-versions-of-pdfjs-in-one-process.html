Two Versions of pdf.js in One Process

Two copies of pdf.js on disk are fine. One global they both reach for is not: the first to start a worker names it there, and the other takes it, whatever its version.

HA
Harsh Ankur
Published 5 November 2026 · 7 min read

An application renders PDF pages with its own pdf.js, 6.4.299, and extracts their text with officeParser, which uses pdf.js 6.2.108. Both are fine on their own. Together, the second one to read a PDF fails: 

The API version "6.2.108" does not match the Worker version "6.4.299".

That was issue #128. The report asked whether officeParser could take a version range for pdfjs-dist, or make it a peer dependency, so the package manager installs one copy. This post is about why I did neither, what the clash really is, and how 8.6.0 runs two versions of pdf.js side by side in one Node process.

Reproducing It

Two packages in a scratch project: pdfjs-dist@6.4.299 for the application, and officeParser, which brings its own pdfjs-dist@6.2.108. npm installs both copies, one nested under officeParser. The application opens a page first, then asks officeParser for the text: 

import { readFileSync } from 'node:fs';
import { getDocument, version } from 'pdfjs-dist/legacy/build/pdf.mjs'; // the app's own pdf.js
import { parseOffice } from 'officeparser';

const file = readFileSync('report.pdf');

const doc = await getDocument({ data: new Uint8Array(file) }).promise;
await doc.getPage(1);
console.log(`app's pdf.js ${version}: ${doc.numPages} pages`);

try {
    const ast = await parseOffice(file);
    console.log(`officeParser: ${(await ast.to('text')).value.length} characters of text`);
} catch (error) {
    console.log(`officeParser: ${error.message}`);
}

On officeParser 8.5.0:

app's pdf.js 6.4.299: 8 pages
officeParser: [OfficeParser]: The API version "6.2.108" does not match the Worker version "6.4.299".

The other order fails too, the other way round. With officeParser reading first, in the same process (separateProcess: false), it is the application's pdf.js that breaks: 

officeParser: 9081 characters of text
app's pdf.js 6.4.299: The API version "6.4.299" does not match the Worker version "6.2.108".

One Global for Every Copy

pdf.js comes in two halves: the API you call (getDocument), and a worker that does the parsing. In a browser the worker is a real Web Worker, started from its own file. Node has no Web Workers, so pdf.js runs what it calls a fake worker: the worker's code, in the same thread, talking to the API through a port. To get that code it first looks for a worker someone has already loaded, on a global: 

static get #mainThreadWorkerMessageHandler() {
  try {
    return globalThis.pdfjsWorker?.WorkerMessageHandler || null;
  } catch {
    return null;
  }
}

Only if that is empty does it import the worker file it was told about, and either way it keeps the answer for good. The worker file, as it loads, puts itself on that global: 

globalThis.pdfjsWorker = {
  WorkerMessageHandler: WorkerMessageHandler
};

So the first copy of pdf.js to start a worker in a process names it on globalThis, and every other copy that starts one later finds it there and takes it, whatever its version. Then the worker checks the version of the API talking to it, finds another one, and refuses the document. That is the error.

The two copies on disk are not the problem. Two copies of most packages live side by side without noticing, because each keeps its state in its own modules. pdf.js's worker is shared through the one object every module in the process can see.

Why Not a Range, or a Peer Dependency

A range such as ^6.2.108 would have helped this report. npm would have seen that 6.4.299 fits it and installed one copy for both. But it only helps while the application's version fits the range: an application on 5.x or 7.x still gets two copies, and so does one using another package that brings its own pdf.js. And it hands the choice of officeParser's pdf.js to whatever else is installed.

That matters because what officeParser reads from a PDF depends on pdf.js's output, which changes between releases. Here is getMarkInfo(), which says whether a PDF is tagged, on the same tagged file, in four releases of pdf.js 6:

pdf.jsgetMarkInfo()Page 1 structure tree
6.2.108{"Marked":true,"UserProperties":false,"Suspects":false}1 top node
6.3.289{}1 top node
6.4.299{}1 top node
6.5.438{}1 top node

The structure is still there in every release, but the flag that announces it is gone from 6.3.289 on, in minor releases of the same major version. officeParser decides whether to trust a PDF's tags by that flag, so under a range, the same officeParser on the same file would read headings from the tags in one application and guess them from font sizes in another. When 6.3.289 came out, I tried it and reverted, because six tests of tagged PDFs failed. A peer dependency moves the same choice to every user, and asks each of them to find a version that works.

So pdfjs-dist stays pinned to the version officeParser is tested with. The pin keeps officeParser's output the same for everyone; the clash has to be fixed where it happens.

A Worker of Its Own

In Node, officeParser reads PDFs in a separate process by default, with its own memory limit. That process has a global of its own, so it was never part of the clash. Why did the first sample fail, then? Because 8.5.0 saw the application's worker on the global and took it for one the caller had loaded on purpose, for officeParser to use, and moved the parse into this process to use it. 8.6.0 takes a worker from that global only where pdf.js's worker file cannot be found, which is the case it is there for: a bundle that carries pdf.js inside it.

That leaves parses in this process: with separateProcess: false, or where a process cannot start. There, officeParser now gives its pdf.js a worker module of its own instead of sharing one:

  1. It imports its pdf.js's worker file at the same address with ?officeparser added. Node keeps modules by their full address, query included, so this is a separate instance of the module, even if the application imported the same file.
  2. Loading, that instance puts itself on globalThis.pdfjsWorker, as every copy does. officeParser puts the global back as it was straight away, so the application's pdf.js never sees it.
  3. It connects its pdf.js to that instance through a pair of ports in the same thread, the way pdf.js connects its own fake worker, and gives the API the port. An API given a port uses it and never looks at the global.

Here is a small check of the first two points, with nothing of officeParser in it: 

const plain = await import(workerFile);
const own = await import(`${workerFile}?officeparser`);
console.log('same module object:', plain === own);
console.log('global now names the second copy:', globalThis.pdfjsWorker.WorkerMessageHandler === own.WorkerMessageHandler);
same module object: false
global now names the second copy: true

The second line is why the global has to be put back: left alone, the application's pdf.js would take officeParser's worker from it the next time it started one.

Warnings That Belong to Someone

Sharing a worker also shared its warnings. pdf.js's worker keeps one warning level for every document it reads, in a variable inside its module, which a message can set and nothing can read back. officeParser raises it while it reads a PDF, to report pdf.js's warnings as its own, and 8.4.0 and 8.5.0 left it raised for the application's documents afterwards. With a module of its own, officeParser's level is its own, and the application's worker keeps whatever the application set.

The warnings themselves still arrive through console.warn, which both workers share. To tell its own from the application's, officeParser runs every message its worker receives inside a Node AsyncLocalStorage context, so a warning written anywhere inside that work, after any number of promises and timers, can be traced back to it. The application's warnings, printed outside it, reach the console as they always did.

The Same Script on 8.6.0

app's pdf.js 6.4.299: 8 pages
officeParser: 9081 characters of text

And officeParser first, in the same process:

officeParser: 9081 characters of text
app's pdf.js 6.4.299: 8 pages

Where It Still Shares

A bundle that inlines pdf.js, such as an ESM bundle for Node or an application shipped without node_modules, has no worker file for officeParser to import. There officeParser's own bundled worker goes on the global, and a pdf.js of another version in the same bundle would find it, as before. In that setup, use officeParser's version of pdfjs-dist. In a browser, pdf.js normally starts a real Web Worker from its own file, so the clash needs a worker loaded on the page itself.

And the pin has a cost of its own: officeParser's pdf.js moves only when I move it. The table above is also the plan for that. Before officeParser can take 6.4 or 6.5, it has to read a PDF's tags from the structure tree rather than from a flag that newer releases no longer set.
