The Answer Was in the Glyph's Name: When "nicht" Reads "ni!ht"

A font's encoding can name a glyph c.sc or T_h.alt, and with no map the text falls back to the code's own character. The name was the answer all along, so I read it, and reported it upstream.

HA
Harsh Ankur
Published 1 November 2026 · 5 min read

A page says nicht The café. Search for "nicht" in the PDF.js viewer and it says "Phrase not found". Search for "ni!ht" and it finds the word the page shows as "nicht". The drawing is right and the text behind it is wrong, and the answer is sitting in the file, in the name of the glyph.

I touched on this in the post on filled forms, where it turned up. This post is the whole of it: how a name can say what a glyph is, why the text comes out wrong without it, how officeParser reads it since 8.4.1, and the report I filed with pdf.js so that everyone using it can get the right text.

A File Small Enough to Read

I built one page with one font, an embedded subset with no /ToUnicode and this encoding: 

<< /Type /Encoding /BaseEncoding /WinAnsiEncoding
   /Differences [33 /c.sc 34 /T_h.alt 35 /uni00E9.sc] >>

The content stream draws the bytes ni!ht "e caf#. Most of those codes mean what WinAnsi says. The three in /Differences select glyphs by name instead: code 33, which WinAnsi calls "!", draws the font's glyph named c.sc, a small capital c. So the page shows the right word.

Reading it is a separate question. Here is pdf.js 6.2.108, the version officeParser uses, on that file: 

import { readFileSync } from 'node:fs';
import { getDocument } from 'pdfjs-dist/legacy/build/pdf.mjs';

const data = new Uint8Array(readFileSync('glyph-name-suffix.pdf'));
const doc = await getDocument({ data }).promise;
const text = await (await doc.getPage(1)).getTextContent();
console.log(JSON.stringify(text.items.map((i) => i.str).join('')));
"ni!ht \"e caf#"

With no name it knows and no map, each code falls back to its own character. Those are the bytes of the content stream, read as text.

What a Name Says

Glyph names look like private labels, but they aren't. The Adobe Glyph List specification gives rules for turning a name into text, so that software can do exactly this:

  1. Drop everything from the first period on. It is a variant's suffix: c.sc is c.
  2. Split the rest at underscores. They join the parts of a ligature: T_h is T and h.
  3. Read each part: a name in the list, or uniXXXX, or uXXXX up to six digits.
  4. The text is the parts in order.

So c.sc is "c", T_h.alt is "Th", and uni00E9.sc is "é". The specification even recommends names like these for new fonts, so suffixes are open-ended: c.alt, one.osf and A.swash all work the same way. A list of known names can never cover them, but the rule does.

pdf.js looks a name up whole, and knows some ligatures by name, such as T_h. It doesn't apply the rule, so c.sc and T_h.alt and uni00E9.sc get no mapping. Poppler does apply it, and pdftotext reads that file as nicht The café.

Where It Came From

I found this in an official German form, saved through macOS's Quartz, where "Nein, trifft nicht zu" read "Nein, trifft ni!ht zu". The blank form names the same glyph and gives its code a map entry: to a capital C, so it reads "niCht", which is the file's own doing. Quartz rewrites the subset's encoding and leaves that code out of its map. A map that leaves a code out behaves like no map at all, so any PDF with such names can go this way after passing through Quartz. These are ordinary files.

What officeParser Does

I can't change what pdf.js returns, so since 8.4.1 officeParser reads the encoding itself. pdf.js doesn't keep a font's encoding where its text is read. It can be asked to, but that sends every font's whole CMap, so officeParser reads the font's dictionary from the file, for simple fonts only. It matches each one to pdf.js's font by the order the page sets them, and reads a glyph by its name only where pdf.js read that glyph as its code's own character: 

const ast = await parseOffice(readFileSync('glyph-name-suffix.pdf'));
console.log((await ast.to('text')).value);
nicht The café

Those limits matter. A code the map does cover keeps what the map says. A composite font is left alone, and a name reads only if every part of it does, so a name like glyph_7 never turns into a stray character. The rule's own answer for an unknown part is an empty string, which is fine for a font's designer and bad for a reader. Beyond uniXXXX and uXXXX, the names officeParser knows cover Latin, Greek and the common marks and ligatures, not the whole list. And it can't do any of this in an encrypted file, whose streams it doesn't decrypt.

Fixing It Where It Belongs

All of that is a workaround in one library for something every pdf.js user meets: its viewer's search and text layer have the same problem, on the page that looks right. So I filed issue #22410 with pdf.js, with the small file, a form made from the official blank with made-up data, where in the code the names fall through, and the rule as a suggested change. With it applied to the worker of 6.2.108, that file reads correctly and draws the same, byte for byte. As I write this, the issue is open, and the decision is the pdf.js team's: one side effect I noted is that a non-embedded font's substitute glyphs could change. If it lands, officeParser's reading can go.

If you parse PDFs with pdf.js and see a stray "!" or "#" in the middle of a word, check the font's /Differences. A close relative of this, a composite font with no map at all and no names to read, is the subject of another post.
