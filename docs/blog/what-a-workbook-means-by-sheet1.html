What a Workbook Means by Sheet1

A workbook with a worksheet and a chart sheet holds two files called sheet1.xml. Telling them apart means following each tab to its part, and knowing which guesses a reader may make when a file spells a path its own way.

HA
Harsh Ankur
Published 9 November 2026 · 8 min read

Unzip an XLSX and you will find a file called sheet1.xml. Which tab is it? Not necessarily the first tab, not necessarily the one called Sheet1, and in a workbook with a chart on a sheet of its own, there can be two files of that name. The file name tells you almost nothing. The workbook says which part each tab is, and where it stands, in two other files.

officeParser 8.7.1 fixes three bugs in getting from a tab to its cells: sheets came out in the order of the files in the package instead of the order of the tabs, a chart sheet's name and hidden state landed on a worksheet that shared its file name, and a chart moved to a sheet of its own was read but placed nowhere. This post is about how a reader should follow a tab to its part, and about the lookup 8.7.1 uses when a target is not written the way its part is named.

Three Files Between a Tab and Its Cells

The tabs live in xl/workbook.xml, one <sheet> each, in the order the tabs are shown. A tab has a name, a state (shown, hidden or very hidden), and a relationship id: 

<sheets>
  <sheet name="Summary" sheetId="2" r:id="rId2"/>
  <sheet name="Sales" sheetId="1" r:id="rId1"/>
  <sheet name="Chart1" sheetId="3" state="hidden" r:id="rId3"/>
</sheets>

The id is looked up in the workbook's relationships, xl/_rels/workbook.xml.rels, which give each id a type and a target. The target is a path, read from the folder of the part that holds the relationship, here xl/: 

<Relationship Id="rId1" Type="…/worksheet" Target="worksheets/sheet1.xml"/>
<Relationship Id="rId2" Type="…/worksheet" Target="worksheets/sheet2.xml"/>
<Relationship Id="rId3" Type="…/chartsheet" Target="chartsheets/sheet1.xml"/>

Only then do you reach a part with cells in it. Nothing along the way ties a tab to a file name or a file number. sheet2.xml can be the first tab. Excel numbers chart sheets apart from worksheets, so a workbook with one of each holds worksheets/sheet1.xml and chartsheets/sheet1.xml. And the order of the files in the zip is whatever the program that wrote it chose: nothing in the format makes it the order of the tabs.

The Workbook I Built

I wrote a small workbook by hand, so I knew exactly what was in it. A Summary tab first, then a Sales tab with three months of figures, then a chart of those figures moved to a chart sheet of its own, Chart1, which I hid. In the package, the Sales part comes before the Summary part, the other way round from the tabs.

Then I listed the sheets officeParser returns, with each sheet's name, whether it is hidden, and the kinds of node it holds: 

const { OfficeParser } = require('officeparser');

(async () => {
    const ast = await OfficeParser.parseOffice('sales.xlsx', { extractAttachments: true });
    for (const sheet of ast.content) {
        console.log(sheet.metadata.sheetName, sheet.metadata.hidden ?? false, sheet.children.map(node => node.type).join(' '));
    }
})();

What Went Wrong, Step by Step

8.7.0 built a map from file name to tab name. For each relationship it kept only the last segment of the target, target.split('/').pop(), and for each tab it filed the tab's name, and whether it was hidden, under that file name. Summary went under sheet2.xml. Sales went under sheet1.xml. Then Chart1 went under sheet1.xml too, and wrote over Sales.

It then walked the files in the package, read each worksheet it met, and looked its name up by file name. xl/worksheets/sheet1.xml came first in the package, so it came first in the output, under the name Chart1, and hidden. The chart sheet itself was never read as a sheet: its chart reached ast.attachments and nothing in the content pointed to it.

For a long time the cost was a wrong name: tabs were keyed this way at least since 6.0. It became lost content in 8.3.0, when PDF output began to leave hidden sheets out, as a printout does. From then on, a worksheet that shared its file name with a hidden chart sheet was hidden too, and its figures were missing from the PDF. A native PDF of this workbook from 8.7.0 holds one line of text, Quarter total 360. The CSV shows the wrong name plainly:

February,150

# Sheet: Summary

Keyed by the Part

The first half of the fix came as a pull request from jihtsan (#133). It resolves each tab's target from the folder of the part that holds the relationship, so worksheets/sheet1.xml from xl/ is xl/worksheets/sheet1.xml, and so is an absolute target, /xl/worksheets/sheet1.xml. Tabs are filed under that path, so two kinds of sheet with the same file name stay two sheets. And the sheets are sorted by their place in xl/workbook.xml, with a worksheet part no tab names kept in its place in the package after them. Text, Markdown, CSV and chunks all follow the order of the content, so all of them follow the tabs now.

I took the same rule to every relationship a sheet or a drawing follows: its drawings, comments, pictures and charts are found by the path the target resolves to, not by a file name or a folder glued on in front.

A chart sheet is a sheet. With extractAttachments on, a chart sheet whose drawing holds a chart or a picture becomes a sheet node in its tab's place, under its own name and state, holding a chart node for the chart (or an image node for a picture). Hidden, it is left out of a PDF unless pdfConfig.printHidden is set; with it set, the native engine draws the chart. With attachments off, the content is what it was.

That is what found the things absolute targets used to lose. 8.7.0 built a comment's path by gluing xl/ to the target, so /xl/comments1.xml became xl//xl/comments1.xml, a part no package has. I gave the Sales sheet a comment that way. 8.7.0 dropped it. 8.7.1 puts it on the cell it belongs to. A drawing named by an absolute target went the same way in 8.7.0, and the pictures and charts on it with it.

When a Target Is Spelled Another Way

A file-name key had one virtue: it did not care which folder a target was written from. A target of xl/worksheets/sheet1.xml, written from the package's root instead of from xl/, still ended in sheet1.xml. Resolved properly, it names xl/xl/worksheets/sheet1.xml, which is not there. Read by path alone, such a sheet would lose its tab's name, state and place, and such a comment or drawing would be lost outright. So 8.7.1 looks for a part in three steps, and stops at the first that finds one:

  1. The part at the resolved path. A target written as the specification says is found here, and so is an absolute one.
  2. The same path, ignoring case. The package format does not tell part names apart by case, so Worksheets/Sheet1.xml names xl/worksheets/sheet1.xml.
  3. The file name, in the folder of its kind. The relationship's type says what kind of part it names, and each kind has its folder: a worksheet's is xl/worksheets/, a chart sheet's xl/chartsheets/. So a bare sheet1.xml finds a worksheet when the relationship is a worksheet's, and a chart sheet when it is a chart sheet's.

The third step is a guess, and the second, though the format allows it, can make two tabs name one part. Neither may take a part that is someone else's. So the second step never answers with a part that another tab, sheet or drawing names exactly, and the third never with one that another names exactly or but for case. Both rules came out of reviewing this fix before the release: without them, a tab whose own part was missing could take another tab's sheet. And a target whose part is not there finds nothing. The sheet it may have meant is not lost, though: a worksheet in xl/worksheets/ that no tab names is still read, after the tabs, under its file name.

What Changed

  • Sheets come out in the workbook's tab order, in every output (#130).
  • A sheet's name and hidden state are its own tab's, never those of a tab whose part shares its file name (#141).
  • With extractAttachments, a chart sheet's chart is placed in its tab (#142).
  • Comments behind absolute targets are attached, pictures and charts in a drawing named by one are placed, and a stray copy of a part elsewhere in the archive no longer stands in for the real one.

The whole list is in the changelog. If you have a workbook whose sheets still come out wrong, I would like to see it: open an issue with the file, or the smallest copy of it that shows the problem.
