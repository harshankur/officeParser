Document Chunking for Retrieval Done Right: Beyond Naive Token Windows

Teams tune embedding models and re-rankers while feeding them chunks that were cut in the wrong places. Here is what a fixed-size splitter does to a real document, and what chunking on the document's structure fixes.

HA
Harsh Ankur
Published 4 October 2026 · 5 min read

In Retrieval-Augmented Generation (RAG), the quality of the answer is bounded by the quality of what was retrieved. If the relevant passage never reaches the context window, no amount of prompt engineering will produce it.

Yet a great many pipelines still ingest documents with some variation of this: 

// The usual first attempt:
const text = extractRawText(file);
const chunks = recursiveTextSplitter(text, {
    chunkSize: 500,
    chunkOverlap: 50,
});

For prose this is tolerable. For office documents, with their tables and nested headings, it loses exactly the parts that matter. Here is why.

The Anatomy of Chunking Failure

A window of fixed size sliding over a string is blind to structure. It cuts wherever the count runs out:

1. The Table Shredder

Take a financial table with a header row and a row per quarter. The window fills up partway through, and the splitter cuts there:

  • Chunk 1 holds the header row and the first three quarters.
  • Chunk 2 starts with: | Q4 | 47,310 | 19.0% |.

Chunk 2 has lost its column names. When someone asks "What was the operating margin in Q4?", the words "operating margin" appear only in chunk 1, so chunk 2 is a poor match for the query. And if it is retrieved anyway, the model has no way to know what 19.0% measures.

2. The Orphaned Heading

A heading is the context for everything under it. A fixed window often leaves the heading at the end of one chunk and its content at the start of the next: 

[End of chunk 24]
... in accordance with regional regulations.
4.2 Data Retention Exceptions

[Start of chunk 25]
Medical records must be archived for a minimum of 7 years.
All audit trails must be immutable.

Retrieve chunk 25 alone and nothing says that "7 years" is about data retention exceptions and not about, say, ordinary log storage.

The Fix: Chunk the Structure, Not the String

Both failures come from the same place: by the time the splitter runs, the structure is already gone. The fix is to chunk before flattening, while a table is still a table and a heading is still a heading.

Three rules for structural chunking
  1. Cut at structural boundaries. Between paragraphs, sections, pages, or slides. Never in the middle of a table row.
  2. Carry the heading. Every chunk should know which heading it sits under, ideally the whole path of headings above it.
  3. Repeat table headers. When a table is too big for one chunk, every piece should start with the header row.

What officeParser's Chunker Does

officeParser parses every format into one tree, so its chunker works on nodes, not characters. You reach it with ast.to('chunks'): 

import { parseOffice } from 'officeparser';

const ast = await parseOffice('service-agreement.docx');

const { value: chunks } = await ast.to('chunks', {
    chunksConfig: {
        strategy: 'document-structure',  // the default
        splitBy: 'heading',  // or 'paragraph', 'page', 'slide', 'sheet'
        maxChunkSize: 1500,
        tableSplitStrategy: 'row',       // repeat the header row
    },
});

Here is real output for a short Markdown document: a paragraph under the heading "3.2 Uptime Credits", followed by a four-row table that I forced to split by setting a small maxChunkSize. The chunks for the headings themselves are left out: 

[
  {
    "text": "If monthly uptime falls below 99.9%, the customer is
             entitled to a 10% credit. Below 99.0%, a 25% credit
             applies.",
    "metadata": {

      "closestHeading": "3.2 Uptime Credits"
    }
  },
  {
    "text": "| Quarter | Revenue | Operating margin |
             | Q1 | 41,900 | 16.2% |
             | Q2 | 43,750 | 17.1% |
             | Q3 | 45,200 | 18.4% |",
    "metadata": {
      "sourceType": "md",
      "closestHeading": "3.2 Uptime Credits",
      "isTableChunk": true
    }
  },
  {
    "text": "| Quarter | Revenue | Operating margin |
             | Q4 | 47,310 | 19.0% |",
    "metadata": {
      "sourceType": "md",
      "closestHeading": "3.2 Uptime Credits",
      "isTableChunk": true
    }
  }
]

(The long strings are wrapped here to fit the page.) Measured against the three rules:

  • Rule 1, boundaries: done, with one exception. Chunks follow the tree, and a table is cut between rows. A single row longer than maxChunkSize is cut inside, because no chunk could hold it whole.
  • Rule 3, table headers: done. The second table chunk begins with the header row, so the Q4 figures still have their column names. isTableChunk marks both pieces.
  • Rule 2, headings: partly. Each chunk records its closestHeading, along with pageNumber, slideNumber, or sheetName where the format has them. But it is the nearest heading only, not the full path above it, and it lives in the metadata, not in the text that gets embedded.

Putting the Heading Where the Embedding Can See It

If the heading is only in metadata, the embedding model never sees it. Prepend it yourself. A heading is also emitted as a chunk of its own, so skip the case where a chunk is its heading: 

for (const chunk of chunks) {
    const heading = chunk.metadata.closestHeading;
    const textToEmbed = heading && heading !== chunk.text
        ? `${heading}\n\n${chunk.text}`
        : chunk.text;

    // Embed textToEmbed. Store chunk.metadata next to the vector,
    // for filtering and for citations.
}

Sizes in Tokens, and Other Strategies

Sizes are counted in characters by default. To count tokens, pass a lengthFunction: your tokenizer's counter goes in, and maxChunkSize becomes a token budget.

Two more strategies are there when structure is not what you want. fixed-size is the familiar recursive splitter with overlap. semantic cuts where the topic shifts, using an embedding function that you supply.

Measure It on Your Own Documents

I am not going to quote a benchmark here. Retrieval numbers do not travel well between corpora, and the only result that matters is the one on your documents. What I can offer is the experiment worth running on your own files:

  1. Collect a few dozen real questions, and make sure some can only be answered from a table.
  2. For each question, note which passage of which document holds the answer.
  3. Index the documents twice: once with a fixed-size splitter, once with structural chunks.
  4. For each index, count how often the right passage shows up in the top results.

Pay attention to the table questions. That is where the two approaches differ most, and where a wrong answer is hardest to notice.

Summary

Stop treating documents as strings of characters. The structure an author put into a document is information, and a retrieval pipeline that flattens it first is working with less than it was given.

Cut at boundaries, keep tables whole or repeat their headers, and make sure every chunk knows where in the document it came from.
