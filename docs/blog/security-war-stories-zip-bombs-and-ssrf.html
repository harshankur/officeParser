Security War Stories: Decompression Bombs, SSRF, and Hardening an Office Parser

A parser's whole job is to open files that someone else built. Here are four ways a crafted document attacked officeParser, and what the code does about each one now.

HA
Harsh Ankur
Published 4 October 2026 · 7 min read

When your application accepts uploaded Word documents, spreadsheets, or PDFs, it is not just reading text. It is running an interpreter over files that someone else built, and that someone may be an adversary.

These are four problems I found and fixed in officeParser. For each one: how the attack works, what the library used to do, and what it does now. All four are in the changelog.

War Story 1: The ZIP Header That Lies

Every modern office document (.docx, .pptx, .xlsx, .odt) is a ZIP archive, so decompression is the first code an upload reaches.

The classic threat is the decompression bomb. The well-known 42.zip is 42 kilobytes and unpacks, through layers of nested archives, to 4.5 petabytes. Nesting is not even needed: in 2019 David Fifield showed that a single non-recursive archive can reach a ratio above 28 million to one by making its files overlap.

Why Checking the Header Fails

The obvious defence is to read the uncompressed size from the ZIP header and refuse anything too big: 

// Looks safe. Is not.
if (entry.uncompressedSize > 50 * 1024 * 1024) {
    throw new Error('File too big');
}

That field is written by whoever made the archive. An attacker declares 1,024 bytes and ships a DEFLATE stream that inflates to gigabytes. The parser trusts the header, starts inflating into memory, and the process dies.

officeParser used to make exactly this mistake: its size limit was checked against the declared size.

What officeParser Does Now

Archives are inflated as a stream, and the limit is applied to the bytes that actually come out. The moment the running total crosses the limit, extraction stops with ZIP_SIZE_LIMIT_EXCEEDED. The number of entries is capped too (ZIP_ENTRY_COUNT_LIMIT_EXCEEDED). Both limits are yours to tighten: 

const ast = await parseOffice(upload, {
    decompressionLimits: {
        maxUncompressedBytes: 64 * 1024 * 1024, // default: 512 MB
        maxZipEntries: 2000,                    // default: 10,000
    },
});

Entries are held in memory and never written to disk by the library, so a path-traversal name such as ../../etc/passwd has nowhere to go.

War Story 2: SSRF Through PDF Rendering

Server-Side Request Forgery (SSRF) means tricking a server into making a request the attacker could not make directly. The usual target is something only the server can reach, such as an internal service or the cloud metadata address 169.254.169.254, which on a carelessly configured instance hands out credentials.

How a Document Carries the Request

Documents are full of URLs. A Word file can point an image at an external address: 

<!-- Inside word/_rels/document.xml.rels -->
<Relationship Id="rId9"
    Type=".../relationships/image"
    Target="http://169.254.169.254/latest/meta-data/"
    TargetMode="External"/>

HTML does the same with <img src="...">. None of this matters while the URL stays a string. It matters the moment something fetches it.

officeParser's parsers never fetch a URL found in a document. A remote image stays a URL in the AST. The hole was on the output side. The default PDF engine builds HTML from the document and renders it in headless Chromium through Puppeteer. Chromium did what browsers do: it loaded every image and stylesheet the HTML referenced, from the server it was running on.

What officeParser Does Now

The PDF generator intercepts every request the page makes. Inline data: and blob: URIs are allowed, and so is the one host configured for the chart library. Everything else is aborted, and a warning reports that a remote resource was blocked. It blocks all remote loads and does not try to filter by address. A filter for "internal" addresses is easy to get wrong, and a converted PDF has no need to reach the network.

Links are handled separately. On output, a document's link targets pass through a scheme allowlist (http, https, mailto, tel, and relative links), so a javascript: link in an uploaded file does not survive into generated HTML.

War Story 3: A Few Hundred Bytes, Millions of Cells

OpenDocument has an attribute for compressing runs of identical cells: 

<table:table-row>
  <table:table-cell><text:p>Start</text:p></table:table-cell>
  <table:table-cell table:number-columns-repeated="1048576"/>
</table:table-row>

It exists for a good reason. LibreOffice routinely writes table:number-rows-repeated="1048566" to say "the rest of the sheet is empty". But a parser that takes the number at its word runs this: 

for (let i = 0; i < repeated; i++) {
    row.cells.push(new Cell());
}

Rows repeat too, and the two multiply. The ZIP limits cannot help, because the XML is tiny and the expansion happens later, while the tree is being built. officeParser expanded these attributes without a bound, so a few hundred bytes could ask for millions of nodes. After I fixed that for sheets, the same attribute turned up in a chart's embedded table: a 1.3 KB document that repeated one cell 100,000,000 times ended the process out of memory.

The fix could not be "cap the attribute", because that breaks real spreadsheets. What is bounded instead is what gets built:

  • A document may materialize at most maxTableCells cells (default 1,000,000, plus one for each byte of the file, so a large real spreadsheet is not cut short). Past that the parser clamps and warns once.
  • A repeated empty cell builds nothing and is skipped in one step. Looping over it was a CPU attack of its own.
  • Repeated rows and columns share their child nodes; they are not deep copies.
  • maxRepeatedContent (default 16,777,216 characters, plus 16 for each byte of the file) bounds the total content a document may repeat by reference.

War Story 4: Nesting That Runs the Stack Out

XML lets elements nest, and an attacker can nest the same element thousands deep: 

<w:p>
  <w:hyperlink>
    <w:hyperlink>
      <w:hyperlink>
        ... thousands of levels ...
      </w:hyperlink>
    </w:hyperlink>
  </w:hyperlink>
</w:p>

This one bit twice. The first problem was time. Every level of nested hyperlink applied its link to every run inside it, so the work grew with depth times runs. A 23 KB file with 1,000 levels around 400,000 runs took 17 seconds. Now the outermost hyperlink applies its link once.

The second problem was the call stack. A recursive reader that goes deep enough throws RangeError: Maximum call stack size exceeded, and until 8.1.0 that surfaced as a generic "file corrupted" error. How deep is "deep enough" is not a constant. It depends on the engine, the stack size, and even on whether the code has been optimized yet. On Node 25 I measured this traversal running out somewhere between 900 and 1,000 levels in a fresh process.

The 512-level guard

Since 8.1.1 the Word parser counts depth inside a paragraph and stops at 512 levels, well before the stack is at risk. HTML has had a 256-level cap since 7.4.0, and RTF since 8.1.0. Other deep nesting, such as tables inside table cells, still relies on catching the stack overflow. Either way the caller gets the same typed error: 

try {
    await parseOffice(upload);
} catch (err) {
    if (err.officeIssue?.code === 'MAX_NESTING_DEPTH_EXCEEDED') {
        // The input was built to be deep. Reject it.
    }
}

The Baseline, and Its Limits

Beyond those four stories, this is what the library does as a matter of course:

  • Every generator escapes what it writes. Document text is attacker-controlled, so each output has its own escaping: HTML and CSS, URLs, RTF control words, LaTeX commands, Markdown, and CSV formulas.
  • Limits apply to real work, not declared sizes: inflated bytes, ZIP entries, table cells, XML elements, and repeated content.
  • Prototype pollution is closed. A list id of __proto__ in a crafted document once reached Object.prototype through a counter map. Those maps now have no prototype, and the keys __proto__, constructor, and prototype are never copied from a caller's config.
  • The security suite has more than 1,200 checks in test/security/testSanitization.ts. It is part of npm test, which CI runs on every push to master and on every pull request against it.

None of that is a guarantee. I am the sole maintainer, and a parser this size has attack surface I have not found yet. If you process untrusted files, run the parse somewhere you can afford to lose: a worker or container with memory and time limits and low privileges. Use decompressionLimits and abortSignal. Do not rely on any one library's hardening as your whole defence.
