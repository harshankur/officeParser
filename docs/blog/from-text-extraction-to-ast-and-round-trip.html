From String Scraping to AST: The Architectural Evolution of officeParser

For more than six years officeParser returned a string. Here is why that stopped being enough, what replaced it, and the rule that has governed every feature since.

HA
Harsh Ankur
Published 4 October 2026, updated 27 October 2026 · 3 changes · 6 min read

Every library starts with a narrow problem. I wrote the first version of officeParser in 2019 to do one thing: get the text out of Word and PowerPoint files in Node.js, with no LibreOffice to install, no Python to spawn, and no Java bridge.

That first version did exactly that and nothing more. It unzipped the file, parsed document.xml, collected every piece of text it found, and joined the pieces with spaces. You got one flat string.

It was small and it solved the immediate need. Excel and OpenDocument support followed within a week. For years, a flat string was the whole product. Then documents started feeding search indexes and language models, and the flat string became a dead end.

What a Flat String Loses

Consider what happens when you reduce a financial report or a contract to one string:

  • Tables collapse. The cells of a five-column balance sheet become a run of numbers, and which number belonged to which row and column is gone.
  • The outline disappears. A chapter title looks the same as a bullet point three levels down.
  • Links and references vanish. A hyperlink keeps its words and loses its target. A footnote lands wherever the file happened to store it.
  • Code and math lose their edges. Nothing marks where a formula starts or stops.
Why this matters more with LLMs

A language model leans on structure: headings, lists, and tables tell it what belongs together. Hand it a table flattened into a line of numbers and it has to guess which figure answers the question. The information was in the document. The extraction threw it away.

The Pivot: Documents as Compilers See Them

The way out was to stop treating this as a string problem and treat it as a compiler problem.

A compiler does not translate source code to machine code with search and replace. It parses the source into an Abstract Syntax Tree (AST) that captures what the program means, independent of how it was written down.

Documents work the same way. A table may be written as WordprocessingML (<w:tbl>), OpenDocument (<table:table>), HTML (<table>), Markdown (| col |), or LaTeX (\begin{tabular}). The thing being described is the same every time: rows of cells.

The Shape of the Tree

Version 6 (January 2026) replaced the string with a tree. Every parser returns the same structure: 

OfficeParserAST
├── type         'docx' | 'pptx' | 'pdf' | 'md' | ... (14 formats)
├── metadata     title, author, created, modified, ...
├── content      OfficeContentNode[]
├── auxiliary    headers, footers, slide masters, PDF outline
├── attachments  images and charts (with extractAttachments)
├── warnings     non-fatal issues found while parsing
└── to(format)   generate another format from this tree

Each content node has a type, its text, its children, and optional formatting and metadata. The node types are a closed set: 

type OfficeContentNodeType =
    | 'paragraph' | 'heading' | 'list' | 'text' | 'break' | 'code'
    | 'table' | 'row' | 'cell'
    | 'image' | 'chart' | 'drawing' | 'embed'
    | 'slide' | 'sheet' | 'page' | 'slideMaster'
    | 'note' | 'comment' | 'header' | 'footer'
    | 'admonition'
    | 'definitionList' | 'definitionTerm' | 'definitionDescription';

A table is always table, then row, then cell, whichever format it came from. Footnotes and speaker notes hang off the node that refers to them (node.notes), and so do comments (node.comments).

Hub and Spoke: Why Generation Came Next

Once every format parses into one tree, conversion stops being a matrix. Without a shared tree, converting between formats means writing a translator for every pair: 

DOCX -> Markdown     PPTX -> Markdown
DOCX -> HTML         PDF  -> HTML
ODT  -> DOCX         ... one per pair

With the tree in the middle, each format needs at most two pieces: a parser that produces the tree and a generator that consumes it. 

DOCX   PPTX   PDF   Markdown   LaTeX
   \     |     |      |        /
    v    v     v      v       v
        [ OfficeParserAST ]
    /    |     |      |       \
   v     v     v      v        v
DOCX   HTML   PDF   Markdown   chunks

The Round-Trip Rule

Generation brought a rule I now hold every feature to:

A feature is not done until it round-trips

What a parser captures, the matching generator must be able to write back. The test suite checks it directly: parse a sample, generate the same format from the tree, parse the result, and compare what the two trees hold.

That rule is about one format at a time. Across formats, conversion is only as lossless as the target allows. Markdown has no merged cells, so a table with spans is written as an HTML table inside the Markdown. Plain text has no links. Where a target cannot say something, the generator falls back to the closest thing it can say.

Holding to the rule surfaced a long list of details that a text extractor never has to care about:

  • Merged cells (rowSpan, colSpan) surviving between Word, OpenDocument, and HTML tables.
  • List numbering that keeps counting when a list is interrupted by an ordinary paragraph.
  • Bookmarks and heading anchors (anchorIds), so internal links still land.
  • Guarding formula characters in CSV output without corrupting cells that are just negative numbers.

No Office Suite Required

One constraint from 2019 is still in place: parsing needs nothing but the npm package. There is no LibreOffice, no Java, and no Python behind it.

Parsing is JavaScript all the way down. PDF reading uses pdf.js, and OCR uses Tesseract compiled to WebAssembly. That is also why the same code runs in a browser, from a bundle of about 5.5 MB6 MBUpdated 27 Oct 2026 for 8.3.0. The browser bundle was about 5.5 MB when this post went out, and grew to about 6 MB with this release. All revisions, so a file can be parsed without leaving the user's machine.

There is one place where I traded that purity for fidelity, and it is opt-out. The default PDF output engine renders through headless Chromium (Puppeteer, an optional peer dependency), because a browser's layout engine gives the most faithful page. If you do not want a browser, the native engine writes PDF directly with pdf-lib, with simpler layout and the standard PDF fonts, in the standard PDF fonts or in fonts you give itUpdated 27 Oct 2026 for 8.2.0. The native engine now also draws in TrueType and OpenType fonts you give it, for any script. All revisions.

Trade-off Wrapping an office suite officeParser
Install System packages, fonts, and a process to manage One npm package
Runs in the browser No Yes
Page layout fidelity High: it runs a real layout engine Structure, not pixels
What you get back A converted file A typed tree you can inspect, filter, and convert

The third row is a real cost. Where officeParser is the wrong tool covers it and the other jobs this design does not do.

Looking Back

Moving from a string to a tree was not a refactor. It changed what the library is for. Reading a .docx, turning Markdown into a Word report, and chunking a PDF for retrieval look like three features. They are one tree with different things attached to each end.
