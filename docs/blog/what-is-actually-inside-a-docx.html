What is Actually Inside a .docx File? An Architectural Deep Dive

Most developers assume a Word document is styled text in a zip archive. It is closer to a small database: parts tied together by relationships, text split into runs, lists defined in another file, and text boxes nested inside drawings.

HA
Harsh Ankur
Published 4 October 2026 · 7 min read

If you rename any .docx file to .zip and unpack it, you do not find a simple text document. You find a small filesystem governed by ECMA-376 and ISO/IEC 29500, together known as Office Open XML (OOXML).

To read or write these files reliably, you have to look past what the editor shows and understand the data model underneath. Here is a tour of what is actually inside that archive, followed by what officeParser makes of it.

1. The Outer Shell: Open Packaging Conventions (OPC)

A .docx file is an Open Packaging Conventions (OPC) package: a ZIP archive holding data streams called parts, plus XML files called relationships that say how the parts refer to each other.

A minimal unpacked Word document looks roughly like this: 

my-document.docx/
├── [Content_Types].xml        # Content type of every part
├── _rels/
│   └── .rels                  # Package-level relationships
├── docProps/
│   ├── core.xml               # Title, author, created, modified
│   └── app.xml                # Application, page and word counts
└── word/
    ├── document.xml           # The main content
    ├── styles.xml             # Style hierarchy and defaults
    ├── numbering.xml          # List definitions
    ├── settings.xml           # Compatibility and editing settings
    ├── fontTable.xml          # Fonts the document uses
    ├── theme/
    │   └── theme1.xml         # Theme fonts and colours
    └── _rels/
        └── document.xml.rels  # Images, hyperlinks, headers, footers

Two structural patterns matter here:

  • Parts are found by relationship, not by path. The specification does not say the main text lives in word/document.xml. A strict consumer reads _rels/.rels and follows the relationship whose Type ends in /relationships/officeDocument. In practice Word and LibreOffice both write the main part at word/document.xml, and that is where officeParser looks for it.
  • Content types are declared. [Content_Types].xml gives the type of every part, by extension or by part name. Leave a part out and Word will usually report the file as corrupt.

2. The Content Core: WordprocessingML

The body of the document lives in word/document.xml. The root element is <w:document>, which holds one <w:body>. Inside the body, content is a sequence of block-level elements, mainly paragraphs (<w:p>) and tables (<w:tbl>).

The Fundamental Primitive: Runs (<w:r>)

A paragraph in Word is not a string with markup tags in it. It is a container of runs (<w:r>). A run is a stretch of text that shares one set of formatting properties.

Consider a sentence as simple as: "The quick brown fox." You might expect: 

<w:p>
  <w:r><w:t xml:space="preserve">The </w:t></w:r>
  <w:r>
    <w:rPr><w:b/></w:rPr>
    <w:t>quick</w:t>
  </w:r>
  <w:r><w:t xml:space="preserve"> brown fox.</w:t></w:r>
</w:p>

Run Fragmentation

Word often does not produce runs that clean. If the user paused, fixed a typo, ran the spell checker, or moved the cursor away and back, the same sentence can come out in more pieces, with markers between them: 

<w:p>
  <w:r><w:t xml:space="preserve">The </w:t></w:r>
  <w:proofErr w:type="spellStart"/>
  <w:r><w:rPr><w:b/></w:rPr><w:t>qui</w:t></w:r>
  <w:bookmarkStart w:id="0" w:name="_GoBack"/>
  <w:r><w:rPr><w:b/></w:rPr><w:t>ck</w:t></w:r>
  <w:proofErr w:type="spellEnd"/>
  <w:r><w:t xml:space="preserve"> brown </w:t></w:r>
  <w:r><w:t>fox.</w:t></w:r>
</w:p>

The word "quick" is now two runs. Anything that searches one <w:t> at a time will miss it. This is also why a template placeholder such as {{customer_name}} so often fails to match: Word has stored it as {{cust, omer_, and name}} in three separate runs.

3. Numbering and Lists: The Disconnected Graph

Engineers coming from HTML or Markdown are usually surprised by how Word stores lists. In HTML a list is an explicit, self-contained element: <ol><li>First</li></ol>.

In WordprocessingML, there is no list element. Every list item is an ordinary paragraph whose properties (<w:pPr>) point into a separate file, word/numbering.xml. 

<!-- Inside word/document.xml -->
<w:p>
  <w:pPr>
    <w:numPr>
      <w:ilvl w:val="0"/>   <!-- Indent level 0 -->
      <w:numId w:val="2"/>  <!-- Numbering instance 2 -->
    </w:numPr>
  </w:pPr>
  <w:r><w:t>First bullet item</w:t></w:r>
</w:p>

To learn what bullet or number goes in front of that paragraph, a reader follows a three-step chain:

  1. Find <w:num w:numId="2"> in word/numbering.xml.
  2. Read its <w:abstractNumId w:val="4"/> pointer.
  3. Look up <w:abstractNum w:abstractNumId="4">, find the level <w:lvl w:ilvl="0">, and read its <w:numFmt> (for example bullet or decimal) and its <w:lvlText w:val="%1."/> template.

The file never says "this item is number 3". Items of one list can be separated by other paragraphs or tables, so a reader has to keep its own counters as it walks the document.

4. Tables: Grids, Merges, and Nesting

A Word table (<w:tbl>) declares a column grid (<w:tblGrid>), then rows (<w:tr>) of cells (<w:tc>).

Concept OOXML markup What it means
Column spans <w:gridSpan w:val="N"/> The cell covers N grid columns, like HTML colspan.
Vertical merges <w:vMerge w:val="restart"/>, then <w:vMerge/> There is no rowspan="N". The first row marks restart, and every row below repeats the cell with an empty <w:vMerge/>.
Unsplittable rows <w:cantSplit/> The row may not break across pages.
Nested tables <w:tc><w:tbl>...</w:tbl></w:tc> A cell can hold a whole table.

5. Text Boxes and Drawings: The Detached Canvas

Floating shapes and text boxes are one of the most common sources of missing text in simple extractors. A text box does not sit in the paragraph stream as text.

Word anchors a DrawingML element (<w:drawing>) or a legacy VML element (<w:pict>) inside a run, and the text sits deep inside it: 

<w:p>
  <w:r>
    <w:drawing>
      <wp:anchor>
        <a:graphic>
          <a:graphicData uri=".../word/2010/wordprocessingShape">
            <wps:wsp>
              <wps:txbx>
                <w:txbxContent>
                  <w:p>
                    <w:r><w:t>Text inside a floating box</w:t></w:r>
                  </w:p>
                </w:txbxContent>
              </wps:txbx>
            </wps:wsp>
          </a:graphicData>
        </a:graphic>
      </wp:anchor>
    </w:drawing>
  </w:r>
</w:p>

(The full namespace is http://schemas.microsoft.com/office/word/2010/wordprocessingShape.) <w:txbxContent> is a nested document body with its own paragraphs, runs, and tables. An extractor that only walks the paragraphs directly under <w:body> misses every sidebar, callout, and caption drawn this way.

There is a second trap. For older readers, Word usually writes the same text box twice inside an <mc:AlternateContent> element: once as the modern shape, once as a VML fallback. An extractor that reads both branches returns the text twice.

6. Field Codes: The Inline State Machine

Page numbers, dates, cross-references, tables of contents, and some hyperlinks are fields. Word has two ways to write one:

  • Simple fields: <w:fldSimple w:instr="PAGE"> wraps the cached result in one element.
  • Complex fields: a sequence of runs marked by <w:fldChar>:
    1. <w:fldChar w:fldCharType="begin"/>
    2. <w:instrText>HYPERLINK "https://example.com"</w:instrText>
    3. <w:fldChar w:fldCharType="separate"/>
    4. Runs holding the cached visible text: <w:r><w:t>Visit site</w:t></w:r>
    5. <w:fldChar w:fldCharType="end"/>

Fields can nest (an IF field can contain a DATE field), so a reader has to track where each one begins and ends. An extractor that simply takes every text node in the XML returns the instruction (HYPERLINK "https://...") as if it were prose.

What officeParser Makes of All This

parseOffice reads the package and returns a typed tree, the same shape for every format the library supports: 

import { parseOffice } from 'officeparser';

const ast = await parseOffice('quarterly-report.docx');

ast.content;   // paragraphs, headings, lists, tables, ...
ast.metadata;  // title, author, created, modified, ...

const { value: markdown } = await ast.to('markdown');
const { value: chunks } = await ast.to('chunks');

Here is what the fragmented paragraph from section 2 becomes. This is real output: 

{
  "type": "paragraph",
  "text": "The quick brown fox.",
  "children": [
    { "type": "text", "text": "The ", "formatting": {} },
    { "type": "text", "text": "qui", "formatting": { "bold": true } },
    { "type": "text", "text": "ck", "formatting": { "bold": true } },
    { "type": "text", "text": " brown ", "formatting": {} },
    { "type": "text", "text": "fox.", "formatting": {} }
  ],
  "metadata": {}
}

I keep every run as its own text node, with its formatting, so nothing Word recorded is thrown away. The paragraph's own text is the joined string, so search and extraction never see the fragmentation. And the generators merge neighbours that share formatting: ast.to('markdown') writes that paragraph as The **quick** brown fox.

For the rest of the tour:

  • Lists become list nodes carrying listId, listType, indentation, and itemIndex. The index keeps counting when a list is interrupted by an ordinary paragraph, so numbering stays correct.
  • Tables follow table, row, cell, with rowSpan and colSpan worked out from vMerge and gridSpan. A cell can hold another table.
  • Text boxes, content controls, and SmartArt are read where they stand, after the paragraph that draws them. Of the two copies in an AlternateContent, one is read.
  • Headings come from the paragraph style (Heading1, Title, and so on).
  • Tracked changes: inserted text is read, text deleted or moved away is not.
  • Templates: OfficeTemplate.render fills {{placeholders}} even when Word has split one across several runs.

It does not cover every corner of a specification that runs to more than 6,000 pages. The capability matrix in the README lists what each format gives you, and a separate article covers the jobs officeParser is the wrong tool for.
