Text That Looks Real: A PDF Font With No Map

A font with no map from its glyphs to characters gives text that looks real. The only evidence is a character that should not be there, which is also the one thing I had started removing.

HA
Harsh Ankur
Published 1 November 2026 · 6 min read

Extract the text of some PDFs and a line that says "Hi there" on screen comes out as +LWKHUH. There is no error and nothing is missing: the right number of letters, on the right line, in the right place. It just isn't what the page says, and nothing in the string tells you so.

This post is about why that happens, why the file cannot always tell you, and what officeParser 8.5.0 does about it: a warning, PDF_FONT_UNMAPPED, that names the font and its pages. It also says what the warning misses, because a caller may throw text away on it.

Codes, Glyphs and Characters

A PDF does not store text as characters. A page's content stream draws codes in a font: 

BT /F1 12 Tf 72 700 Td <002B004C00030057004B004800550048> Tj ET

To draw, a viewer only needs to turn each code into a glyph, a shape in the font. A code with no meaning beyond "shape number 43" draws perfectly. To read, something has to say which character that shape is, and that is the job of a font's /ToUnicode map. It is optional, because a page looks the same without it.

The font that breaks is a composite one with the encoding /Identity-H, whose two-byte codes are simply glyph numbers, and no /ToUnicode: 

<< /Type /Font /Subtype /Type0 /BaseFont /ABCDEF+Arial
   /Encoding /Identity-H /DescendantFonts [6 0 R] >>

With nothing to go on, pdf.js reads each code as the character of that number. I embedded Arial this way and drew "Hi there" in its glyph numbers. In Arial, "H" is glyph 0x2B, and 0x2B is "+". The letters are all 29 places out, so "i" becomes "L" and "t" becomes "W". That is the whole of +LWKHUH. In a font that was renumbered when it was subset, the numbers follow no pattern at all.

The Character That Gave It Away

The space in that line is glyph 3, and code 3 reads as U+0003, a control character. Up to 8.2.0, officeParser left it in, so the line read +L\u0003WKHUH. Someone reading that could see something was wrong, and as issue #127 reported, a program could too: it dropped lines with such characters and told its user the page could not be decoded.

In 8.3.0 I took those characters out of all PDF text. PDFs from Chromium and LibreOffice leave stray control characters where a mapping was lost, and they have no place in text. That was right for those files, but it took away the one sign the broken ones gave, and it was never mentioned in the changelog. Twelve lines of such a font in 8.2.0 raised PDF_TEXT_ENCODING_SUSPECT, at 40% of characters unmappable. Since 8.3.0 they raise nothing of the kind, because the characters it counts have gone before it counts them.

A simple font can fall back to its code's own character too, but there the glyph's name can still say what it is. That is another post, and an open report with pdf.js. A composite font on /Identity-H has no such names to read.

Why the File Cannot Just Say

The obvious fix is to look at the font: no /ToUnicode on an Identity encoding, so warn. I started there. These are all the same dictionary but for its name and the codes drawn:

The fontCodes drawnReads as
Arial, embeddedArial's glyph numbers+LWKHUH
Named Arial, not embeddedArial's glyph numbersHi there
Any name, not embeddedUnicode code pointsHi there

In the second row pdf.js knows Arial's numbers by its name, so the codes are mapped after all, and that case can be told from the glyphs pdf.js returns. The third is harder. A producer can simply use Unicode code points as its glyph numbers. Tesseract's text layer does: I removed the /ToUnicode from a Tesseract PDF, and its text came out exactly the same. A warning on the structure alone would call that text garbage, and a caller who drops text on the warning would lose it.

So the control characters are not just the old symptom. They are the evidence. Real words in real characters don't have U+0003 in them, and text in low glyph numbers, where the space is glyph 3 as it is in Arial, does.

The Rule

A font is reported only when all of these hold:

  • Control characters were taken out of text in that font that stays in the output. Glyphs an /ActualText replaces don't count, since what they stand for is what you get.
  • It has readable text, not only blanks.
  • On every page with its text, its glyphs were seen and every one read as its own code. A page whose operators were cut short by a limit can't say, so the font is not reported.
  • Its dictionary is a composite font on an Identity encoding with no /ToUnicode stream.

The last check has to find a font's dictionary, and pdf.js gives a font's name but not its dictionary. My first version matched them by following the order fonts are set in each page's content. That read content streams the parser otherwise had no reason to read, and they spend the same bounded budget that reads /ActualText. On a long file, a warning changed the text of a later page. Now the judgement runs after every page is read, finds the font by name in the page's resources, and reads no content at all. A warning has no business changing what it warns about.

Using It

The warning comes once for each font name, with every page that has its text. A text run carries the same name, so you can find the lines themselves: 

import { parseOffice } from "officeparser";
import { readFile } from "fs/promises";

const ast = await parseOffice(await readFile(process.argv[2]));

for (const warning of ast.warnings) {
    if (warning.code !== "PDF_FONT_UNMAPPED") continue;
    console.log(warning.details.font, warning.details.pages);
}

const unmapped = new Set(ast.warnings
    .filter(warning => warning.code === "PDF_FONT_UNMAPPED")
    .map(warning => warning.details.font));
const readable = node => node.children
    ? node.children.map(readable).join("")
    : unmapped.has(node.formatting?.font) ? "" : node.text ?? "";
console.log(ast.content.map(readable).join("\n"));

On a page with one good line and the Arial line above, that prints: 

Arial [ 1 ]
A line that decodes

The text itself is left as it was. Whether to drop it, flag it or send the page to OCR is your call.

What It Misses

The rule prefers saying nothing to being wrong, so it stays quiet on a good deal of garbage:

  • No control character, no warning. If no code of the font falls in that range, as in a subset renumbered from higher up, the line reads ŵŶŝ and nothing is said. The same was true in 8.2.0. This is the biggest gap: I would rather read the embedded font and confirm the codes are glyph numbers, which is work for a later release.
  • PDF_TEXT_ENCODING_SUSPECT still does not count these characters. Counting them brought it back, along with false alarms on good prose in a font with no entry for its space, so it stays as it has been since 8.3.0 for now.
  • Encrypted files and files my reader cannot follow get no warning, because the font's dictionary is out of reach. Nor do fonts on an embedded CMap, or two fonts of one name on every page.
  • It can be wrong the other way. A font of Unicode codes with a stray control character among them is reported, which is why the message says "likely".

A warning that is sometimes silent is still useful, as long as it says what it knows and you don't read its silence as a guarantee. If a document matters, compare a page of its text with the page itself.
