When '250' Is More Than '1000': Comparing Numbers in a Template

Data from a spreadsheet is text, and as text "5000" comes before "800". Changing that would break templates that compare codes, so 8.8.0 keeps it, says so, and compares as numbers exactly when asked.

HA
Harsh Ankur
Published 12 November 2026 · 8 min read

A stock list is kept in a spreadsheet and exported for a template, so every value arrives as text. The template says which items to reorder: 

{{ for row in rows }}{{ if row.stock < row.reorderAt }}Reorder {{ row.name }}. {{ endif }}{{ endfor }}
bolts     stock "250"    reorderAt "1000"
nuts      stock "90"     reorderAt "100"
washers   stock "5000"   reorderAt "800"

officeParser renders that as Reorder washers. Bolts and nuts are running out and are not on the list; washers, of which there are plenty, are. Each comparison was right for what it compared: two texts, character by character, and "5000" comes before "800" for the same reason "apple" comes before "banana".

8.8.0 does not change that answer by default. It says so instead, and gives a way to compare such texts as numbers, exactly. This post is about why the default stays, what "exactly" takes when a number has twenty digits, and the other things 8.8.0 lets a condition do: filters, <>, and data written with more than one kind of decimal separator.

Why the Default Stays

Since 8.7.0, text compared with a number typed in the tag is read as that number: {{ if total > 100 }} with total: "250" is true. There, one side is plainly a number, so the other is meant as one. Between two texts there is no such clue. A spreadsheet column of text may be quantities, or it may be codes: part numbers, postcodes, ids, account numbers. Read as numbers, "007" equals "7", and a template that tells two codes apart would start treating them as the same. Changing the default would change documents that render correctly today, with no word.

So two texts still compare as text. What 8.8.0 adds is a warning, TEMPLATE_NUMBERS_COMPARED_AS_TEXT, when a condition orders two texts that both read as numbers. For the stock list, a render now reports: 

TEMPLATE_NUMBERS_COMPARED_AS_TEXT
{"tag":"{{ if row.stock < row.reorderAt }}","part":"word/document.xml","operator":"<",
 "left":"250","right":"1000","differs":true}
Template tag '{{ if row.stock < row.reorderAt }}' in word/document.xml compares two texts that read as
numbers, '250' < '1000', as text, character by character, which here answers otherwise than comparing them
as numbers. Set numericTextComparison to 'number' to compare such texts as numbers, or to 'text' to keep
comparing them as text without this warning.

It comes once per tag in a render or a check, for the first such comparison, however many rows the loop has. differs says whether comparing as numbers would have answered otherwise for that pair. Only <, <=, > and >= are reported: equality between two texts is what codes need, and is no sign of a mistake.

Comparing as Numbers, Exactly

numericTextComparison: 'number' compares two texts that both read as numbers as numbers, for every operator. The stock list then renders Reorder bolts. Reorder nuts., with no warning. 'text' keeps comparing them as text and says nothing, for a template that orders codes on purpose.

The obvious way to compare as numbers is to turn both texts into JavaScript numbers. That is wrong for the data this option is for. A double holds about sixteen significant digits, and an id often has more: 

Number('12345678901234567890') === Number('12345678901234567891')   // true

So 8.8.0 does not compare doubles. It reads a number from text as its sign, its digits with no leading or trailing zeros, and where the point stands among them, and compares those: the sign first, then where the point stands, then the digits as text, so no digit is ever rounded away. With {{ if order == last }} and those two ids, the answer is New order under 'number', as it is by default. The same reading makes "1.0" equal "1", and, as said above, "007" equal "7": the option is for columns of quantities.

A text compares as a number under 'number' only if it reads as one the way a number picture reads it: an optional sign, digits, a point, an exponent, white space around, all as dataNumberSeparators says. A text past the range of a double (about 1.8e308, such as "1e400") is no number there, as it is no number for format, and compares as text. A text beside a text that is no number compares as text too.

Filters in a Condition, and <>

A form answer is Yes, yes or YES. In 8.7.1 a condition had no way to compare it without case: {{ if answer == "yes" }} with YES is false, and a filter in a condition was refused: 

{{ if (answer | lower) == "yes" }}Confirmed{{ else }}Not confirmed{{ endif }}
8.7.1  TEMPLATE_SYNTAX: uses |, which a condition does not take (a filter goes on a field, and conditions are
       joined with or)
8.8.0  Confirmed

In 8.8.0 a condition's values take the same filters as a field: upper, lower, format, and your own formatters. A filter binds tighter than a comparison, so answer | lower == "yes" is the same as the parenthesised form, and {{ if (a | upper) == (b | upper) }} compares two columns without case. tags() lists the filters an if tag uses.

upper and lower are JavaScript's case mapping, the same in every language: "straße" and "STRASSE" are the same under upper, which is right for German, but the Turkish dotted and dotless i are not mapped the Turkish way. For one language's rules, a formatter of your own does it (fold: v => String(v).toLocaleLowerCase('tr')), and goes in a condition like any filter.

A word after | that is no filter leaves the tag as text, in a condition as in a field. A condition left as text has no block to open, so its {{ endif }} has nothing to close, and the render is refused with the reason named: 

{{ if (answer | lowr) == "yes" }}Confirmed{{ endif }}
TEMPLATE_SYNTAX: uses lowr after |, which is not a filter (format, upper, lower, or one of formatters)

And <> now reads as !=, as spreadsheets write it. 8.7.1 refused it ("uses <>; use != to compare"). A single = is still refused, with a message that asks for ==.

Numbers Written Two Ways

dataNumberSeparators, from 8.7.0, says how numbers written as text in the data are read: { decimal: ',', group: '.' } reads German or Brazilian data such as 1.234,50. But data often comes from two hands: a program that writes 12.50 and a person who types 12,50. One way reads only one of them. In 8.8.0 it takes a list, each way tried in turn. With Total: {{ total | format "#,##0.00" }}:

DataNot given{ decimal: ',', group: '.' }The list of both ways
"12,50"refusedTotal: 12.50Total: 12.50
"12.50"Total: 12.50refusedTotal: 12.50
"1.234,50"refusedTotal: 1,234.50Total: 1,234.50
"1250"Total: 1,250.00Total: 1,250.00Total: 1,250.00
"1.250"Total: 1.25Total: 1,250.00refused, ambiguous-number
"1.000"Total: 1.00Total: 1,000.00refused, ambiguous-number

The last two rows are the point of the list. 1.250 is twelve hundred and fifty written the German way, or one and a quarter written the English way, and nothing in the text says which. When the ways a list gives read a text as different numbers, it is refused with TEMPLATE_DATA_INVALID, reason ambiguous-number, and every reading in details.readings: 

{"reason":"ambiguous-number","tag":"{{ total | format \"#,##0.00\" }}","part":"word/document.xml","kind":"text",
 "readings":[{"separators":0,"decimal":",","group":".","value":1250},
             {"separators":1,"decimal":".","group":"","value":1.25}]}

That is a trade, and it is stated where the option is documented: such a list refuses a German whole number with one group separator, which the German way alone reads. If your data never writes a decimal with a point, keep the single German object, which reads exactly as it did. Where the ways agree, as both read 1250 as 1250, the text is that number. check() lists the refusal per data entry, so a batch shows which rows to fix: for 12,50, 1.250 and 12.50, only the second entry has a problem.

A comparison reads text the same way. With the list, {{ if price < 2000 }} and price: "1.250" is refused, where the German way alone answers true. Two texts under 'number' are refused the same way. Under the default they compare as text, and the warning leaves out differs, since there is no one number to compare.

What It Does Not Do

  • numericTextComparison is set for a whole render, not per tag. A template that compares quantities in one place and codes in another has to keep its codes from reading as numbers, or compare them with == under the default.
  • With one way given, nothing is ambiguous: { decimal: ',', group: '.' } reads 1.250 as 1250, as before, even if a program meant one and a quarter.
  • The warning names the first comparison of each tag that ordered two number texts as text. Later rows of a loop that do the same are not listed one by one.
  • lower and upper are not language-aware; a formatter is.

The options are in the README's template section and the changes in the changelog under 8.8.0. The Template Studio on the site has a sample of conditions to try them on.
