officeParser AST Structure Specification

The officeParser library produces a structured Abstract Syntax Tree (AST) that represents the parsed document in a format-agnostic way. This tree is designed for high-fidelity reconstruction and programmatic analysis.

OfficeParserAST (Root)

Property Type Description
type SupportedFileType The type of the parsed file (docx, xlsx, pptx, pdf, rtf, odt, ods, odp, odg, csv, md, html, epub, tex).
metadata OfficeMetadata Global document metadata (author, title, creation/modification dates).
content OfficeContentNode[] The hierarchical tree of document content nodes.
attachments OfficeAttachment[] Unified array of binary resources (images, charts, objects) referenced in the content.
auxiliary OfficeAuxiliaryContent | undefined Out-of-band layout / template elements that are not part of the main content flow. Contains headers, footers (from DOCX, ODT master pages, RTF, a PDF's running bands, or LaTeX fancyhdr), slideMasters (from PPTX), and outline (a PDF bookmark/TOC tree). Only populated when the respective ignoreHeadersAndFooters / ignoreSlideMasters flags are false.
warnings OfficeIssue[] Non-fatal issues encountered during the parsing phase (e.g. OCR failures, skipped nodes). Always check this after parsing if you use onWarning.
to(destination, config?) Promise<ConversionResult> Recommended: Universal entry point for generation. Converts the AST to text, md, html, csv, rtf, pdf, docx, odt, tex, epub, or chunks. Returns a ConversionResult with { value, messages }.

Node Interpretation Guide

Every node in the content tree follows a consistent recursive structure. Children are stored in the children array, and visuals are defined in formatting.

[!NOTE] Discriminated Union: OfficeContentNode is now a discriminated union type. Narrowing on node.type (e.g., if (node.type === 'heading')) gives precise metadata inference, with no type-casting needed.

OfficeContentNode

Property Type Description
type OfficeContentNodeType The functional role of the node (e.g., paragraph, table, list). Discriminant for type narrowing.
text string Flattened text content of this node and all its descendants. Useful for quick search/indexing.
children OfficeContentNode[] Recursive child nodes. Use these for high-fidelity rendering.
comments OfficeContentNode[] | undefined Comments/annotations attached to this node. Each entry is a comment node with CommentMetadata (author, date, commentId). Populated only when ignoreComments: false (default).
notes OfficeContentNode[] | undefined Footnotes, endnotes, or slide speaker notes attached to this node. Each entry is a note node. Populated only when ignoreNotes: false (default).
metadata ContentMetadata Type-specific configuration. The exact type is inferred from node.type when the discriminated union is narrowed (e.g., HeadingMetadata for type === 'heading').
formatting TextFormatting Styling applied to the node (bold, italic, size, color, etc.).
bounds NodeBounds Geometric page coordinates for this node in PDF page space. Present unless ignorePageGeometry is set.
rawContent string | undefined The raw XML or RTF source markup for this specific node. (Only if enabled in config).

Core Node Types

1. Lists (The list Node)

Lists are represented as a flat sequence of list nodes. To reconstruct the visual nesting (nested ul/ol), you must interpret the metadata.

  • indentation: Integer starting at 0. Represents the structural nesting level.
  • paragraphIndentation: Physical paragraph indentation formatting (e.g., left, hanging) measured in twips.
  • listType: 'ordered' or 'unordered'.
  • listId: A unique identifier for the list group. Use this to determine if adjacent items belong to the same logical list.
  • itemIndex: (Ordered lists only) The 0-based index of the item.
[!TIP] Interpretation Logic: Maintain a "List Stack". When indentation increases, push a new list container. When it decreases, pop the stack. If listId changes at the same indentation, start a new list block.

2. Tables

  • table: The container. Carries TableMetadata with optional anchorIds and align ('left' | 'center' | 'right'): where the table stands on the page, not how its columns are aligned (that is each cell's own align). Round-tripped from HTML data-align and, in Markdown, from an attribute list under the table ({align=right}).
  • row: A horizontal group of cells.
  • cell: A container for other content (paragraphs, images, or even nested tables). Use metadata for rowSpan, colSpan, and backgroundColor (populated from DOCX w:shd fills; also read from HTML colspan/rowspan attributes so merged cells survive an HTML round-trip).

3. Structural Containers

These nodes represent large-scale document sections:

  • slide: Container for PPTX/ODP slides and LaTeX beamer frames. metadata.slideNumber provides the position: for PPTX, the slide's place in the presentation's slide list, which is also the order slides are read in (a slide part the list no longer names is not read). Slide speaker notes are now attached via slideNode.notes[] instead of being inserted as top-level note nodes.
  • page: Container for PDF pages. metadata.pageNumber provides the position.
  • sheet: Container for XLSX/ODS spreadsheets. metadata.sheetName provides the label.

Title blocks. A document's typeset title is content, not only metadata: a Word paragraph in the Title style, or a LaTeX \maketitle (beamer \titlepage), is a heading whose metadata.style is 'Title'. LaTeX follows it with paragraphs styled 'Author' and 'Date' (and 'Subtitle' in beamer), with any \thanks as footnotes. The LaTeX generator typesets such a block with \maketitle. The same values also stay in ast.metadata.

4a. Layout & Template Nodes (Auxiliary)

These nodes are not part of the main content tree. They live under ast.auxiliary:

  • header: A running page header: DOCX headers, ODT master-page headers, RTF \header groups, a PDF's top-band running header, or LaTeX fancyhdr fields. Carries HeaderFooterMetadata.type ('default', 'first', 'even'). Found in ast.auxiliary.headers[].
  • footer: A running page footer, from the same sources. Same metadata. Found in ast.auxiliary.footers[].
  • slideMaster: A PPTX slide master. Carries SlideMetadata. Found in ast.auxiliary.slideMasters[].
  • outline: A PDF bookmark / table-of-contents tree. Found in ast.auxiliary.outline.

4b. Annotation Nodes

  • comment: An inline comment or annotation attached to a document node via node.comments[]. Carries CommentMetadata: author, initials, date, commentId, and for a reply in a PowerPoint comment thread parentId (the commentId of the comment it replies to).
  • comment with sourceSyntax: 'html': A source comment, <!-- ... --> from Markdown (always) or HTML and EPUB (under htmlParserConfig.preserveComments): the author's hidden note, as a block node or inline in a run. text holds the raw body verbatim; it has no children. The Markdown and HTML generators re-emit it, and the LaTeX generator writes it as % <!-- ... --> lines that the LaTeX parser reads back; every other output format omits it.

4c. Markdown-Dialect Nodes

These node types are produced by the extended Markdown/HTML dialect support (task lists, admonitions, embeds, definition lists) and round-trip symmetrically between Markdown, HTML, and EPUB.

  • admonition: A callout/alert block (GitHub > [!NOTE] or GLFM :::note ... ::: on import; LaTeX beamer blocks and the LaTeX generator's coloured admonition boxes read back the same way). Carries AdmonitionMetadata.admonitionType ('note' | 'tip' | 'important' | 'warning' | 'caution'), an optional title and anchorIds. Has children for its block content.
  • embed: A rich embed such as a YouTube video. Carries EmbedMetadata: embedType, videoId, url, width, align.
  • definitionList / definitionTerm / definitionDescription: Markdown Extra-style definition lists (Term\n: Definition). The list node's children alternate term and description nodes. Each may carry DefinitionMetadata.anchorIds.
  • list task-list items: ListMetadata.isTask and .checked mark a GFM task-list item (- [x] Done).
  • Text-node metadata additions: TextMetadata.citationKey (Pandoc/MultiMarkdown [@key]), .wikilink (Obsidian [[page]]), and .abbreviationTitle (Markdown Extra *[HTML]: ... abbreviations).
  • Equations are code nodes carrying CodeMetadata.math ('inline' | 'block'), with node.text holding bare LaTeX. Every format that can carry an equation produces this same node: OOXML <m:oMath> (DOCX, PPTX), MathML <math> (ODT/ODP/ODS embedded objects, HTML, EPUB3), Markdown $...$/$$...$$, and LaTeX $...$/\(...\), \[...\] and the equation/align/gather environments (user macros expanded).

4. Rich Content

  • image: References an item in the root attachments array via metadata.attachmentName. Also carries optional width and align ('left' | 'center' | 'right'), round-tripped from HTML data-width/data-align or an inline style="width:...". An image that is a link (a badge, a clickable picture) carries link, linkType ('internal' | 'external') and an optional linkTitle, as a linked run carries them on TextMetadata.
  • chart: References a chart attachment. Contains structured chartData in metadata if requested.
  • drawing: A vector drawing or shape. A member of the node-type union; it carries no type-specific metadata (undefined/none).

5. Breaks (The break Node)

Breaks are added as break nodes when includeBreakNodes is enabled in the configuration. They represent physical layout changes within the document flow. DOCX writes them inline (w:br/w:cr), so they appear as children of the paragraph; ODF carries page and column breaks on the paragraph style (fo:break-before/fo:break-after), so those are emitted as siblings around the paragraph. LaTeX \newpage/\clearpage become page breaks between blocks, and \\/\newline stay inside the paragraph as line breaks.

  • breakType:
    • 'textWrapping': Standard line break (Shift+Enter). This is the default break type.
    • 'carriageReturn': Explicit hard return (w:cr), often used for legacy compatibility.
    • 'page': Hard page break, forcing subsequent content to a new page.
    • 'column': Column break, moving text to the top of the next column in multi-column layouts.
    • 'lastRenderedPage': A "soft" page break marker indicating where a page naturally ended during the last render.
    • 'thematic': A thematic break / horizontal rule (Markdown ---/***/___, HTML <hr>).
  • clear: (Only for textWrapping) Specifies where the next available line should start when wrapping around floating objects (all, left, right, none).
  • anchorIds: Bookmark ids on a rule or page break (HTML <hr id>, a Markdown <a id> line before ---), so a link can target it.
[!NOTE] Plain Text Conversion: Even though break nodes have no text property, ast.to('text') automatically converts them into newlines (\n) or the configured newlineDelimiter to preserve the document's visual structure.

OfficeIssue Interface

All warnings and errors from both parsing (ast.warnings) and generation (result.messages) use this unified shape:

interface OfficeIssue {
    type: 'warning' | 'info' | 'error';
    code: OfficeWarningType | OfficeErrorType; // typed enum, e.g. 'OCR_FAILED'
    message: string;
    node?: OfficeContentNode; // the node that triggered the issue, if applicable
    details?: any;            // original error object or extra context
}

Use issue.code for programmatic handling (e.g. if (issue.code === 'OCR_FAILED') { ... }).

Thrown errors carry the same object on error.officeIssue, so a failed parse is identified by the same stable code, rather than by matching message text:

try {
    const ast = await officeParser.parseOffice(buffer, { fileType: 'docx' });
} catch (err) {
    switch (err.officeIssue?.code) {
        case 'ZIP_NO_ENTRIES_FOUND':  // not a ZIP archive at all
        case 'ZIP_TRUNCATED':         // cut off in transfer, entries incomplete
        case 'REQUIRED_PART_MISSING': // readable ZIP, but not the format it claims
            console.error('Unusable file:', err.officeIssue.message);
            break;
        default:
            throw err;
    }
}
[!IMPORTANT] A corrupt file throws; it does not parse as an empty document. If an archive is not readable, is truncated, or is missing the part its format requires (word/document.xml, xl/workbook.xml, ppt/presentation.xml, ODF content.xml, the EPUB OPF), parsing rejects with one of the codes above, so an empty result means the document really is empty. Files that are legitimately empty still parse and say so through onWarning / ast.warnings (NO_WORKSHEETS_FOUND, NO_SLIDES_FOUND).

OfficeMetadata Extensions

Two new fields added to the root ast.metadata object:

  • keywords (string): Keywords associated with the document, extracted from document properties.
  • language (string): The document's primary language as a BCP-47 tag (e.g. en-US).
  • nativeProperties (Record<string, any>): All format-specific metadata extracted verbatim. Examples:
    • HTML: All <meta> tag values indexed by name / property
    • DOCX: docProps/app.xml entries (e.g., Pages, Application)
    • XLSX: docProps/app.xml entries
    • PDF: Raw pdfjs document info dict and XMP metadata object
    • Markdown: YAML frontmatter key-value pairs
    • LaTeX: documentClass, classOptions, packages, plus date/subtitle (the \date/\subtitle text)

Programmatic Traversal Best Practices

  1. Depth-First Search: Use recursion to walk the children tree for rendering.
  2. Fallback to .text: If you only need plain text, use the text property of any node: it is pre-calculated to include all text from its children.
  3. Map Attachments First: Before rendering, create a Map from the attachments array using the name property for O(1) lookups when encountering image nodes.
  4. Traverse node.notes and node.comments: These arrays are separate from children and will not appear during a standard DFS of children. Iterate them explicitly if you need footnotes, endnotes, or comments. A note or comment referred to from several places is one node each reference holds: skip one you have already handled, by identity, and do not mutate it expecting one reference to change.
  5. Access Auxiliary Content via ast.auxiliary: Headers, footers, and slide masters are not in ast.content. Access them via ast.auxiliary?.headers, ast.auxiliary?.footers, or ast.auxiliary?.slideMasters.
  6. Type Narrowing: Narrow on node.type before accessing node.metadata to benefit from precise TypeScript inference (e.g., node.type === 'cell' && node.metadata?.backgroundColor).
